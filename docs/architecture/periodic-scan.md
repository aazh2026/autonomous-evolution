# 定时项目扫描 —— 看得见那些"没有发生"的问题

设计依据：`docs/tasks.md` TASK-P3-012（交付物：`core/evolution/scan.py`
扫描契约、`orchestration/scan.py` 基于索引的扫描器、`apps/scheduler/scan_job.py`
定时调度器；验收条件"定期扫描能发现事件触发发现不了的问题（跨模块耦合类）"；
验证 T1 + T2）、R-080（定期扫描与事件触发结合）、`docs/design.md` §4（六个触发
源：定时 / 代码 / 质量 / 运行 / 外部 / 知识）。

> **六个触发源里有五个是"某件事发生了"才来的。** 提交、流水线失败、用户反馈、
> 依赖漏洞 —— 它们各自指向一个具体的地方。**跨模块耦合不是这种形状的问题。
> 它没有事件。**
>
> 一个模块被七个模块依赖、而它自己一条用例都没有：没有任何一条事件会宣告这
> 件事发生。**一切都正常** —— 流水线是绿的、用例是全过的、没有人报错。只有
> 把整个仓库摊开看，才看得见。

## 0. 一句话

**事件驱动的那一半天生只看局部；定期扫描补的就是另一半。** 两者不是二选一
—— 少了定时扫描，长期积累的结构性问题永远浮不上来；少了事件驱动，局部变化
又要等到下一次定时才被看见。

## 1. 三层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 契约 | `core/evolution/scan.py` | 定义扫出什么、怎么算"扫过了" | 不知道仓库长什么样 |
| 编排 | `orchestration/scan.py` | 从索引推导信号、信号转候选 | 不做处置决策 |
| 调度 | `apps/scheduler/scan_job.py` | 到点就扫、只对新问题开轮 | 不写库 |

**分三层是因为形状不同，抄本迟早对不上。** 契约层在 `core/`，它连"索引"这个
词都不该出现 —— 它只定义"一条信号长什么样"。推导需要架构模型，而架构模型在
`knowledge/`，那是比 `core/` 高的一层。处置是决策层的事（P1-054 的 record /
defer / reject）—— 扫描器替它做判断就是越权。

**信号不是候选，候选不是任务。** 一条信号说"这里有个耦合枢纽，fan_in 是 5"；
它不说"该重构"。信号 → 候选是编排层的 `candidates()`；候选 → 任务是决策层
的事。

## 2. 五种信号

全部五种都是**从索引里推出来的事实**，不是判断：

| 种类 | 推法 | 事实 |
| --- | --- | --- |
| `dependency_cycle` | 强连通分量（Kosaraju，迭代版） | 环上有哪些模块、多大 |
| `coupling_hub` | 数扇入 | fan_in / fan_out / impact / 依赖者名单 |
| `layer_violation` | 查依赖方向 | 谁依赖了谁、违规类型 |
| `untested_module` | 查"有没有用例 import 过这个模块" | 公开接口有几个 |
| `orphaned_public_api` | 查"有没有用例 import 过这些符号" | 符号名单 |

**唯一的判断成分是阈值，而阈值写在策略里，与结论分开。** "fan_in 到 5 才算
枢纽"是**本仓库选的默认值**（`DEFAULT_COUPLING_HUB_THRESHOLD`）；"这个模块的
fan_in 是 5"是**从索引里读出来的事实**。两者混在一起说，就分不清"我们认为
它高"与"它确实高"。

**后两种说的是"覆盖缺口"，不是"死代码"。** 静态分析看不见运行时：属性访问
（`obj.method()`）、插件式注册、动态 `getattr` —— 用例可能真的在用它，只是索
引里看不出来。所以 `orphaned_public_api` 的准确读法是"**没有任何用例 import
过它**"，不是"没人用它"。这个区别决定了下一步该做什么：前者是补一条用例
（或者加一条显式的豁免说明），后者才谈得上删。

## 3. 为什么"没开轮"必须说得清

定时扫描天天跑同一个仓库。同一个问题天天报一遍、天天开一轮，预算几天就烧光
了 —— 所以**只有新出现的信号才值得开一轮**。

"新"靠**身份**判定：`ScanSignal.fingerprint` 只由种类与涉及的模块决定，**不含
时间、不含计数**。被依赖数从 5 涨到 9，它还是同一个问题 —— 变了的是 `facts`，
不是身份。所以"耦合环还在"这件事在两轮扫描之间是可比的，而"今天多了一个新
的耦合环"是能被认出来的。

**"没开轮"有四种，必须分开说：**

| 情形 | `reason` |
| --- | --- |
| 没到期 | `due()` 返回 `False`（压根不跑） |
| 没有新问题 | "这次扫描没有新问题 —— 上轮报过的都还在，没有新冒出来的" |
| 没接触发器 | "有新的扫描结果，但没有接演进触发器 —— 出了报告，没有开轮" |
| 被去重窗口挡下 | `suppressed_by_window=True`，理由来自窗口 |

**"有新的，但窗口说不行"与"压根没有新的"是两件事。** 混成一句"跳过"，就没人
知道该修哪儿 —— 前者要调窗口或换触发源，后者什么都不用做。

**新信号走事件而不是直接调演进循环**，是因为事件那一侧有去重窗口（P1-064）：
扫描产出的事件类型固定（`scan.found`）、主体是项目，于是两轮扫描报出同样的
问题时，第二轮落在同一个指纹上被窗口挡下。这正是我们要的行为。

## 4. 实测：T1

**测的是"能不能看出来"，不是"看到了什么格式"。** 用例钉在一个**真能跑、但整
体有毛病**的仓库上（`tests/support/coupled_repo.py`）：耦合枢纽、循环依赖、
依赖方向反了、没人测的模块、没人用的接口。

**那个仓库是照着验收条件造的。** 它刻意安排成"全绿" —— 只有当仓库看起来完
全健康时，"扫描发现了事件发现不了的问题"这句话才站得住；否则读的人分不清扫
出来的是**问题**还是**本来就坏掉的东西**。

`tests/system/test_periodic_scan.py` 是验收测试，两边都证：

- **事件侧是空的** —— 子进程真跑那个仓库自己的 pytest：**2 passed**，退出码 0。
  流水线全绿 → 没有失败事件 → 六个触发源里没有一个会为耦合枢纽开轮。
- **扫描侧找到了** —— 一次扫描报出 **20 条信号**，覆盖 **5 种**种类。

同时有一条断言防"空壳仓库"：光看退出码 0 是不够的（零个用例也算全绿），所以
还断言了 `"passed" in stdout` 且 `"no tests ran" not in stdout`。

**环是导入层面的，不是调用层面的。** `pkg.ring_a` 与 `pkg.ring_b` 互相 import，
但函数不互相递归 —— 一个绕回来的依赖环在运行时会无限递归，那是另一个问题。
这里要的是"改哪一个都像被另一个卡住"，而仓库本身是好的、跑得起来的。

## 5. 实测：T2

**可量化的数。** 在那个 15 个模块的仓库上：

| 指标 | 值 | 怎么来的 |
| --- | --- | --- |
| 事件侧发现数 | **0** | 流水线全绿，没有任何失败事件 |
| 扫描侧发现数 | **20** | 一次 `scan()` 的 `len(report.signals)` |
| 耦合枢纽 | **1**（`pkg.hub`） | fan_in = **5**、fan_out = **0**、impact = **6** |
| 依赖环 | **1**（2 个模块） | `pkg.ring_a → pkg.ring_b → pkg.ring_a` |
| 分层违规 | **1** | `pkg.importer` → `tests.helpers`（产品依赖测试） |
| 没人测的模块 | **7** | 有公开接口、无任何用例 import 过 |
| 没人用的公开接口 | **10** | 有公开符号、无任何用例 import 过 |
| 生成的候选 | **20** | 一条信号一个候选，证据是真实文件路径 |
| 被扫过的模块数 | **15** | 报告里的 `examined_modules` |

**fan_in 是 5、impact 是 6 —— 这两个数不是同一个数，而且都对。** 扇入是"直接
依赖我的"（5 个用户模块）；影响面是"改了我会波及的"，多出来的那 1 个是用例
`tests.test_users` —— 它依赖 `pkg.user1`，而 `pkg.user1` 依赖 `pkg.hub`，所以
它被间接波及。

**"跨模块耦合类"这句话的依据**：耦合枢纽涉及多个模块，且它描述的是**被依赖**
这件事 —— 把 `pkg.hub` 单独拿出来看，它没有任何毛病（一个函数、一个返回值）。
毛病只在**模块之间的关系**里。

**时间**（本机、15 个模块的小仓库）：

| 步骤 | 耗时 |
| --- | --- |
| `build_index` | 0.98 ms |
| `build_architecture` | < 0.01 ms |
| `scan()` | 0.26 ms（热身后 0.165 ms） |
| `candidates()` | 0.12 ms |

**扫描读索引，不读仓库** —— 这正是 TASK-P2-016 的验收条件要求的形状（R-064）：
扫描是**定期**跑的，一次全量重读仓库的成本会被放大成"每天一次全仓库遍历"，
而读索引只要零点几毫秒。

## 6. "空报告"有三种

一个空报告，可能是三件完全不同的事：

1. **扫了，没发现问题** —— `examined_modules > 0`；
2. **没扫这一种** —— 种类不在 `policy.kinds` 里；
3. **压根没有数据可扫** —— `examined_modules == 0`。

第 3 种最容易被当成第 1 种：只看信号列表时它们长得一模一样。所以被扫过的模块
数放在报告里 —— 它是三种情况里唯一能一眼分辨的那个。**范围写错了（模块前缀
对不上任何东西）就是第 3 种，不是第 1 种。**

## 7. 没测的，和已知的不足

**没测的：**

- **没有接上真正的调度器。** `ScheduledScanner` 是"到点就跑"的逻辑，`due()` 与
  `run()` 都在；**把它挂到 cron / 定时任务上的那一段没做** —— 那一段属于
  阶段三的编排（TASK-P3-010 Temporal），不属于这一层。
- **没有落库。** 扫描结果留在报告里，由调用方决定怎么落。落库是演进流水线
  的事（P3-013）。
- **没有真实项目的基线。** 上面那些数字全部来自**本仓库造出来的那个 15 模块
  的仓库**。它在设计上就带着三类问题，真实仓库的问题分布是什么样的 —— **没
  测过**。在真实仓库上跑一遍、看看阈值定在哪合适，是下一步。

**已知的不足（不是设计，是缺口）：**

- **扫描历史只活在内存里。** `InMemoryScanHistory` 进程重启就忘了 —— 重启后
  第一轮扫描会把上轮报过的问题当成新的再报一遍。多报一次不会造成损失（决策
  层会 reject 掉重复的），但它确实是个缺口：真正的做法是把这份历史落到库里，
  与周期记录放在一起。
- **符号级的判断看不见属性访问。** `tests/test_users.py` 写的是 `from pkg
  import user1` 然后 `user1.use()` —— 模块被引用了，符号没有。所以 `pkg.user1.use`
  会被报成"没有任何用例引用过"。**这不是 bug，是静态分析的边界**，已写进
  `ScanKind` 的文档与一条专门的断言里。
- **`fan_in` 与 `impact` 容易被混用。** 两个数都在报告里，但它们回答的不是同
  一个问题 —— 前者是"谁直接依赖我"，后者是"改了我会波及谁"。

## 8. 与设计要求的关系

| 要求 | 落在哪 |
| --- | --- |
| R-080 定期扫描与事件触发结合 | `apps/scheduler/scan_job.py`：扫描事件走 `TriggerSource.SCHEDULE` 进事件那一侧的去重窗口 |
| R-064 不每轮重读仓库重建认知 | 扫描器读 `ArchitectureModel`，不读仓库 |
| R-029 证据必须可独立核验 | 候选的 evidence 是**模块在仓库里的那个文件路径** —— 拿着它就能去看、去改 |
| R-033 假设要能被事后比 | 每条信号带 `hypothesis` 与 `expected_outcome` —— 事后拿实际收益来比 |
| R-028 候选要有真实证据 | 一条信号一个候选，20/20 都带上了真实文件证据 |
