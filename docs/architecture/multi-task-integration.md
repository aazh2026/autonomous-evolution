# 多任务集成引擎 —— 检得出、挡得住、落得下

设计依据：`docs/design.md` §3.5C（Task Branch → Local Validation → Integration
Branch → Cross-task Integration Test → Architecture & Regression Test → Merge
Approval → Main；"单任务通过测试，不代表多个任务集成后也通过测试"）；
`docs/tasks.md` TASK-P2-017（交付物 `harness/integration/multi_task.py`；验收
"构造两个各自单测通过但联合运行时产生符号冲突的任务，集成引擎精准检出并阻断
合并"）、R-056（集成流水线顺序）、R-057（必须做跨任务集成测试）、R-058（独立
Integrator 解决冲突并回归）；TASK-P1-047（单任务集成路径）。

> **一批任务合在一起，才会出"合在一起才出"的错。** 每个任务单独看都是好的 ——
> 它的单测过了，它的契约过了，它自己的分支是绿的。**错在合上之后才显形。**
>
> **静默的错误比报出来的错误危险。** 文本冲突 git 会报，报了就能改。**符号冲
> 突 git 挡不住** —— 两个任务各自新增了同一个函数，git 合得干干净净，Python
> 也照跑不误（后一个定义把前一个盖掉），而合出来的代码已经不是人写的那份了。

## 0. 一句话

**TASK-P1-047 管"一个任务合进 main"，这一层管"一批任务合进 main"。** 差的不
只是数量 —— 是三样只有在合在一起时才看得见的东西：文本冲突、符号冲突、联合
回归。

## 1. 一个文件，两段

| 做什么 | 怎么做 | 不做什么 |
| --- | --- | --- |
| 汇入集成分支 | `integrate()`：本地验证 → 逐个汇入 → 符号检查 → 联合回归 | 不碰 main |
| 推进 main | `merge_to_main()`：审批 → 暂存合并 → main 上复验 → 提交 | 不推到底，等人表态 |

**分成两段是因为审批要等人。** 等人的那段时间里，引擎不该占着工作区，更不该
把半截结果往前推。所以 `merge_to_main()` 走到 `AWAITING_APPROVAL` 就停 —— 人
批了之后再调一次。

**集成分支是草稿，不是产物。** 产物是 main。所以任何一步没过，集成分支都被
拨回 main 原来的位置（`reset --hard`）—— **半截的集成没有意义**，还会让下一
轮跑同一条分支时被上一轮的残留污染。

**只复位带 `integration/` 前缀的分支。** 别的分支不是草稿，复位它们就是在毁
掉别人的东西。引擎在请求里就把前缀钉死了（`INTEGRATION_BRANCH_PREFIX`），
并且**拒绝**在集成工作区与 main 工作区是同一个目录时开跑 —— 那时一次
`reset --hard` 就能抹掉 main 的现场。

## 2. 次序是死的

```
本地验证（逐个任务） → 汇入集成分支（逐个任务） → 符号检查 → 联合回归 → 审批 → main 上复验 → 提交
```

**每一道都在下一道前面，因为后一道的结论依赖前一道的前提：**

- **先验后合。** 没验过的分支不该被合进来 —— 它连自己那关都没过。
- **符号检查在合并之后。** 冲突只在合在一起时才看得出来 —— 任务分支各自都
  是绿的。
- **联合回归在符号检查之后。** 符号都打架了，跑出来的回归结论没有意义。
- **先暂存再验证。** 与 TASK-P1-047 同一套规矩：合并结果停在索引与工作区
  里，在 main 上复验通过了才提交。**main 一个提交都没有前进过，直到验过为止。**

### 2.1 三态，不是两态

**"没验成"与"验了没过"是两件事**，处置也不同：

| 状态 | 阶段 | 该做什么 |
| --- | --- | --- |
| 通过 | `INTEGRATED` | 进审批 |
| 没过 | `*_FAILED` | **返工** —— 改代码再来 |
| 没验成 | `*_ERRORED` | **阻塞** —— 环境的问题，改代码没用 |

**缺实测值是 FAILURE，不是 0。** 工作区没了、验证引擎跑不起来 —— 那不是
"过了"。这一层（`harness/verification/engine.py`）本身就有三态，这一层只是
**不把它压扁**。

**清场失败不许盖掉原来的结论。** 集成分支收不干净是运维的事，这一批为什么
没过是另一回事 —— 后者才是调用方要拿去做决定的。

## 3. 符号冲突怎么判

这是这一层最要紧的一处判定，所以规矩写死：

| 判据 | 为什么 |
| --- | --- |
| **只认 `.py`，只认顶层定义** | 别的语言按猜出来的规则去判，比不判更糟；嵌套在函数里的东西不构成命名空间冲突 |
| **解析不了就当没有符号** | 语法错误是别的事（编译检查会报），这一层不越权替它下结论 |
| **只声明"新"符号** | 基线取的是**与 main 的共同祖先**，不是 main 现在的头 —— 已有符号被改动不算声明，那种情况 git 的文本冲突管，而且 git 管得住 |
| **同一个路径 = 同一个模块** | 文件路径就是模块的身份 |
| **内容一样不算冲突** | 两个任务写了同一个定义 —— 那不是"打架"，那是"做了同一件事"，合出来还是那一份。这类可以自动消解，不该挡住合并 |
| **只有两个以上任务才算冲突** | 一个任务声明一个符号不叫冲突 |

**报出来要说得出是谁。** `SymbolConflict` 带着路径、符号名、涉及的任务，以及
一句人话：

```
mod.py 里的 calculate：任务 task-a、task-b 各自定义了一份，内容不同
```

只说"有冲突"的话，人还得自己去查 —— 而查出来之前，这一批是停着的。

## 4. 审批绑在具体的提交上

**人批的是他看到的那份内容。** 所以审批请求的 diff 摘要第一行是
`commit:<集成分支的提交号>`，机器可读，人也看得见：

```
commit:8f2a1c0e9b3d...
两个任务合到一起
```

**集成分支变了，旧批准就不再成立。** `_approval_for()` 复用审批请求的前提是
"它批的就是现在这个提交"；覆盖不到当前提交，就另起一条新的。判定落在**那
一条**请求上，而不是"这个任务最近的一条" —— 后者一变结论就跟着变，而人批的
东西没变。

## 5. 怎么跑

```bash
# 演示：真的建仓库、真的撞符号冲突、真的合并到 main
.venv/bin/python scripts/demo_multi_task_integration.py

# 单测（40 条）：次序与处置
.venv/bin/python -m pytest tests/unit/harness/integration/test_multi_task.py -q

# 集成测试（13 条）：真 git
.venv/bin/python -m pytest tests/integration/test_multi_task_integration.py -q
```

演示分三步：

1. **符号冲突** —— 两个任务各自绿，引擎精准检出（说得出文件、符号、哪两个
   任务），main 一个提交都没前进；
2. **联合回归** —— 两个任务各自绿，合在一起不绿，联合回归挡下；
3. **都通** —— 一批任务落到 main 上，审批真的要人批。

**单测用假 git，真 git 另有一组。** 假 git 记的是"做了哪几步"，所以"先验后
合、冲突要撤销、失败要清场"能被一条断言钉住；真 git 才会在"暂存了但没提交"
的时候，让 main 的工作区真的停在半路。

## 6. 边界

- **这一层不落任务状态。** 与 `orchestration/gates` 同一套做法：算结论、给迁
  移，写状态的是调用方。
- **这一层不排期。** 谁先谁后是 `orchestration/dag_scheduler.py` 的事；这一层
  只管"给你一批任务，按你给的顺序合"。
- **这一层不解决冲突。** R-058 说的"独立 Integrator 解决冲突"指的是**人或者
  另一个角色**去改；这一层负责**检出**并**挡住**，把该返工的批次报清楚。
- **这一层不重试。** 重试是有界修复那条线的事（`orchestration/repair.py`）。
- **这一层不碰 `orchestration/` 与 `agents/`。** `harness/` 不得反向依赖编排层
  （`tests/unit/harness/test_layering.py` 用 AST 卡着）。
- **集成工作区必须与 main 工作区分开。** 引擎拒绝在同一个目录上开跑。
