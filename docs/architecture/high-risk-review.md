# 高风险变更治理 —— **标记为高风险的变更，100% 经过独立评审才可执行**

设计依据：`docs/tasks.md` TASK-P4-060（交付物"架构级变更的独立评审与放行流程"；
验收条件"**标记为高风险的变更 100% 经过独立评审后才可执行**"；验证 T1 + T2）、
R-061（高风险操作独立授权）、R-102（不得自主修改控制自身的系统）、
`docs/design.md` §3.5D（"删除、发布、合并、部署等高风险操作有独立授权"）、§7。

> **一份改动要不要多审几遍，取决于它这一次有多危险；谁来审，取决于它改的是哪
> 一类东西。**
>
> 这两件事问的不是同一个问题，混成一件就一定会错。把"要几份"按**种类**写死，
> 那么"今天这次合并是高风险、明天那次是低风险"这件事就没法表达 —— 而风险恰恰
> 是**逐次**的。反过来，把"谁来批"按**风险**分，那么"改架构要架构评审人"这条
> 就丢了 —— 改架构不管风险多高，都得有人看得懂架构。
>
> 所以规矩分成**两条轴**：**操作 → 风险档 → 份数**；**种类 → 资格下限 → 谁来
> 批**。**两条轴交叉的那一点，才是一次变更要走的全部流程。**
>
> 而最要紧的一句是"**独立评审**"。**一个人批自己提的东西不叫评审**；一个人点
> 两次批准也不叫两份意见；一份批准签在"提案编号"上、内容事后被改了，也不叫批
> 过了那一份改动。这三样都要在代码里挡住 —— 不是写在文档里就算数。

## 0. 一句话

**标记为高风险的变更走四步：提交 → 发起评审 → 记录评审 → 放行；份数由风险档
推出来、资格由改动种类推出来，资格只认名册；放行前从评审存储里把结论重新取回
来核对 —— 伪造一份"已批准"的对象也放行不出去，审计写不进去就一步都不往下走。**

## 1. 缺口在哪

旧审批门（`core/policy/approval.py`）做的是"** somebody ≠ 提出人** 表态一次就放
行"。它挡住的是自批，挡不住下面这几样：

| 缺什么 | 后果 |
| --- | --- |
| **只有一个人表态就能放行** | 高风险改动（合并、部署、改治理）同样只要一票 |
| **不知道这一份有多危险** | 风险是**逐次**的，合并到主干和跑个测试不该一样重 |
| **没人知道批的人懂不懂** | 让一个只懂测试的人去批改架构的改动，等于没批 |
| **批的是"这条审批请求"而不是"这一版改动"** | 批完之后偷偷改内容，批准照样生效 |
| **没有人可以说"这份改动不算高风险"** | 风险只能由规矩给 —— 提的人给不了 |
| **没有"放行只有一条路"的保证** | 任何一处"直接执行"的口子，前面几道关全成摆设 |

**后三行是这一层存在的全部理由。** 前两行好办 —— 实体校验就能挡住。

## 2. 两条轴

### 2.1 第一条轴：操作 → 风险档 → 要几份

**风险档先由操作定下来**，因为有些操作**天生**就是高风险：

| 操作 | 风险档 | 最少独立评审 | 为什么 |
| --- | --- | --- | --- |
| `merge_to_main` | 高 | **2** | 合进主干 —— 影响所有人 |
| `production_deployment` | 高 | **2** | 上生产 —— 出事就是线上出事 |
| `modify_governance` | 高 | **2** | 改"谁能批、怎么批" |
| 其它操作 | 中 | 1 | 一次代码改动、一次测试 |

**份数再由风险档推出来**，而**不是**再写一份表：

| 风险档 | 最少独立评审 |
| --- | --- |
| 低 | 0 |
| 中 | 1 |
| **高** | **2** |

> **为什么份数表不按种类分。** 风险是**这一次**的属性。同一类改动，这一次是高
> 风险（合并、部署）、那次是低风险（本地改个注释），是常事 —— 所以"要几份"必
> 须由**风险档**推出来。要是按种类写死，"这一次标了高风险"这件事就表达不出来，
> 而验收条件说的正是"**标记为高风险的**变更"。
>
> **为什么高风险要两份。** 一份是自证 —— 提出人自己写、自己批、自己说"我看过
> 了"。**两份才意味着另一个人也看了。**

### 2.2 第二条轴：种类 → 资格下限 → 谁来批

**"看得懂吗"跟着改动的种类走**：

| 种类 | 风险下限 | 最少独立评审 | 要求的评审资格 |
| --- | --- | --- | --- |
| `code_change` | 中 | 1 | （无 —— 通用资格即可） |
| `configuration_change` | 中 | 1 | （无） |
| `dependency_change` | 高 | 2 | **security** |
| `architecture_change` | 高 | 2 | **architecture** |
| `acceptance_criteria_change` | 高 | 2 | **governance** |
| `policy_change` | 高 | 2 | **governance** |
| `governance_change` | 高 | 2 | **governance** |

> **为什么通用资格不顶替专门资格。** `general` 的意思是"看得懂这一段改动" ——
> 拿它去顶"看得懂架构"，等于把门槛降低成"什么都会一点的人"。**改架构就得有人
> 真的懂架构。**
>
> **为什么每一项资格都要有人持有，而不是一个人持有全部。** 架构与安全是两个人
> 分别看得懂的东西 —— 让一个人同时具备两项资格，是把门槛抬高到另一种不必要。

### 2.3 两条轴交叉

一次变更要几份评审、要求什么资格，是**两个下限取严**的结果：

```
风险档 = max(操作天生的风险, 种类天生的风险)
份数   = 风险档推出来的下限（项目可以再往严里加）
资格   = 种类天生的下限（项目可以再往严里加）
```

**提变更的人给不了这两样。** 他能写的只有"改什么、为什么改"；**算多高风险、要
几份评审、要什么资格**，是规矩说了算。而**提的人可以往高里标，不能往低里标**
—— 往低里标的那一份，压根建不出来。

**规矩只能往严里加。** 写一个比下限更松的值，**策略压根建不出来**
（`ValueError`，不是被悄悄忽略）。

> **为什么"更松就报错"而不是"更松就取下限"。** 悄悄忽略会让人以为那份配置生效
> 了 —— 于是"我明明把它放松了啊"这种误解会一直传下去。**报错**才说得清。

## 3. 名册：资格不住在结论上

**这是这一层与 TASK-P4-070 最大的不同。** 自我改进流程里，评审人的资格记在他
自己签的那份结论上（`ProposalApproval.scopes`）；**这里不这么干**。

> **为什么。** 评审结论是评审人**自己写的** —— 他可以在结论上写"我是架构评审
> 人"。**自己给自己签发资格，那份资格就不独立。** 所以资格住在**名册**
> （`core.policy.high_risk.ReviewerRegistry`）里，**流程去查名册**，而不是查结
> 论上的自称。
>
> **所以 P4-060 的评审结论里压根没有"资格"这个字段。** 不是忘了记 —— 是**记
> 了就等于让结论上的自称说了算**。

名册的三条规矩：

| 规矩 | 挡的是什么 |
| --- | --- |
| **不在册就不能评审** | 随便一个人签个字就算评审 |
| **通用资格不顶替专门资格** | "什么都会一点的人"顶替"真的懂架构的人" |
| **要求为空时也仍然要在册** | "没要求资格"≠"谁都能评" |

## 4. 状态机

**六个状态，一个不多一个不少**：

```
draft
  │ submit
  ▼
submitted ──request_review──▶ under_review
  │                              │ record_review(拒)
  │                              ▼
  │                          rejected（终态，且是粘的）
  │ record_review(够数)
  ▼
approved ──release──▶ released（终态）
```

| 状态 | 含义 | 还能往前吗 |
| --- | --- | --- |
| `draft` | 刚写出来 | 能 |
| `submitted` | 已提交，等发起评审 | 能 |
| `under_review` | 评审进行中 | 能 |
| `approved` | 评审齐备，可以放行 | 能 |
| `rejected` | 被人拒了 —— **终态**，而且是**粘的** | **不能** |
| `released` | 已放行 —— **终态** | **不能** |

**拒绝是终态，而且是粘的。** 拒过的东西不会因为没人再表态就变成"没人反对"。
**没有明确批准，就等于没有批准。**

**构造出来的变更一律是 `draft`。** 别的状态只能由状态机推出来 —— **凭空造一个
"已放行"的变更，构造时就报错**。

**评审绑在内容摘要上。** 评的是**人当时看到的那一份改动** —— 内容变了，那份评
审就不再是他评的东西了，哪怕变更编号没变、标题没变、还是那场评审。**绑定的是
内容，不是名字。**

**提出人不能评审自己的变更。** 这一条在两处挡：记评审的时候（实体层），和放行
的时候（流程层，对**存储里那份结论**再查一遍）。

## 5. 内容摘要

摘要用**规范化 JSON** 算（字段排序定死、空白定死），再取 SHA-256：

```python
canonical = json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
digest = hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

**摘要覆盖"这次要改什么"** —— 项目、操作、种类、标题、目标、改了什么、风险档、
要几份、要什么资格。**状态、评审记录、时间戳都不在里面**：它们是这份变更**走
过的路**，不是**变更的内容**。

> **为什么不用拼字符串。** 拼字符串时，"字段顺序变了"、"少了一个冒号"都会算出
> 另一个摘要 —— 于是"内容其实没变"会被误判成"内容被改过"，而误判的方向恰好是
> **把好的当成坏的**：放行被无端卡住。规范化 JSON 把顺序与空白都定死。

## 6. 流程层：真正的闸

**领域层的状态机是纵深防御** —— 它让"漏写一步"在代码里就发生不了。但 Python
里的对象是**可以伪造的**：绕过冻结直接改字段，谁都能把状态改成"已放行"。

> **所以流程放行前不信任对象。**
>
> `HighRiskReviewFlow.release` 每次放行都**从评审存储里把结论重新取回来**，再拿
> 它跟变更当前的内容摘要、份数、独立性、**名册**逐项对。**对象说什么不算，存
> 储里那份与名册说了算。**

放行前逐项核对，**对不上就停**：

| 核对 | 对不上时 |
| --- | --- |
| 存储里**一条结论都没有** | 没有评审结论 |
| **有人拒过** | 有人拒过 —— 拒绝是终态 |
| 独立评审**不够数** | 只有几份、要几份 |
| **提出人在评审人里** | 评审人里有提出人自己 |
| 评审绑的**摘要 ≠ 当前摘要** | 评的不是这一版内容 |
| **名册里没人持有要求的资格** | 评审资格不足 —— 批过的人里没有看得懂的那位 |

**实体层的闸还在**：核对过了还要过 `HighRiskChange.release` 的四道校验（状态、
份数、独立性、资格覆盖）。**两层都要过** —— 一层查对象，一层查存储。

**评审结论存在对象之外。** 变更上记着 `review_request_id` —— 流程据此知道去哪
儿取结论。**这不是冗余**：对象上的 `status` 是可以伪造的，**请求号只能指路，
不能替结论**。

## 7. 失败关闭与台账顺序

**审计写在效果之前。** 写不进去，就**不动手**：

```
核对 → 实体层的闸 → 写审计（失败就停） → 执行变更 → 记台账
```

> **为什么审计排在落地前面。** 没留痕的放行比没放行的变更更糟 —— 前者连"它发生
> 过"都答不上来。**先记下来，再做**；记不下来，就别做。
>
> **为什么台账排在执行后面。** 台账记的是"**放行了什么**" —— 写在执行之前，执
> 行失败就会留下一行"放行了"却什么都没发生。**审计才是权威的**（写在执行之前，
> 且失败关闭）；台账只是一份事后好查的索引。

**审计事件带三样凭据**：内容摘要（事后核对的凭据）、变更编号与项目（定位）、动
作与细节（谁批的）。**光有"放行了"三个字，事后什么也核对不了。**

### 8.2 伪造路径是**真的被测过**的

**"标记为高风险的变更 100% 经过独立评审后才可执行"这句话，单靠"代码里没写这
条路"是不够的。** 所以测试里有一类专门的用例：**绕过冻结直接改字段，造出一份
假的**：

```python
clone = object.__new__(type(change))
for field_ in fields(change):
    object.__setattr__(clone, field_.name, getattr(change, field_.name))
object.__setattr__(clone, "status", HighRiskStatus.APPROVED)  # 伪造"已批准"
```

然后把它塞回存储，走完整的放行流程 —— **放行不出去**（`没有评审结论`）。同类
的还有：伪造一份"内容被偷改"的（`这一版内容` 对不上）、在评审人里塞一个提出人
自己（`提出人`）、把存储里的结论删掉一份（`独立评审` 不够数）。

**这些用例是这一层最重要的几条** —— 它们测的正是验收条件里那句话。

### 8.3 真语料回放（T2）

**真库里有 45 条真跑出来的审批记录**（`approval_request` 表），全是从 M1 演示
里合入主干时留下的。**把它们原样送进新的放行闸里跑一遍**：

| 口径 | 条数 |
| --- | --- |
| 语料 | **45** 条审批请求，45 个任务，全是 `merge_to_main` |
| 提出人 | `director` × 45 |
| 表态人 | `lr-approver` × 32、`m1-approver` × 13 |
| **每个任务有几条审批** | **1** × 45 |
| **按现行规矩放行** | **45**（每一次都是 somebody ≠ 提出人） |
| **提出人自己批了自己** | **0** |

三个场景：

| 场景 | 性质 | 变更数 | 放行 | 拦住 | 拦在哪 |
| --- | --- | --- | --- | --- | --- |
| `as-is`（照真语料原样跑） | **实测** | 45 | **0** | **45** | 独立评审份数不够（45） |
| `paired`（补上另一位真实评审人） | 推演 | 45 | **45** | 0 | —— |
| `architecture`（当作架构级改动） | 推演 | 45 | **0** | **45** | 评审资格不足（45） |

**这三行各自回答一件事。**

- **`as-is` 是实测**：照现在这样跑下去，**新闸会把真语料里的 45 次合并全部拦
  住** —— 因为每一次都只有一份评审，而合并是高风险、要两份。**这就是这次治理
  的代价：45 次合并，一次都放不出去。**
- **`paired` 是推演**：把语料里另一位真实评审人补上，**45 次全部放行** —— 证明
  **闸门不是"一律拦住"**。一道只会拦不会放的闸，和没有闸是一回事。
- **`architecture` 是推演**：把每一份都当作架构级改动，**45 次全部因"评审资格
  不足"被拦** —— 证明**资格那一层有牙齿**，不是摆设。

### 8.4 类型与规范

`ruff`（本仓库全套规则，含 `PLR0913`、`PLR2004`、`RUF022`、`ANN`）与 `mypy`
（`disallow_any_explicit`）在这几个新模块上**全绿**：

```bash
.venv/bin/python -m ruff check core/evolution/common.py core/evolution/risk.py \
  core/evolution/proposal.py core/policy/high_risk.py orchestration/high_risk_review.py \
  evaluation/governance/ scripts/run_release_audit.py
.venv/bin/python -m mypy core/evolution/common.py core/evolution/risk.py \
  core/evolution/proposal.py core/policy/high_risk.py orchestration/high_risk_review.py
# Success: no issues found in 5 source files
```

> **为什么这几个模块不用 Pydantic 模型。** 仓库里的 `disallow_any_explicit` 是全
> 局开的，而 Pydantic v2 继承来的 `BaseModel.__init__(**data: Any)` 会让每一个
> Pydantic 模型模块在类定义那一行报 `explicit-any`。绕过去的办法是往
> `pyproject.toml` 的 per-module 豁免清单里加名字 —— 而那份清单本身是**受测试
> 守着的窄门**（`tests/unit/core/test_no_any_escape.py`：清单多一个就红）。
>
> **能不登记就不登记。** 改成冻结数据类 + 显式 `__post_init__` 校验之后，**豁免
> 清单一个字都不用动** —— 校验也是**显式写出来**的，不依赖框架的默认行为。

### 8.5 分层

```
core/evolution/risk.py        （叶子：词汇与下限）
core/evolution/common.py      （叶子：摘要、空串、占位、资格去重）
        ↑
core/evolution/proposal.py    （P4-070 的提案实体）
        ↑
core/policy/high_risk.py      （规矩与实体）
        ↑
orchestration/high_risk_review.py（放行流程 —— 只引 core）
```

**没有环。** `core/policy/` 放领域模型这件事是有先例的（`core/policy/approval.py`
"审批领域模型"，`core/entities/approval.py` 反过来引它）—— 而**把实体放在
`core.policy` 而不是 `core.evolution`，是为了不让 `core.evolution` 反过来依赖
`core.policy`**。

## 9. 没测的，和已知的不足

1. **新闸还没接进真实路径 —— 这是最大的一条。** `apps/director/cycle.py` 的合
   并走的**仍然是旧审批门**（一个人表态就合）。**这一层现在是"另一条路"，不是
   "替换掉旧路"** —— 旧路仍然能放行合并。接进去要动 `apps/director/cycle.py`，
   而那不是这一次的活。**在这条接上之前，"100% 经过独立评审"这句话只在**新闸
   **这条路上成立。**
2. **没有接数据库。** 放行流程的六个端口只有内存版（测试里的与 T2 回放里的）。
   **"真的从数据库里取回评审结论"这件事没有测过。**
3. **名册是假设出来的。** 真语料里**没有"谁有什么资格"这一项** —— 名册是按语
   料里出现过的人**一律**按最松的一档（general）登记的。**这是对新闸最不利的假
   设**：在这个假设下它都拦不住，那才是真的拦不住。
4. **真语料里没有"改动种类"这一项。** 所以"资格那一层"在真数据上答不了这个问
   题 —— 只能推演（`architecture` 场景）。
5. **真语料里没有拒过的、没有过期的。** "拒绝是终态""过期盖不住拒绝"两条在真
   数据上没有被触发，只有单元测试覆盖。
6. **闸拦住之后怎么办，没测。** 谁被通知、怎么补评审、能不能重新发起、驳回之后
   提改动要不要重新走一遍 —— **这一层没有规定**。
7. **执行端口没有真的执行任何东西。** T2 回放里那 45 次"放行"，执行的是一个内
   存执行器；它记了账，没合任何代码。
8. **并发没测。** 两个人同时评一份变更会怎样、评审与改内容同时发生会怎样 ——
   **这一层没有并发控制**，没有乐观锁也没有悲观锁。
9. **摘要是"这次要改什么"的摘要，不是"落地的那份东西"的摘要。** 落地方式变了
   （同一份摘要，换了个实现）而摘要不变 —— 这条路是通的。
