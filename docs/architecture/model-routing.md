# 多模型路由 —— 按任务 / 成本 / 能力挑模型，钱记在项目名下

设计依据：`docs/tasks.md` TASK-P4-020（交付物"按任务 / 成本 / 能力路由模型"；
验收条件"不同模型处理不同决策角色（如 Critic 用更强模型）；**成本归集到项目维
度**"；验证 T1 + T2）、R-018（Budget 管 Token / 模型调用 / 计算资源和时间预算）、
R-076（七种任务类型）、I-13（三处成本必须同源同币种）、`docs/design.md` §3.1
（Budget Manager 管理 Token、模型调用、计算资源和时间预算）、`TASK-P4-010`（项目
作用域与分项目记账）。

> **单模型下，路由是看不见的。**
>
> 一个模型干所有的活时，"该用什么模型"这个问题**不存在** —— 没有第二个选择，
> 就没有做错选择的余地。于是能力差异、成本差异全都被平均掉了：让便宜模型去
> 做架构判断，让强模型去写文档，两头都在花钱，**而没有一个地方会报错**。
>
> 更麻烦的是**路由最危险的失败模式不是选错，而是选不出来时悄悄换一个**。钱
> 照花、能力照降，而日志里什么异常都没有 —— 直到某天发现"这段时间的产出质量
> 掉了"，而谁也说不清为什么。
>
> 所以路由必须**失败关闭**：挑不出来就报错，并把每个候选为什么被排除带出来。

## 0. 一句话

**能力是硬条件，任务给出**有边界的**降级阶梯，成本是硬上限；挑不出模型就报
错，绝不静默回退；账记在 `project:<id>` 这个 scope 上，记账认的是**实际**用量
而不是路由时的估算。**

## 1. 缺口在哪

阶段一已经有六套角色化 Prompt（`TASK-P1-057`），每套 Prompt 自带一个
`ModelSettings` —— 但那个模型名是**写死的默认值**（`claude-sonnet-4-6`）。也就是说：

| 缺什么 | 后果 |
| --- | --- |
| 没有"这个角色要多强的模型"的说法 | Critic 与 Analyst 跑同一个模型 —— **判错的代价差着量级** |
| 没有"这个任务要多强的模型"的说法 | 重构与写文档跑同一个模型 |
| 没有按成本挑的路 | 预算只剩一条硬闸：要么全跑，要么全停 |
| 没有把成本归到项目维度 | 多项目下"这个项目花了多少"答不上来 |

## 2. 三个轴，各管各的

`core/policy/routing.py` 是纯函数：没有数据库、没有 IO、没有配置。它只回答"这活
该谁干"。

| 轴 | 是什么 | 硬还是软 |
| --- | --- | --- |
| 能力 | 这个模型会不会干这活（要读代码？要长上下文？） | **硬** —— 不会就是不会 |
| 任务 | 这活要多强的模型（层级偏好） | **有边界的阶梯** —— 按偏好列表依次试 |
| 成本 | 这次调用最多花多少 | **硬上限** —— 超过就不选它 |

**为什么放在 `core` 而不是 `agents/`。** 路由要按"角色"分档，但 `core` 不认识角
色（角色是 `agents/` 的概念），所以低层用的是"工作负载"这个更一般的说法 ——
角色怎么映射到工作负载，是 `agents/` 的事（`agents/prompts/routing.py`），任务
类型怎么映射，是 `core/task/routing.py` 的事。**依赖方向是单向的**：`agents/` 与
`core/task/` 认识 `core/policy/`，反过来不成立。

**能力是硬的，因为"不会"没有降级空间。** 让一个不能读长上下文的模型去读一个仓
库，它不会报错，它会**编** —— 而编出来的差距清单看起来跟真的没有区别。

**成本是上限，不是目标。** 预算是"不许超过"，不是"尽量少花"。所以同一层级里挑
**最便宜**的，而不是最贵的：层级已经把能力分档了，同档之内再比能力是自欺欺人。

## 3. 降级有边界

**降级的阶梯是"这个活自己给的"。** Critic 允许"首选强模型、退而求其次标准模
型"，但**绝不包括便宜模型**：

| 角色 | 层级偏好 | 能力要求 | 为什么这么分 |
| --- | --- | --- | --- |
| Analyst | 只用便宜档 | 长上下文 | 输出是带证据引用的清单，弱模型够用 |
| Strategist | 标准档 | 推理 | 价值与优先级判断，要推理，不必读代码 |
| Architect | 强档 → 标准档 | 推理 + 代码 | 架构判断错了，重构代价很高 |
| Quality | 标准档 → 便宜档 | 代码 | 质量与测试充分性评估，要读代码 |
| Director | 强档 → 标准档 | 推理 | 最终决策，综合目标、风险、成本与收益 |
| Critic | 强档 → 标准档 | 推理 + 代码 | 独立复核；**退到标准档仍算复核，退到便宜档就不算了** |

**一次没人复核的合并，比一次贵一点的复核更糟。** 所以 Critic 的偏好列表到标准
档为止。项目没钱时它**要么退到标准档，要么不跑** —— 不退到底。

任务类型那一侧同理（`core/task/routing.py`）：重构走强档（**行为保持最难验** ——
改错了测试未必拦得住），写文档走便宜档（要与实现一致，读得懂代码就够）。**"都在
写代码"不等于"难度一样"。**

## 4. 失败关闭

**挑不出来就报错，并把每个候选为什么被排除带出来。** "回退到默认模型"是这类系
统最常见的静默失败：钱照花、能力照降，而日志里什么异常都没有。

拒绝理由**按固定次序给出，只给一条**（不可用 → 缺少能力 → 层级不在偏好列表里 →
超过成本上限）。**只报最先卡住的那一条** —— 一次报四条会让人以为"修好一条就能
用了"，而实际上四条都得满足。

**路由结果是可复现的。** 同样的请求两次给出不同的模型，那"这次为什么用这个模
型"就永远答不上来 —— 而多模型系统里最常见的事故恰恰是"说不清是哪个模型干的"。
排序是**全序**的：先按层级偏好，再按成本，最后按模型标识兜底。

## 5. 成本归集到项目维度

`orchestration/model_dispatch.py` 把三步接成一次调用：

```text
路由（挑模型）→ 计价（算出钱）→ 记账（记到项目名下）
```

**为什么"路由"和"记账"必须在同一个对象里。** 分开的话，中间那个"用了哪个模
型"就只是日志里的一行字 —— 而钱是按**实际 token 用量**算的，不是按"选了哪个模
型"算的。两件事分属两处时，账本上的数字没法反推"是哪个模型花的"。所以这里把三
步接成一次，返回的 `ModelDispatch.cost` **就是账本记下的那一个对象** —— 观测端
拿它去记，三处就同源同币种（I-13）。

**记账的作用域是 `project:<id>`** —— 与 `TASK-P4-010` 的分项目账本同一套口径，
所以**不需要加迁移**（见 §10）。上限取**这个项目还剩多少额度**，而不是某个全局
数字：甲项目有钱就用强模型，乙项目快没钱了就在**它自己允许的档位里**退一档。

**钱花了就是花了。** 账本拒绝超限时不抛异常给调用方，而是记一条"被拒绝"的流水
并把 `recorded` 置假 —— 这次活已经干完了，把它变成失败等于丢掉已经做好的工作，
而重做一遍更贵。该拦的是"下一轮要不要继续"，那件事由预算检查去做。

## 6. 估算与实际

**两个数，各有各的用处。**

| 数 | 从哪来 | 管什么 |
| --- | --- | --- |
| 估算 | 模型画像里的 `cost_per_call` | **路由** —— 还没定用哪个模型时只能拿估算做比较 |
| 实际 | 按实际 token 用量算出来 | **记账** —— 账本记的是真金白银 |

**所以"路由说买得起"不保证这一笔记得进去** —— 估算乐观时，路由过了而账本拒
了。**账本那一下才是底线。**

**为什么路由这一层不扣钱。** 记账算的是实际发生的钱（执行器跑完才知道用了多少
token）；拿估算扣账，账上的数与真实花的钱永远对不上 —— 而"对不上"这件事没人会
去核。所以路由只管"谁干"，钱由执行器跑完后按实际用量上报。

## 7. 接线：路由的结果要落到执行器上

**挑对了却没接线，那整套路由就是一段没人调用的代码** —— 而"没人调用"是那种不
会报错的失败。

`orchestration/loop_a.py` 多了一个可选端口 `ModelResolverPort`：

| 场景 | 行为 |
| --- | --- |
| 没有装路由 | 编排层不给模型 —— **行为与从前完全一样** |
| 装上了路由 | 挑好的模型名进 `SessionConfig.model` |
| 路由挑不出来 | **报错** —— 不悄悄换一个模型跑完 |

**为什么失败时不兜底。** 静默兜底是这类系统最常见的失败方式：跑完了、记了账、
看着一切正常，而"这次根本没过路由"这件事没有任何地方会提。**一次没人路由过
的执行，比一次明确报错的执行危险得多** —— 因为前者不会被看见。

| `tests/unit/agents/prompts/test_role_routing.py` | 20 | **角色到档位的策略**，以及**降级的边界**（Critic 与 Architect 不退到便宜档） |
| `tests/unit/orchestration/test_model_dispatch.py` | 25 | **钱记到项目名下**、按选中的模型计价、上限来自项目余额、估算乐观时账本兜底 |
| `tests/unit/orchestration/test_model_routing_wiring.py` | 7 | **路由的结果落到了 `SessionConfig` 上**，且失败时不兜底 |

### 8.2 真实数据库层（T2，13 条）

`tests/integration/test_model_routing.py` —— 真 PostgreSQL，两个项目**并行**发
起调用（`asyncio.gather`）。

**账在项目名下（6 条）**：账户行的 scope 是 `project:<id>`；两个项目各占一行；流水
的 scope 不跨项目；**模型调用次数也归到项目名下**；金额是**选中的那个模型**的价
（强档 60 / 标准档 15）；挑不出模型时**一笔都不花**（账户表零行）。

**模型按项目选（5 条）**：有钱的项目走强档；快没钱的退到标准档（`downgraded_from`
是强档）；**退不到便宜档就不跑**；两个项目拿到的是**不同的模型**；有钱的项目里
Analyst 仍然走便宜档（档位是角色定的，不是钱定的）。

**并发（2 条）**：两个项目同时跑，账仍分开；**同一个项目的两笔并发扣减总和不超
限**（额度 15 只够一次标准档调用时，至多一笔记下，另一笔要么在路由前发现没额
度、要么被账本拒下）。

## 9. 没测的，和已知的不足

1. **没有真的调过模型。** 这里的"模型"是画像里的三档与一张单价表，**不是真的
   LLM**。真接上之后，"估算与实际的差"要从真账单里量 —— 现在这个差是构造出来
   的。
2. **单价表与模型画像是两份数据，没有绑在一起。** `ModelProfile.cost_per_call`
   与 `RateTable.model_rates` 说的可能是两个价，而**没有任何一处会检查它们是否
   一致**。今天的夹具里它们相等，**那是被构造出来的相等，不是被保证的相等**。
3. **`budget_entry` 表里没有"哪个模型"这一列。** 所以"这笔钱是哪个模型花的"在
   库里**只能靠金额反推**（金额对得上哪个档位）。要按模型出报表就得加一列 ——
   而这一版不碰 schema（见 §10）。
4. **路由结果没有被写进执行轨迹。** `SessionConfig.model` 带进了执行器，但轨迹
   事件里没有"这次选了哪个模型、为什么"。要复盘"这次为什么用便宜模型"，现在
   只能靠重跑路由。
5. **降级只在"这个角色允许的档位"里发生，没有跨角色的兜底。** 一个项目穷到连
   标准档都跑不起时，Critic 不跑 —— 这是有意的，但意味着**这种项目会卡住**，而
   "卡住"这件事目前没有单独的信号。
6. **没有测"路由与执行器报价不一致"。** 执行器报上来的实际花费与路由时的估算不
   一致时（真实世界里这是常态），这条差额目前**没有对账口径** —— 它会直接体现
   为"账上的数比估算高"，而没人知道那高出来的是正常的还是异常的。
7. **能力集是自由文本。** `"code"` / `"reasoning"` / `"long_context"` 这几个名字
   没有中心定义 —— 两个模块各写各的，写错一个字母就**静默地少一条要求**（多会
   一点没关系，少会一点才是问题，而少的那条不会被发现）。

## 10. 为什么没加迁移

这一版**没有动 schema**。成本归集用的是 `budget_account.scope` 与
`budget_entry.scope` —— 两张表**早就有**这一列，而且是自由文本列（不是项目外
键）。项目维度**骑在现成的列上**：`scope` 用 `project:<id>` 这个带前缀的键，与
"全局"这类别的口径区分得开，且能解析回来。

**没有加 Alembic 迁移是有意的。** 阶段四还有 0010、0011……要加，而同一时刻另一
个工作树也在改这个仓库 —— 两边各加一个 head，`alembic upgrade head` 就会对谁都
失效。所以这一版**先不碰 schema**。

**代价要说清楚**：账本里没有"哪个模型"这一列（§9 第 3 条），按模型出报表只能
靠金额反推。
