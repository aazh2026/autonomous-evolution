# 二维能力矩阵 —— 执行器 × 模型，按实测选型

设计依据：`docs/tasks.md` TASK-P4-030（交付物"执行器 × 模型的二维能力矩阵"；验收
条件"**能力矩阵由实测数据得出，且能指导自动选型**"；验证 T2）、R-111（阶段二验收：
结果可比较可评估）、I-17（多执行器结果可比性口径需前置设计）、`TASK-P2-018`（一维
的执行器横向评测 —— 本篇是它的二维版本）、`TASK-P4-020`（多模型路由 —— 路由按
"这个角色要多强的模型"挑，能力矩阵按"实测下来这个组合有多强"给证据）、R-039
（成本同源同币种）。

> **一维评测会让人以为"执行器好"与"模型好"是两件可以分开谈的事。**
>
> 于是"最好的执行器 + 最好的模型"成了默认做法 —— 但那**从来没有人测过**。某个
> 执行器配上某个模型可能根本没跑过；而另一些组合之间可能有明显的交互（同一个
> 模型在 A 执行器上要 10 轮才做对，在 B 上 3 轮就够）。
>
> **边际（一维平均）会把这两种情况都抹平。** 交互存在时，边际最好 ≠ 格子最好 ——
> 按边际选，选出的是一个没测过的组合；交互不存在时，边际与格子一致 —— 那就明说
> "可以分开选"，不必假装矩阵给了新的信息。
>
> 更要紧的是**选型的失败方式不是选错，是选不出来时悄悄换一个**。钱照花、能力
> 照降，而日志里什么异常都没有。所以这里**失败关闭**：没证据就不跑。

## 0. 一句话

**矩阵按（执行器 × 模型）切片，格子里的数**全部实测**；统计上分不开的格子归同一
"能力档"，档内按成本排；选型**一个对象同时回答"用哪个执行器"与"用哪个模型"**，
两个答案**必须来自同一格**；挑不出来就报错，绝不静默回退。**

## 1. 缺口在哪

`TASK-P2-018` 的一维评测答的是"哪个执行器更强"。它有三个答不了的问题：

| 缺什么 | 后果 |
| --- | --- |
| 没有"这个模型在这个执行器上有多强" | 选出来的组合**可能根本没跑过** |
| 没有"执行器与模型能不能分开选"的结论 | 按边际选时，选的是一个**没测过的格子** |
| 没有把分不开的格子归一档 | 一次运行的差别就被当成差别，**下一轮就不成立** |

第三行是最隐蔽的：两个格子成功率差一次运行，是噪声，不是能据此排序的差别。
**拿噪声当差别，选出来的组合在下一轮就不成立了** —— 而矩阵是用来指导自动选型的，
指导错了比没有更糟。

## 2. 一格长什么样

`core/policy/capability.py` 是纯数据与纯函数：不碰数据库、不碰 IO、不认识执行器
适配器，也**不认识统计检验**（谁与谁分得开是评测层算出来的结论，作为**数据**带进
来）。

一格 = 一个（执行器 × 模型）组合：

| 字段 | 是什么 | 没有实测值时 |
| --- | --- | --- |
| `runs` | 该跑几次 | 0 |
| `executed` | 其中真跑起来几次 | 0 |
| `succeeded` | 其中通过验收几次 | 0 |
| `measured_runs` / `regressed` | 验过回归套件的次数 / 引入回归的次数 | 0 |
| `cost_median` | 成本中位数（**统一价目表折算**） | `None` |
| `duration_median` | 耗时中位数（我们量的墙钟时间） | `None` |
| `tokens_median` | token 用量中位数 | `None` |
| `capability_group` | 能力档 —— 统计上分不开的格子共用一个档 | `""`（"没比过"） |

**三态，不是两态。** "没测出来"与"是 0"必须长得不一样：

- **可用率** = 跑成了几次 / 该跑几次 —— 归因上，"跑不起来"是**环境**问题；
- **成功率** = 做对了几次 / **跑成了**几次 —— "跑不成"不进分母，把环境问题说成
  能力问题；
- **做对率**（`overall_rate`）= 做对了几次 / **该跑**几次 —— **选型真正看的数**。

第三行是选型的口径：一个"三次里跑起来两次、做对两次"的格子，比一个"跑起来十次、
做对六次"的格子**更值得选**。

**没有实测值的格子一律不进候选** —— 不是"排在最后"。把它排在最后等于让一个没测过
的组合跟测过的组合比，那不是选型，是抽签。

## 3. 口径不许两套

`evaluation/agents/capability_matrix.py` 切片时**直接复用**一维评测的
`evaluate_executor` —— 同一套可用率 / 成功率 / 回归率 / 成本 / token / 耗时的算法。

**两套口径的两张表没法比。** 一维那张表是本仓库里唯一一份"执行器跑得怎么样"的
数据，二维矩阵如果另起一套算法，那两张表就会各说各话 —— 而看板上不会有人发现。

**成本按统一价目表折算，不拿各家自报的数比。** 各家 CLI 自报的成本是按各自的计
价表算的，同一个模型同一个调用能差十几倍，拿自报成本互相比，**比的是记账口径**。
价目表来自 models.dev 的 `minimax` 条目（取值日期见 §11），**没有给价目表的格子就
没有成本这一列** —— 宁可空着。

## 4. 分不开的格子归一档

**怎么算"分不开"。** Fisher 精确检验（比较两格的"该跑几次里做对几次"），再对
**全部两两比较**做 Holm 校正 —— 多比几对，证据就得更硬。

**校正之后还显著的才算"分得开"。** 分不开的归成同一档，档内按**成本**排（既然做
对的程度分不出高下，那就选便宜的），再按耗时排。

**聚类用贪心的"完全连接"。** 按做对率从高到低排，每一格跟它已经落进的档比：跟档里
**每一格**都分不开，才并进那一档。

> **为什么不按"连通的就算一档"。**
>
> 连通聚类会串：A 与 B 分不开、B 与 C 分不开，就把 A 与 C 也归成一档 —— 而 A 与 C
> **可能分得开**，那一档就成了一句错话。

**没比过的格子各自成一档。** 空档的意思是"没比过"，不是"和别人一样" —— 把它们归
进同一档等于替它们下了一个没做过的结论。

## 5. 交互项：能不能把执行器与模型分开选

矩阵的结论不是"谁更好"，而是"**能不能分开选**"。

**零假设**：在每个执行器内部，模型标签是可交换的（也就是"没有交互"）。
**统计量**：各执行器上"模型 A 减模型 B"这个差额的**方差** —— 差得越不齐，交互越
强。

**为什么用置换检验。** 样本很小（每格几十次运行），而且"做对率"在边界附近并不服
从正态分布。置换检验只问一个换问题：**如果其实没有交互，观测到的这个参差程度有
多罕见？** 它对分布形状不作任何假设。**样本够小就精确枚举，够大就蒙特卡洛** ——
方法名会写明是哪一种（蒙特卡洛带 +1 修正，**不该报出 p=0** —— 那是"没抽到"，不是
"不可能"）。

## 6. 接线：一次选型，两个端口

`orchestration/capability_resolver.py` 的 `MatrixCapabilitySelection` **一个对象实现
两个端口**：

| 端口 | 问什么 | 答什么 |
| --- | --- | --- |
| `AgentSelectorPort.select(state, candidates)` | 用哪个执行器 | 那一格的 `executor` |
| `ModelResolverPort.resolve(project_id, task_type)` | 用哪个模型 | **同一格**的 `model` |

**为什么必须是一个对象。** 分开问两次，就会选出两个互相矛盾的组合 —— 矩阵里最强的
那格是"claude-code × 某个模型"，按执行器选挑出 claude-code、按模型选挑出另一个模
型，凑起来的组合**根本没测过**。这不是"更精细的选型"，这是**把矩阵最想防的事又
做了一遍**。

**决定被记住，返修那一轮不重选。** 同一个组合从头跑到尾 —— 中途换模型，前半轮的
实测结论对后半轮就不作数了。

**任务类型取自 `state.plan.task_type`，不是 `state.task_type`。** 规划器写的是
`state.plan`，而状态上那个 `task_type` 字段**没人写** —— 它停在默认值 `FEATURE`。
用错了这里，`select` 记的键与 `resolve` 问的键就对不上，于是"执行器选了、模型挑
不出来"。

**成本上限来自项目余额，不写死。** 上限是一个按 (项目, 任务类型) 给的函数 ——
甲项目有钱可以用贵的那格，乙项目快没钱了只能在它自己允许的档位里退一档。上限是
**硬闸**：宁可这次不跑，也不要花掉不属于这个项目的钱。

## 7. 失败关闭

| 场景 | 行为 |
| --- | --- |
| 矩阵里没有候选执行器的格子 | **报错** —— 不退回"随便挑一个" |
| 格子没有实测值 | **不进候选** —— 不当"成功率 0" |
| 格子一次都没跑起来 | **不进候选** |
| 成本没测出来而设了上限 | **不进候选** —— 不知道多少钱，就没法说它没超 |
| `resolve` 时缓存里没有决定 | **报错** —— 说明顺序不对，不猜一个模型顶上 |
| 没有计划 | **报错** —— 选了执行器也没有配套模型 |

**排除必须带理由。** 只说"没选它"，事后没人知道是它不行、是它没测过，还是它压根
不在候选里 —— 而这三件事的处置完全不同。`SelectionOutcome.rejected` 逐格记下理
由。

## 9. 没测的，和已知的不足

1. **矩阵只有一个后端。** 实测跑的是 MiniMax（`MiniMax-M3` 与
   `MiniMax-M3.1-Flash`）—— **跨厂商的交互项没测过**。而交互恰恰是最可能在跨厂商
   时出现的东西（不同的工具调用协议、不同的上下文窗口用法）。
2. **任务集很小。** 9 个试点任务，够看出执行器之间的差别，**不够看出"这个任务类
   型该用哪个组合"**。要按任务类型分档选型，样本还差得远。
3. **同一天、同一台机器、同一批账号。** 耗时中位数里混着网络抖动与后端负载；耗时
   只在**同一次运行**内可比，跨机器不可比。
4. **成本是折算出来的，不是账单。** 统一价目表 × 各家自报的 token —— 比自报金额可
   比，但**折算口径与厂商账单未必一致**（缓存写的计价各家不同，本仓库按输入价
   计，偏保守）。
5. **没跑成与做不对的区分靠的是记录，不是根因。** `NOT_RUN` 只说明"没跑起来"，不
   区分"环境没配好"与"模型跑崩了"。
6. **交互检验的统计量是"各执行器上模型差额的方差"。** 它对"两个执行器的样本量差很
   多"这件事**不稳健** —— 样本少的那一层的估计噪声更大，而方差恰恰对噪声敏感。
7. **能力档是贪心完全链接聚类。** 簇的形状依赖排序，**不是唯一的** —— 换个排序可能
   得到不同的分档。档的**成员关系**是稳定的（那由显著性决定），档的**边界**不是。
8. **一次只测一个组合。** 矩阵里的格子**彼此独立**，没有交叉验证 —— 某个组合运气
   好连赢三把，会把整行都抬高。

## 11. 复现

```bash
# 纯函数层（78 条）
.venv/bin/python -m pytest tests/unit/policy/test_capability.py -q
.venv/bin/python -m pytest tests/unit/evaluation/test_capability_matrix.py -q
.venv/bin/python -m pytest tests/unit/orchestration/test_capability_resolver.py -q

# 真实运行层：跑一遍二维评测（约 9 小时，串行）
.venv/bin/python -m scripts.run_capability_matrix \
  --attempts 3 --timeout 600 --workers 1 \
  --log docs/evaluation/capability-matrix-runs.jsonl \
  --board docs/evaluation/capability-matrix-board.md \
  --matrix docs/evaluation/capability-matrix.json

# 只重画看板（不重跑）
.venv/bin/python -m scripts.run_capability_matrix --render-only \
  --log docs/evaluation/capability-matrix-runs.jsonl \
  --board docs/evaluation/capability-matrix-board.md \
  --matrix docs/evaluation/capability-matrix.json
```

**为什么必须串行（`--workers 1`）。** 实测：在**同一个后端账号**上同时跑两个会话，
会撞上 `429 "已达到 Token Plan 用量上限"`。那不是请求并发限制，是**token 吞吐限
制** —— 两次并发的直连 API 调用都成功，而一次 claude-code 运行要烧掉约 75 万
token。串行跑才能让耗时与一维基线可比。

**价目表**（`scripts/run_capability_matrix.py` 的 `PRICE_TABLES`）取自 models.dev 的
`minimax` 条目，2026-11-10 取值：

| 模型 | 输入 / 百万 | 输出 / 百万 | 缓存读 / 百万 | 缓存写 / 百万 |
| --- | --- | --- | --- | --- |
| `MiniMax-M3` | 0.30 | 1.20 | 0.06 | 0.30 |
| `MiniMax-M3.1-Flash` | 0.15 | 0.60 | 0.015 | 0.15 |

**没标价的模型不是免费** —— 价目表里没有的模型，成本列记的是**未知**，不是 0。
