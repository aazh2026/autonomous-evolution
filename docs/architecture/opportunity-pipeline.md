# 演进机会发现流水线 —— 六路观察接上，一批候选

设计依据：`docs/tasks.md` TASK-P3-013（交付物：Observe 层六类数据源接入 +
Discover 层；验收条件"六类数据源各接入 ≥1 个真实来源；候选的 evidence 指向
真实可解析的证据"；验证 T1）、R-028（Observe 覆盖六类数据源）、R-024（五类
演进机会分类法）、R-029（证据必须可独立核验）、R-030（Candidate ≠ Task）、
`docs/design.md` §3（第一层项目状态观察的六类数据来源；第二层演进机会发现）。

> **观察层早就在设计文档里了，但只有一份名单。**
>
> `design.md` §3 写着"Git Commit、PR、代码变更；单元测试、集成测试、E2E
> 测试；静态代码分析、依赖漏洞、代码复杂度；运行时性能、日志、异常和业务
> 指标；产品需求、Issue、用户反馈；技术文档、架构决策和设计规范" —— 六条，
> 一条不多。**但那是一份清单，不是一次观察。**
>
> **"覆盖六类数据源"这句话要有底，底是六个真的来源。** 不是六条枚举值，
> 不是六个接口 —— 是六个真的东西：真的 git 历史、真的跑一遍 pytest、真的
> 扫一遍依赖图、真的跑一条命令、人写的台账、真的决策记录。

## 0. 一句话

**六路各读各的真的东西，读成一份快照；快照里的每一条事实都带着证据；证据
当场核不上，那条事实就不变成候选。** 前半句是"看得见"，后半句是"看得见
的才算数"—— 缺了任何一个，"发现机会"都只是把观察换个名字。

## 1. 两层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 契约 | `core/evolution/observe.py` | 一条观察长什么样、哪类观察能带哪种证据 | 不知道观察从哪来 |
| 契约 | `core/evolution/opportunity.py` | 证据核验的口子与"观察到 → 候选"的规则表 | 不知道证据长什么样 |
| 编排 | `orchestration/observe.py` | 六路各读各的，拼成一份快照 | 不知道 git 长什么样 |
| 编排 | `orchestration/discover.py` | 逐条核验证据，翻译成候选 | 不知道证据在不在 |
| 观察 | `apps/observe/sources.py` | 六路各读真的东西 | 不决定要不要开轮 |
| 观察 | `apps/observe/resolvers.py` | 拿证据引用去仓库里找 | 不解释找到的东西 |
| 接线 | `apps/observe/pipeline.py` | 把六路接成一条流水线 | 不做判断 |
| 读法 | `apps/readers.py` | 起子进程、解析文本格式 —— **只此一处** | 不解释 |

**契约层在 `core/`，它连"git"和"pytest"这两个词都不出现。** 它只回答两个问
题：**这件事属于哪一类观察？它能带哪种证据？** 一个生产者把"用例没过"标成
"代码改动"，契约层必须报错 —— 因为那时候下游看到的是"某个文件改得频繁"，
而实际上它是一条没过的用例，**事后没人能查出真相**。

**编排层有两条，各管一件事。** `Observer` 只负责"六路读成一份快照"，
`OpportunityDiscoverer` 只负责"逐条核验、翻译成候选"。**它们不合并** ——
因为"看到了什么"与"由此推出了什么"是两种记录，混成一种就分不清"什么都没
看到"与"看到了一堆但全被否了"。后者是需要有人去看的。

**观察层在 `apps/`，它只说"现在什么样"。** 那一堆 `Source` 类就是六路真源。

**读法只有一处**（`apps/readers.py`）。触发层（P3-011）与观察层读的是同一个
世界的六个角落 —— git 历史、测试结果、跑一条命令、人写的台账、决策记录。
**读法一样就该有一处读法**：各写各的，迟早有一处改了另一处没改，于是"git
log 的输出长什么样"在系统里有两个答案，而触发源与观察源给出的提交列表对不
上，**没有人会发现**。

## 2. 六类观察，各有各的落点

| 观察类别 | 读的是真的什么 | 证据落在哪 | 变成哪一类候选 |
| --- | --- | --- | --- |
| `changes` 代码变更 | `git log --name-only`（最近 20 次提交） | 那个文件本身 | 工程实现 |
| `tests` 测试 | **真的跑一遍 pytest** | 那个用例所在的文件 | 质量 |
| `static` 静态分析 | 真的扫一遍仓库的依赖图 | 那个模块所在的文件 | 架构 |
| `runtime` 运行时 | **真的跑一条命令** | 那条命令看的文件 | 工程实现 |
| `feedback` 产品反馈 | 人写的报告台账 | 台账文件 + 问题单号 | 产品 |
| `docs` 技术文档 | 知识库里的决策记录 | 那篇记录本身 | **不产出候选** |

**每一路都必须能落一个证据。** 这是 R-028 与 R-029 的硬要求，也是这一层最
容易踩空的地方：运行那一路的探针如果没说是看哪个文件的，就产生不了观察 ——
一条"命令崩了"的观察没有落点，就只是一句话。所以 `RuntimeProbe` 把
`evidence_path` 写进了自己的字段里，而不是让人在事后补。

**六类里只有五类变成候选。** 决策记录写的是当初已经做过的决定，不是待办 ——
**把它变成候选，等于把"我们当初决定这么办"读成"我们该改一改"**。这一类仍然
要被读到（"六类数据源各接入 ≥1 个真实来源"是验收条件），但产出的那一条会
被丢掉，**并且留下丢掉的理由**。

**技术类候选不在这一侧。** 五类演进机会里有一类是"技术"（R-024），但技术候
选要的是**趋势**与**收益论证**（R-025）—— 观察给不出趋势。趋势与论证是
P1-052 那套 `TechnologyTrend` / `ProjectBenefit` 的事，那一层自己去看世界。
**这里不假装自己接了它。**

**一个环只报一次。** 违规清单里也有循环依赖那一类，但静态分析那一路跳过它
—— 否则同一个环会被报两遍（"a 依赖了 b" 与 "a 与 b 兜圈子"），**两遍就是两
批候选，候选 id 还会撞车**。环那一遍说得更全（把环上所有的模块都列出来），
所以留它。

## 3. 三态：读到了、空、失败

本仓库的老规矩：**缺实测值是失败，不是 0。**

快照里每一类观察源有一行状态，三种取值：

| 状态 | 意思 | 例子 |
| --- | --- | --- |
| `observed` | 读到了，而且有东西 | 9 条用例真的没过 |
| `empty` | 读到了，确实没有 | 仓库里没有依赖环 |
| `failed` | 压根没读成 | pytest 退出码 2、起不来的子进程 |

**"读到了没有东西"与"压根没读成"必须分开。** 一个跑不起来的测试套件看起来
和一个全绿的套件一模一样 —— 把它当成后者，就等于报了一句假结论。**假结论
没人会去查。**

**一路坏了，其余五路照跑。** 观察编排器把每一路单独包起来：读不成的这一路
记成 `failed` 并把异常类型与消息留在细节里，其余路照常产出观察。**整体崩掉
比"这一路坏了"有用得多** —— 后者能让人去修那一路，前者只能让人重跑。

**同类多路合成一行。** 同一类接了多个来源时（比如两个测试套件），快照里仍然
只有一行：**有一个读到了就是读到了**，但坏掉那路的细节要留着，不能藏。

## 4. 证据关口

**候选的 evidence 指向真实可解析的证据** —— 这句验收条件落在两个地方。

**第一处：观察与候选都得有证据。** 观察的契约层直接拒绝没有证据的观察（抛
`ObservationContractError`），拒绝证据种类对不上的观察（"代码改动"不许带问
题单编号）。**候选那一层复用 P1-051 的 `EvolutionCandidate`**，它的
`evidence` 同样必填。

**第二处：证据要当场核一遍。** 发现层拿着每一条证据引用去问核验器，核验器回
三态：

| 核验结果 | 意思 | 候选 |
| --- | --- | --- |
| `resolved` | 找到了 | 留下 |
| `missing` | 找过了，不在 | **丢掉**（"证据指错了地方"） |
| `unavailable` | 查不了 | **丢掉**（"这一条流水线只产出当场核验过的候选"） |

**`missing` 与 `unavailable` 都丢掉，但理由不同** —— 前者要改的是引用，后者
要补的是核验手段（接产物存储、接 CI 报告）。**理由不同，补救动作就不同。**

**"查不了"不等于"不在"。** 本机没有产物存储，所以 `artifact://` 与
`test_report://` 这两种证据一律 `unavailable` —— 不是"那个产物不存在"，是
"这儿没法查"。**把它们混成 `missing`，就会有人去删一个其实好好的产物。**

**候选 id 由主体生成**（`opp-<类别>-<主体的 slug>`），**撞车的后一条被丢掉**
并留痕。撞车说明两条观察说的是同一个主体 —— 那是上游的重复，不是这一层该
悄悄合并的事。

## 5. 实测：T1

**验收条件一：六类数据源各接入 ≥1 个真实来源。**

验收测试里造了一个**真的仓库**：真的 `git init`、真的四次提交（一个文件被改
了 4 次）、真的 pytest 项目（一条 `xfail(strict=True)` 的复现用例 + 一条过的
用例）、真的依赖环（`pkg.a` ↔ `pkg.b`）、真的分层违规（`pkg.importer` 导入
`tests.helpers`）、真的会崩的命令、真的台账、真的决策记录。

| 观察类别 | 观察到几条 | 证据落在哪 |
| --- | --- | --- |
| `changes` | **1** | `src/pkg/hot.py` |
| `tests` | **1** | `known_issues/test_known.py` |
| `static` | **2**（1 违规 + 1 环） | 导入方 / 环上第一个模块 |
| `runtime` | **1** | `src/pkg/a.py` |
| `feedback` | **2** | `PILOT-001`、`PILOT-002` + `docs/issues.md` |
| `docs` | **1** | `docs/adr/0001-first.md` |
| 合计 | **8** | |

**验收条件二：候选的 evidence 指向真实可解析的证据。**

| 指标 | 值 |
| --- | --- |
| 观察 | **8** 条 |
| 候选 | **7** 条 |
| 丢掉 | **1** 条（那条决策记录） |
| 候选的证据重新核验 | **7/7 全部 `resolved`** |
| 覆盖的候选分类 | 架构 / 工程实现 / 质量 / 产品（**技术类不在这一侧**） |

**"重新核一遍"是这一条验收条件的验法。** 不是"证据字段非空"，不是"证据长得
像个路径" —— 是**拿核验器把每一条证据再查一遍，要求全部 `resolved`**。一个指
向不存在文件的引用，在核验的时候就露馅。

**断言写的是"六类全在"，不是"至少一类"。** 后者会被"只有一路接上了"蒙过去
—— 那是个把整件事做了一半的实现，一样能通过"至少一类"。

**观察 8 条 → 候选 7 条 → 丢掉 1 条**，那个 1 是决策记录。**丢掉也要留痕**
（`DroppedOpportunity` 带 `reason`）—— 不留痕的话，读的人分不清"判断为不适
用"与"压根没看见"，而这两种情况的补救动作完全相反。

### 5.1 同一个流水线跑在试点仓库上

`samples/pilot_repo`（一个**刻意做小**的试点仓库）上的实测：

| 观察类别 | 观察条数 | 状态 | 候选 |
| --- | --- | --- | --- |
| `changes` | **0** | `empty` | — |
| `tests` | **9** | `observed` | 9 条质量 |
| `static` | **0** | `empty` | — |
| `runtime` | **1** | `observed` | 1 条工程实现 |
| `feedback` | **20** | `observed` | 20 条产品 |
| `docs` | **0** | `empty` | — |
| 合计 | **30** | | **30 条候选，0 条丢掉** |

**那 9 条是 `xfail(strict=True)` 的复现用例** —— 默认跑起来是"预期中的失
败"，**不算质量问题**。所以测试那一路默认带 `--runxfail`：**"这些毛病还在
吗"要按真失败来跑。** 不带这个开关，那 9 条会一条都不报 —— 而那正是最该报
的东西。

**那 1 条运行观察是真的崩。** 探针跑 `python -m tinylib.cli stats ""`，退出
码 1，异常是 `ValueError: 空序列没有平均值`。

**那 20 条是台账里的 20 条，一条不少。**

**三路是空的，原因各不相同，而且都不该被藏起来：**

- `changes` 空，是因为**最近 20 次提交里没有哪个文件被改过两次以上**（阈值
  是仓库默认值 2，不是实测值）—— 试点仓库最近没怎么动。
- `static` 空，是因为试点仓库**没有分层违规也没有依赖环** —— 不是没接。
- `docs` 空，是因为**试点仓库没有 `docs/adr/` 目录** —— 这一路接的是决策记
  录，试点仓库里那种东西写在 `docs/issues.md` 里。

**"空"与"没接"长得几乎一样 —— 所以状态是显式的三态，不是"看有没有产出"。**

### 5.2 每一路多慢（本机）

| 一路 | 耗时 | 说明 |
| --- | --- | --- |
| 代码变更（`git log` 20 次） | 20.0 ms | 起子进程 |
| 测试（真跑一遍 pytest） | **377.1 ms** | 起子进程，跑 43 + 9 条用例 |
| 静态分析（扫一遍依赖图） | 0.1 ms | 读索引 |
| 运行时（真跑一次 CLI） | 31.9 ms | 起子进程 |
| 产品反馈（读台账） | 0.3 ms | 读一个文件 |
| 技术文档（读 ADR 目录） | 0.0 ms | 目录不存在 |

整条流水线在试点仓库上跑一遍 **1370.1 ms**（含建索引）。

**测试那一路慢了三个数量级 —— 所以它不能待在请求路径上。** 它得在后台跑，
或者挂在 CI 上；这也是为什么它默认带一个 120 秒的超时上限。

## 6. 没测的，和已知的不足

**没测的：**

- **没有接上真正的调度器。** 六路源都在，但"谁在什么时候调用 `observe()`"
  这一段没做 —— 那属于阶段三的编排（TASK-P3-010 Temporal，依赖未装）。
- **没有落库。** 快照与候选都只在内存里，返回给调用方就散了。真正跑起来的
  时候要落库，与周期记录放在一起。
- **没有真实项目的基线。** 上面那些数字全部来自 `samples/pilot_repo` 与一
  个测试里造的仓库 —— 那是一个**刻意做小**的试点仓库。真实仓库上六路的产
  出比例是多少（提交多的仓库和文档多的仓库完全不是一回事）**没测过**。
- **没有测并发。** 同一个项目同时跑两条流水线会怎样，没测过。
- **没有测规模。** 一万个文件、两万个提交、十万条台账条目时，六路各多久、
  各自产出多少，**没测过**。

**已知的不足（不是设计，是缺口）：**

- **改动频率的阈值是拍的。** `CHURN_WINDOW = 20`（看最近多少次提交）与
  `CHURN_THRESHOLD = 2`（改过几次算反复）都是**仓库默认值，不是实测值**。
  真实的阈值要看项目的提交历史分布，而那个分布本仓库没测过。
- **静态分析只接了依赖图。** 设计文档里那一类写的是"静态代码分析、依赖漏
  洞、代码复杂度" —— **依赖漏洞扫描与复杂度度量都没接**。这一层不假装自己
  接了它。
- **运行那一路只报事故，不报性能。** 设计文档里那一类还写着"运行时性能、
  日志、异常和业务指标" —— 性能观测要**基线与阈值**，那是另一件事。这里只
  报"崩了、挂住了、起不来"。
- **没有产物存储，所以 `artifact://` 一律核不了。** 测试报告类的证据要接上
  CI 的产物存储才谈得上"可独立核验"。**目前这类候选一律被丢掉**（理由是
  "查不了"），不会假装自己核过了。
- **落不了证据的文件名，这一路看不到。** 证据词表（P1-051）只收带分隔符、
  点开头或带扩展名的路径 —— `Makefile`、`LICENSE` 这种名字**与一句自然语
  言描述分不开**，所以不收。**代价说清楚**：这一路因此看不到根目录下的这
  些文件。**跳过了几个要写在观察的细节里**，不然读的人分不清"没有热点"与
  "有热点但说不出证据"。
- **台账格式是定死的**（`### <编号> —— <标题>`）。人写的格式一旦变了，这一
  路就会安静地什么都不产出 —— 而"什么都没产出"跟"没有反馈"长得很像。
- **`confidence` 与 `risk` 是规则表里的默认值，不是量出来的。** 九条规则里
  的置信度（0.60 / 0.70 / 0.80 / 0.90）与风险档是**写死的仓库默认值**。真正
  的置信度要用实际收益校准（R-033），那是 TASK-P3-014 的事。
- **候选还没有优先级。** 这里产出的候选是**平铺**的，谁先做谁后做没有答
  案 —— 排序是 P1-053 与 P3-014 的事。

## 7. 与设计要求的关系

| 要求 | 落在哪 |
| --- | --- |
| R-028 Observe 覆盖六类数据源 | `apps/observe/sources.py`：六路源各读各的真的东西；验收测试断言六类全有观察 |
| R-024 五类演进机会分类法 | `core/evolution/opportunity.py` 的规则表：五类候选，四类由观察产出，技术类不在这一侧 |
| R-029 证据必须可独立核验 | `apps/observe/resolvers.py`：每条证据当场核一遍，三态分得开；核不上的候选丢掉 |
