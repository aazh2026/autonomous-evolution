# 跨周期趋势看板 —— 四层指标在时间上的曲线

设计依据：`docs/tasks.md` TASK-P3-017（交付物"跨周期趋势看板（达成度、质量、
成本）"；验收条件"能导出 ≥7 天连续运行的四层指标趋势"；验证 T2）、`docs/design.md`
§10（四级指标体系）、§12（可验证的改善）、R-117（不得用任务数 / Token 数 / 提交量作
核心指标）、R-118（四级指标体系）、R-039 / I-13（成本同源同币种）。

> **单轮的指标回答不了"系统是不是在变好"。**
>
> `task_success_rate` 是 0.9 —— 这是**哪一天**的 0.9？上个月也是 0.9 吗？三个月
> 前是 0.5 吗？**一个不带时间的指标，只能说明"此刻是什么"，说明不了"在往哪儿
> 走"。**
>
> 更麻烦的是：**画曲线这件事本身会改变被画的东西。** R-117 禁的那三个量（任务
> 数 / Token 数 / 提交量）恰恰是最容易画成曲线的三个量 —— 一个漂亮的上升曲线
> 长得就像成绩。**所以看板的难点不在画，在拒绝画错的东西。**

## 0. 一句话

**指标层只算纯函数；数据层只取行；编排层只接线。窗口的每一天都必须有一个点，
哪怕那天什么都没发生；算不出来的时候报"算不出来"，绝不报 0。**

## 1. 三层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 指标 | `evaluation/trend.py` | 把原料算成逐日曲线 | 不碰数据库 |
| 数据 | `infrastructure/database/trend.py` | 从库里取出算指标要的那些行 | 不知道什么叫"有效发现率" |
| 编排 | `orchestration/dashboard.py` | 取数 → 算指标 → 导出 | 不碰指标口径 |

**"指标层不碰数据库"是这一层的地基。** 指标是纯函数，所以给它一组已知原料，
它每次给出同样的看板 —— 于是"第 D 天的点怎么算"能被单独证伪
（`tests/unit/evaluation/test_trend.py`，35 条）。而数据层与编排层各自的事也
能被单独测。

**三层之间只通过数据形状说话。** 数据层给的是 `CycleSample` / `VerificationSample`
/ `CostSample`；编排层拿一个 `TrendSource` 协议去取它 —— **协议，不是一个具体
实现**，所以"给一组假原料，看板算出什么"这件事不需要真数据库。

## 2. 第一件事：缺一天就是少一天

看板的窗口是 **7 天**，验收条件是"≥7 天连续运行"。

**窗口的每一天都必须有一个点。** 不是"有数据的那些天各有一个点" —— 是**每一天**
。少一天，那天在图上就是**不见了**；而"不见了"在图上读起来与"那天是平的"**完全
一样**。这两件事的含义相反：一个是"没有进展"，一个是"根本没有观测"。

所以这件事是**构造不出来**的，而不是"建议"：

```python
if len(trend.points) != len(days):
    raise TrendError(...)          # 点数与窗口对不上
if tuple(p.day for p in trend.points) != days:
    raise TrendError(...)          # 日期对不上
```

**没有周期的那天，点在，值与前一天相同**（累计口径），细节里写着
`cycles_closed` —— 读的人能看见"那天没闭合周期"。**这是"平的"与"没观测"之间
唯一的区别，而这个区别必须写在数据里，不能靠读者自己猜。**

**脚本层再钉一道。** `--days` 小于 7 直接拒绝执行：

```
--days 不得少于 7 天 —— 验收要求「≥7 天连续运行」，而少于七天的窗口看起来照样正常
```

**"少于七天的窗口看起来照样正常"** —— 正是这句话说明这道拒绝是有必要的。

## 3. 第二件事：算不出来不是 0

每个点都带状态，不是只有值：

| 状态 | 意思 |
| --- | --- |
| `computed` | 算出来了 |
| `no_samples` | **有口径，但没有样本** —— 例如还没有跑过验收 |
| `baseline_missing` | **口径需要一个还没建立的基线** —— 例如还没做人工标注 |

**三者在报表上都长得像"0"。** 而它们的含义完全不同：

- `computed` + `0` = **真的查了，没有**。这是结论。
- `no_samples` = **还没查**。这是一句"不知道"。
- `baseline_missing` = **没法查** —— 需要的东西还没有。**这是一句"还没开始"。**

**把它们都渲染成 0，最先出事的是那个 `baseline_missing`。** 没有人工标注时，
"有效问题发现率"算出来是 0 —— 于是读的人会得出"系统一个真问题都发现不了"的
结论；而真相是"**还没人来标**"。**一个会骗人的结论，比没有结论更糟。**

所以：值是 `None`，Markdown 里渲染成 `—`，表头旁边写着"**— 表示算不出来（基线
未建立 / 无样本），不是 0**"。

**看板上写死的那两条"算不出来"，是这一层最要紧的两处诚实：**

| 指标 | 为什么算不出来 |
| --- | --- |
| 有效问题发现率 | 需要人工标注基线（`evaluation/labels/pilot.py`） |
| 回归缺陷率 | 阶段一的库里**没有缺陷表** —— 没有查过，不是查了没有 |

**第二条尤其要写下来。** "回归缺陷率 0%"读起来像"我们的改动很安全"；而真相是
"**我们没有缺陷数据**"。`TaskOutcome.introduced_defects` 传的是 `None`，不是
`0` —— `None` 与 `0` 在这一层是两种不同的结论。

## 4. 第三件事：曲线是累计的

**第 D 天的点 = "截至第 D 天为止"的指标值。**

理由是**近因偏差**：按天算的话，最后一天的任务还没跑完，那一天的成功率必然
低 —— 曲线一路向下，**而那不是系统在变坏，是口径在骗人**。一个刚启动的任务
还没跑完就被记成失败，一个只看最近一天的人会以为系统在崩。

累计口径没有这个问题，**而且与注册表里那些指标本身的定义一致** —— 它们的分母
本来就是"到目前为止的全部样本"。

**代价是：数据层要读全部历史，不能只读窗口里的。** 窗口是**横轴的范围，不是数
据的过滤器** —— 所以第 1 天的点算的是"从项目开始到第 1 天为止"，而不是"第 1 天
那一天"。否则第一天与第二天的分母不是一回事，**那条曲线自己跟自己都没法比**。

## 5. 第四件事：看板主动拒绝被禁的量

R-117 禁三个量：**任务数、Token 数、提交量**。

**看板在构造时主动拒绝它们**，而不只是"初始集合里没有它们"：

```python
if is_forbidden(trend.metric_id):
    raise ForbiddenMetricError(...)
```

**区别很大。** "初始集合里没有"是**默认**，而默认是可以被绕过的 —— 哪天有人想
加一条"任务数"的曲线，改一行代码就够了。**拒绝是结构性的**：任何一条被禁的量
都进不来，除非有人去改 `is_forbidden` 本身，而那是一个**显式的、需要解释的**
动作。

**核心指标与诊断量互斥，也是结构性的。** 核心指标（成绩）必须登记在注册表里；
诊断量（背景）必须**没有**登记过 —— 一个量既是成绩又是背景，读者迟早会把它当
成绩看，于是它就被优化了，那正是 R-117 要防的事。

看板上有 **8 条核心曲线（4 层）+ 2 条诊断曲线**：

| 层 | 指标 |
| --- | --- |
| 自主发现 | 有效问题发现率、重复发现率 |
| 决策质量 | 决策采纳率、误报率 |
| 工程交付 | 任务成功率、返工率、回归缺陷率 |
| 项目演进 | 目标达成度差值 |
| 诊断量 | 验收通过率（质量）、累计花费（成本） |

**四层一层都不能少 —— 这是构造条件，不是建议。** 少了项目演进层，看板就答不了
"项目是否真的变好"；少了任何一层，它就答不了那一层的问题。

## 6. 成本只认账本

**成本曲线只从预算账本取数**，不从周期记录里的 `cost` 汇总取 —— 那是调用方抄
过去的一份（`infrastructure/database/budget.py` 才是**同源**的那一份，R-039）。

**被拒绝的花费不进成本。** 账本里 `blocked` 的流水是"系统试图超预算但被拦住了"
的证据 —— **那不是花掉的钱**。见 `docs/architecture/resource-control.md` §3：
被拒的流水是"今天到头了"的证据，账本不许删除，所以它天然活得下来。

**没有流水时报"取不到"，不报 0。** "没记账"与"一文未花"在报表上长得一样，而后
者是一个**假的安全信号**。

**币种必须只有一个。** 两个币种的数不能相加 —— 那算出来的数什么都不是。混了币
种时指标层**直接报错**，而不是替人折算（折算需要汇率，而汇率是另一个话题）。

## 7. 已知缺口：`project_snapshot` 没有时间戳

**这一节写下来，是为了免得以后有人把它当成设计。**

`project_snapshot` 表**没有时间戳列** —— 它记的是"第 N 版快照"，不是"什么时候
的快照"。所以真正从 KR 实际值算出来的**覆盖率 / 质量趋势**（快照那一层）目前
**无法按天归集**。

（这个缺口在集成测试里被钉住了：`tests/integration/test_trend_board.py` 里的
`TestTheProjectSnapshotHasNoTimestamp` 直接查 `information_schema.columns` 断言
"没有 `created_at`、也没有 `recorded_at`"，同时对照断言 `verification_run` **有**
`created_at`。）

**所以看板的质量维度用的是验收通过率**（来自 `verification_run.created_at`），
而不是快照里的指标 —— **能用时间戳归集的那一份，才是可以画成曲线的那一份。**

补齐这个缺口有两条路：给 `project_snapshot` 加时间戳列（改数据模型，影响历史
数据），或者把快照按周期关联（`project_snapshot` 挂到 `cycle_id` 上，用周期闭
合时间归集）。**第二条不动表结构**，但要求周期与快照一一对应 —— 这件事在阶段
二之后才有意义（那时一个周期可能对应多份快照）。**当前先记下来，不假装它已经解
决了。**

## 8. 已知缺口：单位成本收益留到阶段四

`docs/design.md` §10 的项目演进层最终形态是**单位成本收益**（达成度提升 ÷ 成
本）。看板里这一层给的是**达成度差值**（`attainment_delta`），**不是**单位成本
收益。

**理由在设计文档里已经写死了：阶段一没有可辩护的做法，硬算出来的是噪声。** 除
以一个可能为 0、可能币种不一、可能根本没记账的成本，得到的数没有意义 —— 而一
条看起来精确的曲线比没有曲线更危险。

**它留到阶段四，与 TASK-P4-050（自主演进策略优化）、TASK-P4-080（A/B 对照实验）
一起做。** 那时候有三样今天还没有的东西：稳定的成本归集、足够长的样本、以及能
区分"变好是因为这一笔投入"与"变好是因为别的"的对照实验。

## 9. 实测：T2

**验收条件：能导出 ≥7 天连续运行的四层指标趋势。**

### 9.1 纯函数层（35 条）

`tests/unit/evaluation/test_trend.py` —— 给定原料，断言算出来的形状：

| 验的是什么 | 断言 |
| --- | --- |
| 窗口七天 | 每条曲线**恰好 7 个点**，日期与窗口逐日对齐 |
| 缺口不是零 | 没有周期的那天，**点在**，值与前一天相同，`cycles_closed` 照实写 |
| 被禁的量进不来 | 画一条"任务数"曲线 → `ForbiddenMetricError` |
| 未登记的进不来 | 核心指标没登记 → `TrendError` |
| 核心与诊断互斥 | 诊断量撞上核心指标 → `TrendError` |
| 四层缺一不可 | 少一层 → `TrendError` |
| 没有基线不是 0 | 标注基线不在 → `baseline_missing`，**值是 `None`** |
| 跳过不算失败 | `skipped` 不进分母 |
| 混币种要报错 | 两个币种 → `ValueError`（"币种"） |
| 一个点不叫持平 | 只算得出一个点 → `unknown`，不是 `flat` |
| 导出可逐字节比较 | JSON 键排好序，两次写出来一样 |

### 9.2 真实数据库层（19 条）

`tests/integration/test_trend_board.py` —— 真 PostgreSQL、真周期、真候选、真决策、
真任务、真验收、真账本流水。**种七天，其中 11-06 故意没有周期。**

| 量 | 值 |
| --- | --- |
| 窗口 | 2026-11-04 ~ 2026-11-10，**7 天** |
| 任务成功率 | **4 / 7**（前四天完成，后三天没完成） |
| 决策采纳率 | **7 / 7** |
| 重复发现率 | **0 / 7**（每天引用各自的报告） |
| 达成度差值 | **0.20**（0.40 → 0.60） |
| 验收通过率 | **4 / 7**，被跳过的那次**不进分母** |
| 累计花费 | **7.00 USD** —— 每天 1.00，**被拒的那笔 5.00 不在里面** |
| 有效问题发现率 | **基线未建立**（值是 `None`，不是 0） |
| 回归缺陷率 | **基线未建立**（库里没有缺陷表） |
| 没闭合的周期 | **不进看板** |
| 账本里的 `blocked` 流水 | **在库里，成本曲线里没有它** |
| 没有数据的项目 | **也给一块空看板** —— 明确说"这儿还没有数据" |

**"被拒绝的那笔不在成本里"是被单独断言的** —— 不是靠"总额对得上"顺带证明的。

**"分母是全部任务，包括没跑完的"** 也是被单独断言的：只拿"跑完的任务"当分母，
会让一个跑不完就放弃的系统显示出很高的成功率。

## 10. 没测的，和已知的不足

**没测的：**

- **没有真的连着跑 7 天。** 上面的七天是**种出来的**，不是跑出来的。**真实的
  七天里会有中断、会有半途而废的周期、会有重复触发** —— 这几件事对曲线形态的
  影响**没有量过**。TASK-P3-018（连续 10 周期长跑）会补上这一块。
- **没有测过 30 天、90 天。** 天数越多，取数越慢（累计口径要读全部历史）——
  **这条曲线有多长还不知道**。
- **没有测过多个项目。** 看板是按项目 id 取数的，但"两个项目同时看板"这件事没
  验过 —— 成本的作用域默认是项目 id，而**账本里可能有别的作用域**。
- **没有测过标注基线接上之后的曲线。** 集成测试里标注基线**一直是缺的** ——
  有效发现率与误报率这两条曲线**从来没有在有基线的情形下跑过**。

**已知的不足（不是设计，是缺口）：**

- **`project_snapshot` 没有时间戳**，覆盖率 / 质量趋势暂时画不出来。见 §7。
- **单位成本收益不在其中**，阶段四才有。见 §8。
- **窗口是横轴，不是过滤器。** 读全部历史意味着取数随项目寿命线性增长 ——
  **跑久了会慢。** 现在没有分页、没有预聚合、没有缓存。
- **只有一个币种能画。** 混了币种直接报错 —— 但"报错"不等于"有解"，多币种项
  目目前画不出成本曲线。
- **没有告警。** 看板是给人看的报表，**曲线掉下去不会有人被叫醒** —— 把它接进
  告警需要另一套阈值机制（而且阈值本身需要基线，而基线正是不够的那部分）。
- **方向只比头尾两个点。** `direction` 拿**第一个算得出的点**与**最后一个**比 ——
  中间怎么走的看不出来。**"先崩后涨"与"一路涨上去"在这条判据下是一样的。**
- **任务归到周期上要穿过决策。** 任务表上没有 `cycle_id` 列，所以一个**没有决
  策的任务**（直接创建的）**在看板里不存在**。这是数据模型的现状，不是这一层
  的选择 —— 但它意味着**看板只看得见"从候选到任务"那条路走通的东西**。

## 11. 与设计要求的关系

| 要求 | 落在哪 |
| --- | --- |
| TASK-P3-017 交付物"跨周期趋势看板（达成度、质量、成本）" | `evaluation/trend.py` + `infrastructure/database/trend.py` + `orchestration/dashboard.py` |
| TASK-P3-017 验收"能导出 ≥7 天连续运行的四层指标趋势" | `tests/integration/test_trend_board.py`（19 条，真库）+ `scripts/export_trend.py`（`--days` 下限 7） |
