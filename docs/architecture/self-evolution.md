# 系统自身改进提案 —— **自我修改只能走提案、独立测试、审批、发布这条路**

设计依据：`docs/tasks.md` TASK-P4-070（交付物"``SystemEvolutionProposal`` 实体 +
独立测试 + 审批后发布"；验收条件"系统提出的自我修改全部走独立测试与审批；**不存在
绕过审批的发布路径**"；验证 T1）、R-102（不得自主修改控制自身的系统）、R-104
（防止系统自改验收标准）、`docs/design.md` §7、`TASK-P1-011`（治理外置 + 变更需
审批）。

> **系统可以改进被管理的项目，但不能改进控制自己的那部分。**
>
> 这两件事在能力上只差一层，但性质完全不同。前者是被管理对象的事，系统有把握；
> 后者是**裁判给自己改判罚标准**——改了验收标准，改动就更容易通过验收，然后
> 再改一次。design.md §7 划的正是这条线。
>
> 而"不允许"不是好答案：把自我改进整个禁掉，系统就永远学不会自己哪里做得差。
> **正确答案是一条绕不过去的路**：改自己得先提一份提案，**由别人测、由别人批**，
> 批的是**具体那一版内容**，判的是**具体那一版标准**——**缺一样都发不出去**。
>
> 最要紧的是：**这条路上不能有第二个出口。** 只要有一个"直接改"的口子，前面
> 三道关就都是摆设。而"没有第二个出口"这件事，**靠文档说是不够的**——得靠
> 代码把每一个绕法都堵死。

## 0. 一句话

**自我修改走四步：提交 → 独立测试 → 审批 → 发布；四道凭据（测试人、审批人、
内容摘要、验收标准版本）全部绑死，每一步的结论都存在对象之外**——**发布前
从审批存储里把结论重新取回来核对，伪造一份"已审批"的对象也发不出去。**

## 1. 缺口在哪

改动被管项目的代码，系统自己就有把握，改就改了。但**改动控制自己的那部分**，
把握就没了：

| 缺什么 | 后果 |
| --- | --- |
| 没有"**提案**"这个载体 | 改了什么、谁改的、凭什么改 —— 事后说不清 |
| **提案人自己测自己** | 自证：改坏的东西自己宣布通过 |
| **提案人自己批自己** | 自批：既当运动员又当裁判 |
| 审批批的是"**这条提案**"而不是"**这一版内容**" | 批完之后偷偷改内容，批准照样生效 |
| 审批不绑**验收标准版本** | 先改标准、再回头拿旧批准过关 —— **R-104 直接针对的那件事** |
| 没有"**发布只有一条路**"的保证 | 任何一处"直接改"的口子，前面三道关全成摆设 |

后三行是这一层存在的全部理由。**前两行（自己测、自己批）好办** —— 实体校验就
能挡住。**第三行以后（绑定、唯一路径）不好办** —— 因为它们要么需要跨对象的一致
性，要么需要防"绕过状态机"，而这两样都不是单个类能保证的。

## 2. 四条硬约束

**这四条不是流程上的建议，是校验里写死的规矩** —— 违反的提案**压根建不出来**。

| # | 约束 | 挡的是什么 |
| --- | --- | --- |
| 1 | **测试人 ≠ 提案人** | 自证 |
| 2 | **审批人 ≠ 提案人** | 自批 |
| 3 | **测试与审批绑在内容摘要上** | 批完之后偷改内容 |
| 4 | **审批绑在验收标准版本上** | 先改标准、再拿旧批准过关 |

**为什么"绑在摘要上"而不是"绑在提案上"。** 人批的是**他当时看到的那一份改
动**。内容变了，那份批准就不再是他批的东西了 —— 哪怕提案编号没变、标题没变、
还是那场审批。**绑定的是内容，不是名字。**

**为什么第 4 条不能省。** 没有它，系统可以：先把验收标准改松 → 拿旧标准下的
批准 → 用新标准验收自己的改动。**这就是"系统逐步修改验收标准，让自己更容易通
过验收"** —— R-104 说的正是这件事。

## 3. 状态机

**七个状态，一个不多一个不少**，每多一个就多一个"现在到哪一步了"说不清的地方：

```
draft
  │ submit
  ▼
submitted ──record_test(没过)──▶ failed_test（终态）
  │ record_test(过)
  ▼
verified ──record_approval(拒)──▶ rejected（终态）
  │ record_approval(够数)
  ▼
approved ──publish──▶ published（终态）
```

| 状态 | 含义 | 还能往前吗 |
| --- | --- | --- |
| `draft` | 刚写出来 | 能 |
| `submitted` | 已提交，等独立测试 | 能 |
| `verified` | 独立测试通过，等审批 | 能 |
| `failed_test` | 独立测试没过 —— **终态** | **不能**，改了要重新提 |
| `approved` | 审批齐备，可以发布 | 能 |
| `rejected` | 被人拒了 —— **终态**，而且是**粘的** | **不能** |
| `published` | 已发布 —— **终态** | **不能** |

**两个终态是"粘的"，这一点是刻意的。**

- **测试没过是终态。** 改一改再提可以，但**不能在同一份提案上"再测一次直到
  通过"** —— 那样测试就变成了"调到过为止"。
- **拒绝是终态。** 拒过的东西不会因为没人再表态就变成"没人反对"。**没有明确
  批准，就等于没有批准。**

**构造出来的提案一律是 `draft`。** 别的状态只能由状态机推出来 —— **凭空造一个
"已审批"的提案，构造时就报错**。这一条挡住的是"**绕过状态机直接造出终态**"
这条路。

## 4. 内容摘要：批准的是"人当时看到的那一份"

摘要用**规范化 JSON** 算（字段排序定死、空白定死），再取 SHA-256：

```python
canonical = json.dumps(payload, ensure_ascii=False, sort_keys=True, separators=(",", ":"))
digest = hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

**摘要只覆盖"这次要改什么"** —— 项目、种类、标题、目标、改了什么、补充说明、
风险档、审批数。**状态、审批记录、时间戳都不在里面**：它们是这份提案**走过的
路**，不是**改动的内容**。

> **为什么不用拼字符串。** 拼字符串时，"字段顺序变了"、"少了一个冒号"都会算出
> 另一个摘要 —— 于是"内容其实没变"会被误判成"内容被改过"，而误判的方向恰好是
> **把好的当成坏的**：发布被无端卡住。规范化 JSON 把顺序与空白都定死。

**摘要变了，那份测试与那份审批就全都失效。** 这不是"建议作废"，是**校验里判
"批的不是这一版内容"** —— 记审批的时候就拒。

## 5. 验收标准版本：R-104 的落点

**版本号是治理外置的。** 现在生效的是哪一版，住在治理存储里
（`orchestration/self_evolution.py` 的 `CriteriaPort`），**既不在提案对象里，也
不在策略对象里**。

> **为什么不能把它塞进策略对象。** 策略对象是系统自己手里的东西。系统自己掌握
> "现在是第几版标准"，就等于自己掌握"我这份提案按哪版判"这个答案 —— 而那正
> 是 R-104 要防的事。**标准版本必须住在系统改不到的地方。**

**版本形状定死**：`^criteria-v\d+$`。`v3`、`三`、`3.0` 三种写法都能塞进一个
字符串字段，而只有一种写法能保证"推进一版"这件事不会算错。

**推进是机械的**：只有当**一份已审批的"改验收标准"提案真的发布了**，版本才
推进一版（`criteria-v3` → `criteria-v4`）。**没发布就不推进** —— 提案被拒、
测试没过、审批没齐，版本都原地不动。

## 6. 风险下限、审批数与评审资格：规矩只能往严里加

**下限钉在种类上**，因为风险是这类改动的**内在属性**，不是项目的心情：

| 种类 | 风险下限 | 最少独立审批 | 要求的评审资格 | 为什么 |
| --- | --- | --- | --- | --- |
| `code_change` | 中 | 1 | （无） | 改自己的实现代码 |
| `configuration_change` | 中 | 1 | （无） | 阈值、超时、并发数 |
| `dependency_change` | 高 | **2** | **security** | 换依赖可能换进新的攻击面 |
| `architecture_change` | 高 | **2** | **architecture** | 改分层、改边界 |
| `acceptance_criteria_change` | 高 | **2** | **governance** | **改判罚标准** |
| `policy_change` | 高 | **2** | **governance** | 改决策策略、权限策略、预算限制 |
| `governance_change` | 高 | **2** | **governance** | **改"谁能批、怎么批"** |

**改标准、改策略、改治理 —— 这三类动的都是"谁说了算"。** 一个人既提标准又批
标准，等于自己给自己定规矩又自己验收。**所以这三类一个人批不够。**

**"有几个人批了"回答不了"这几个人看得懂吗"。** 让一个只懂测试的人去批改架构
的改动，等于没批 —— 所以每一类改动还有一条**资格下限**：改依赖要安全评审人，改
架构要架构评审人，改标准、改策略、改治理要治理评审人。

> **为什么资格下限也住在提案实体里，而不是只在流程层查。** 实体这一层是**纵深防
> 御** —— 它让"漏写一步"在代码里就发生不了。**要是资格只在流程层查，那么任何
> 绕过流程直接调用 `publish` 的路径就绕过了它。** 实体层按审批记录上记着的资格
> 判，流程层再拿**在册的评审人名册**核一遍（`orchestration.high_risk_review` 干
> 的就是这件事）—— **两层都要过**。

**没提要求 = 用天生的下限**，而不是"什么都不要"。**规矩只能往严里加**：减去一项
资格，改架构就没人看得懂了 —— 那样的一份提案**建不出来**（`ValueError`）。

**项目可以在下限之上再抬**（`core/policy/self_evolution.py`），但**只能往严里
加**：写一个比下限更松的值，**策略压根建不出来**（`ValueError`，不是被悄悄忽
略）。

> **为什么"更松就报错"而不是"更松就取下限"。** 悄悄忽略会让人以为那份配置生效
> 了 —— 于是"我明明把它放松了啊"这种误解会一直传下去。**报错**才说得清。

**审批数按人算。** 一个人点两次批准**不算两份意见** —— 一个人可以在系统里留三
份审批记录，但那还是一个人的意见。所以治理类提案要的第二份审批**必须来自另一
个人**。

## 7. 流程层：真正的闸

**领域层的状态机是纵深防御** —— 它让"漏写一步"在代码里就发生不了。但 Python
里的对象是**可以伪造的**：绕过冻结直接改字段，谁都能把状态改成"已发布"。

> **所以流程发布前不信任对象。**
>
> `SelfEvolutionFlow.publish` 每次发布都**从审批存储里把结论重新取回来**，再拿它
> 跟提案当前的内容摘要、验收标准版本、提案人**逐项对**。**对象说什么不算，存
> 储里那份说了算。**

发布前逐项核对，**对不上就停**：

| 核对 | 对不上时 |
| --- | --- |
| 存储里**一条结论都没有** | 没有审批结论 |
| **有人拒过** | 有人拒过 —— 拒绝是终态 |
| 独立审批**不够数** | 只审批了几份、要几份 |
| **提案人在审批人里** | 提案人自己批自己 |
| 审批绑的**摘要 ≠ 当前摘要** | 内容变了，批准作废 |
| 审批绑的**标准版本 ≠ 提案判定时的版本** | 用的不是判定时那一版标准 |
| 提案的**标准版本 ≠ 现在生效的版本** | 标准在审批之后变了（R-104） |

**实体层的闸还在**：核对过了还要过 `SystemEvolutionProposal.publish` 的四道校验
（状态、通过的独立测试、够数的独立审批、标准版本一致）。**两层都要过** —— 一层
查对象，一层查存储。

**审批结论存在对象之外。** 提案上记着 `approval_request_id` —— 流程据此知道去
哪儿取结论。**这不是冗余**：对象上的 `status` 是可以伪造的，**请求号只能指路，
不能替结论**。

## 8. 失败关闭

**审计写在效果之前。** 写不进去，就**不动手**：

```
核对 → 实体层的闸 → 写审计（失败就停） → 落地改动 → （改标准的那一类）推进版本
```

**为什么审计排在落地前面。** 没留痕的发布比没发布的改动更糟 —— 前者连"它发生
过"都答不上来。**先记下来，再做**；记不下来，就别做。

**审计事件带三样凭据**：内容摘要（事后核对的凭据）、验收标准版本（R-104 的凭
据）、动作与细节。**光有"发布了"三个字，事后什么也核对不了。**

### 9.2 伪造路径是**真的被测过**的

**"不存在绕过审批的发布路径"这句话，单靠"代码里没写这条路"是不够的。** 所以
测试里有一类专门的用例：**绕过冻结直接改字段，造出一份假的**：

```python
clone = object.__new__(type(proposal))
for field_ in fields(proposal):
    object.__setattr__(clone, field_.name, getattr(proposal, field_.name))
object.__setattr__(clone, "status", ProposalStatus.APPROVED)  # 伪造"已审批"
```

然后把它塞回存储，走完整的发布流程 —— **发不出去**（`没有审批结论`）。同类
的还有：伪造一份"内容被偷改"的（`这一版内容` 对不上）、在审批之后把标准推到
下一版（`验收标准` 对不上）、在审批人里塞一个提案人自己（`提案人`）。

**这四条用例是这一层最重要的四条** —— 它们测的正是验收条件里那句话。

### 9.3 类型与规范

`ruff`（本仓库全套规则，含 `PLR0913`、`PLR2004`、`RUF022`、`ANN`）与 `mypy`
（`disallow_any_explicit`）在这几个新模块上**全绿**：

```bash
.venv/bin/python -m ruff check core/evolution/common.py core/evolution/risk.py \
  core/evolution/proposal.py core/evolution/placeholders.py \
  core/policy/self_evolution.py orchestration/self_evolution.py
.venv/bin/python -m mypy core/evolution/common.py core/evolution/risk.py \
  core/evolution/proposal.py core/evolution/placeholders.py \
  core/policy/self_evolution.py orchestration/self_evolution.py
# Success: no issues found in 6 source files
```

> **为什么多出两个模块。** `core/evolution/common.py`（摘要、空串、占位、资格去重）
> 与 `core/evolution/risk.py`（评审资格词汇与下限）**是 TASK-P4-060 那一层抽出来
> 的叶子模块** —— 两边都要用同一套"算摘要""查占位""去重资格"的规矩，而各写一份
> 迟早会对不上。**它们不依赖任何东西**，所以放在最底下，谁都能引。

> **为什么这几个模块不用 Pydantic 模型。** 仓库里的 `disallow_any_explicit` 是全
> 局开的，而 Pydantic v2 继承来的 `BaseModel.__init__(**data: Any)` 会让每一个
> Pydantic 模型模块在类定义那一行报 `explicit-any`。绕过去的办法是往
> `pyproject.toml` 的 per-module 豁免清单里加名字 —— 而那份清单本身是**受测试
> 守着的窄门**（`tests/unit/core/test_no_any_escape.py`：清单多一个就红）。
>
> **能不登记就不登记。** 改成冻结数据类 + 显式 `__post_init__` 校验之后，**豁免
> 清单一个字都不用动** —— 校验也是**显式写出来**的，不依赖框架的默认行为。与
> `core/policy/approval.py` 是同一套写法。

## 10. 没测的，和已知的不足

1. **这一层没有接数据库，也没有接真的 LLM。** 端口是六个 Protocol，实现只有
   测试里的内存版。**"真的从数据库里取回审批结论"这件事没有测过** —— 生产版
   仓储层还没写（见 §12）。
2. **没有端到端地跑过一次真实的自我修改。** 测的是"**提案机制本身**"，不是
   "**系统真的自己改了一处、并且改对了**"。后者要等 TASK-P4-050。
3. **审批人是谁，这里只当字符串处理。** "谁有资格批"这一层（权限）**不在这
   一层里** —— 这一层只保证"批的人 ≠ 提的人"。**两个不同的人，其中一个有权限
   一个没有，这一层看不出来。**
4. **独立测试是"有独立测试报告"这件事，不是"真的独立跑了测试"。** 测试报告由
   端口给；这个端口背后跑的是什么，**这一层不关心也不验证** —— 那是
   `TASK-P4-060`（高风险变更治理）要接的东西。
5. **审计的持久化没测。** 只测了"审计写不进去就不发布"这个失败关闭的**行为**，
   没测审计本身写进数据库之后能不能查出来。
6. **并发场景没测。** 两个人同时批一份提案会怎样、审批与改内容同时发生会怎样
   —— **这一层没有并发控制**，没有乐观锁也没有悲观锁。
7. **摘要只覆盖内容，不覆盖"这个改动会被怎么落地"。** 落地方式变了（同一个
   `change_summary`，换了个实现）而内容摘要不变 —— 这条路是通的。**这一层管
   的是"批的那一版内容还在不在"，不是"落地的东西和批的完全一致"。**
8. **版本推进只推进一版。** 一次发布只走一版 —— 并发的两个"改标准"提案同时发
   布，一个推进到 v4、另一个推进到 v5 还是都推进到 v4，**这一层没处理**。
