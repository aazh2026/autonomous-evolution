# 独立验证引擎 —— 六层各判各的

设计依据：`docs/design.md` §3.5B（"不要让 Coding Agent 自己决定是否验收通过"；
六层验证表；Acceptance Contract）、§3.2（"不能所有任务都走相同的验收流程"）；
`docs/tasks.md` TASK-P2-014（交付物 `harness/verification/six_layer.py`；验收
条件"六层验证独立执行并产出结构化多维报告，任一层失败独立给出修复诊断，不坍缩
为单个布尔值"）、R-050（六层验证能力）、R-077（不同任务类型走不同验收流程）、
降级 G（阶段一不做性能层，进入阶段二前需先补基准环境与判定规则）。

> **这一层把阶段一的"一个布尔值"拆成六份独立的结论。** 阶段一的验证引擎
> （`harness/verification/engine.py`）回答的是"这次够不够"—— 一个判定、一个
> 结论。阶段二要回答的是另一件事：**"哪一层坏了，怎么修"**。

## 0. 一句话

**一个布尔值回答不了"下一步该干什么"。**

"验收没过"这句话不告诉你该改哪儿：改测试？改 lint 规则？把依赖方向倒过来？
撤掉刚泄漏的密钥？补一次人工评估？这些的返工成本差着几个数量级。**把它们
压成一个布尔值，被压掉的就是返工时要用的那份信息。**

## 1. 六层，各有各的判定

| 层 | 验什么 | 这一层说什么 |
| --- | --- | --- |
| 功能 | 需求是否实现 | 哪几条用例没过 |
| 代码 | 代码是否符合规范 | 哪个文件第几行、哪条规则 |
| 架构 | 是否违反架构约束 | 哪条依赖边、哪个方向错了 |
| 安全 | 是否存在安全问题 | 命中了哪条禁止项、在哪个文件 |
| 性能 | 是否出现性能退化 | 哪个指标、比基线差多少 |
| 产品 | 是否达到预期体验 | 哪个目标没达到、缺哪次人工评估 |

**每一层有自己的执行器（`LayerRunner`）与自己的判定器。** 一份执行器只能属于
一层 —— 两层共用一份执行器，那它们的判定也就必然共用，"独立"就成了空话。

### 1.1 三态不够用，四态才够

阶段一的 `CheckOutcome` 是三态：通过 / 不通过 / 没验成。六层之后多出来的那
一态是 **判不了**（`NOT_JUDGED`）：

| 结论 | 含义 | 该怎么办 |
| --- | --- | --- |
| `PASSED` | 验了，过了 | —— |
| `FAILED` | 验了，没过 | **返工** |
| `ERROR` | 没验成（命令不存在、超时、层自己崩了） | **重跑**（环境问题） |
| `NOT_JUDGED` | 判不了（依据不具备：没基线、没人评） | **先把依据补上** |

**`ERROR` 与 `NOT_JUDGED` 必须分开。** 前者该重试或换环境，后者该先把基线建
起来 —— 重试解决不了"没有人做人工评估"这件事。混在一起就只剩"再试一次"，
而"再试一次"解决不了任何一种。

## 2. 四条不肯让步的规矩

### 2.1 "判不了"不等于"通过"

降级 G 写的是"性能基线未建立"，**不是 0**。这一层在基线建立之前只报数、
不下结论：

```python
result = _layer(report, VerificationLayer.PERFORMANCE)
assert result.outcome is LayerOutcome.NOT_JUDGED
assert "基线未建立" in result.detail
assert result.metrics["latency"].number == Decimal(120)  # 数还是量出来了
```

**报数与下结论是两件事。** 把实测的 120 读成 0，恰好抹掉了"现在到底多快"
这个唯一有用的信息 —— 而降级 G 要的恰恰是"基线未建立"这句话，不是把数字
藏起来。

产品层同理：**目标没达到是确定的失败，人没评是判不了。** 合成一个"没过"，
就会让人去改那些本来没错的东西。

### 2.2 一层失败，不影响其余五层

层的执行与判定都是**各自独立**的。一层崩了（抛异常），记成 `ERROR`，其余
五层照常给结论：

```python
report = await verifier.verify(request)
assert report.errored_layers == (VerificationLayer.FUNCTIONAL,)
assert report.failed_layers == ()  # 崩的那层不算"失败"
assert report.result(VerificationLayer.CODE).outcome is LayerOutcome.PASSED
```

**"崩了"与"没过"不能混。** 崩了是环境问题，该重跑；没过是产出问题，该返工。

### 2.3 每一层自己给修复诊断

**通用的"检查没通过，请修复"对六层都成立 —— 所以它没有提供任何信息。**
每一层的诊断里必须有**只有这一层会说的话**：

| 层 | 诊断里必须有的 |
| --- | --- |
| 功能 | 哪条用例（`tests/unit/test_a.py::test_one`） |
| 代码 | 哪个文件第几行、哪条规则（`src/pkg/thing.py:1:8 F401`） |
| 架构 | 哪条依赖边（`pkg.thing → tests.test_thing`） |
| 安全 | 命中了哪条禁止项（`secrets_in_diff`） |
| 性能 | 哪个指标（`latency`） |
| 产品 | 哪个目标（`响应时间`） |

测试就是这么钉的：把某一层的诊断换成通用话术，那条用例会红。

**lint 的两种输出格式都要认。** 紧凑格式（`path:line:col: CODE 消息`）与
ruff 默认的完整格式（先一行规则名，再一行 `--> path:line:col`）—— 只认一种
的话，另一半的 lint 报错就只剩"检查没通过"这句话了。

### 2.4 整体结论是**派生**的

报告里存的永远是六份独立的层结果。整体结论由它们算出来，随时可以重算：

```
FAILED > ERROR > INCOMPLETE > PASSED
```

**只看算数的层**（`required`）。不算数的层照样跑、照样记结果 —— 但它不参与
整体结论。

## 3. 哪几层算数：R-077

`docs/design.md` §3.2 说"不能所有任务都走相同的验收流程"。落法是**按任务
类型给一套默认的层**：

| 任务类型 | 默认要的层 |
| --- | --- |
| `FEATURE` | 功能、代码、架构、产品 |
| `BUGFIX` | 功能、代码、架构、安全 |
| `REFACTORING` | 功能、代码、架构 |
| `TEST` | 功能、代码 |
| `PERFORMANCE` | 功能、代码、性能 |
| `DEPENDENCY` | 功能、代码、架构、安全 |
| `DOCS` | 代码、产品 |

**这是"默认"，不是"强制"。** 优先级是：**契约里写明的 `required` > 任务类型的
默认 > 全部已配置的层**。契约说话最响 —— 那是执行前就定下的验收标准。

文档类任务不要功能层：改一段文档不需要跑单元测试；反过来，一个性能任务
绕不开性能层，而一个改测试的任务不需要产品层（它本身就是在写判据）。

## 4. 契约与六层怎么接上

**不另写一套契约判定。** 六层的结果被翻译成阶段一那份
`ContractEvidence`，再交给阶段一的 `evaluate_contract`：

```python
evidence = ContractEvidence(
    task_id=request.task_id,
    checks=...,  # 每层 → 它的必检项 → CheckOutcome
    metrics=...,  # 各层量到的指标
    violations=...,  # 安全层命中的禁止项
    produced_artifacts=...,
)
evaluation = evaluate_contract(contract, evidence)
```

**每一项必检项恰好归一层**（`CHECK_LAYERS`）。一个必检项归两层，等于有两个层
对它有发言权，而层与层之间并不知道对方判了什么 —— 那就等于没有人对它负责。

`NOT_JUDGED` 在投影成 `CheckOutcome` 时一律变成 `ERROR`，**绝不变成
`PASSED`**。

## 5. 为什么用"仓库索引"而不是"再起一个进程"

架构层是六层里唯一**不起子进程**的：它读仓库索引（`knowledge/`）算依赖边。

- **起进程跑架构测试**要装依赖、要写测试、要在每个仓库里重写一遍规则；
- **读索引**是把"依赖方向对不对"这件事变成一次查询。

索引是阶段二 TASK-P2-016 的产物 —— 六层验证正好用它。**"依赖规则的执行方"
从一开始就不在验证引擎里**，验证引擎只负责把结果翻译成结论。

## 6. 落在哪儿

```
harness/verification/six_layer.py     六层执行器、判定器、报告与投影
harness/verification/contract.py      阶段一的契约（被复用，没有另写一套）
knowledge/repository_index/index.py   架构层读它算依赖边
knowledge/architecture/model.py       架构层读它算分层违规
```

**依赖方向**：`harness` → `knowledge` 是**兄弟层之间**的引用，成环即可接受；
`harness` 不依赖 `executors`（R-049，这条有测试守着）与 `orchestration`。

## 7. 怎么跑

```bash
# 单元测试
uv run pytest tests/unit/harness/verification/test_six_layer.py -q

# 演示
uv run python -m scripts.demo_six_layer
```

演示要证明的不是"六层都过了" —— 那样什么也证明不了：全过的时候一个布尔值就
够了，六维报告和一个布尔值给出的信息完全一样。演示让六层**坏在不同的东西
上**：

| 层 | 演示里它坏在哪 | 结论 |
| --- | --- | --- |
| 功能 | —— | 通过 |
| 代码 | 一处未使用的导入（**真的 ruff 跑出来的**） | 未通过 |
| 架构 | 产品代码依赖测试代码（**真的索引读出来的**） | 未通过 |
| 安全 | 工作区里有一把密钥（**真的扫描器扫出来的**） | 未通过 |
| 性能 | ——（没有基线） | 判不了 |
| 产品 | 人工评估没通过 | 未通过 |

**三种结论同时出现在一份报告里** —— 这就是"不坍缩为单个布尔值"的意思。

**演示里没有一个替身。** 真的起进程跑 pytest、真的跑 ruff、真的扫密钥、
真的跑基准脚本。假密钥只存在于临时工作区里（而且是拼出来的，仓库自己的密钥
扫描器看不到它）。

## 8. 边界

**这一层不做的事**：

- **不替 Agent 做判断。** 它给结论与诊断，改什么是 Director 与修复器的事
  （TASK-P2-015）。
- **不改阶段一的引擎。** 阶段一的扁平引擎还在原地，六层是**加**上去的一层，
  不是替换 —— 两者共用契约与判定规则。
- **不建基线。** 性能层的基线从哪来、怎么更新，是基准环境的事；这一层只
  负责"没有基线就说没有基线"。
- **不替人做评估。** 产品层的人工评估是人给的；这一层只负责把它记下来、
  分清"没评"与"评了没过"。
