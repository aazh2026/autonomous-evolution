# 事件驱动六触发源 —— 六个触发源不是六个枚举值

设计依据：`docs/tasks.md` TASK-P3-011（交付物：`core/evolution/triggers.py`
事件契约、`orchestration/triggers.py` 派发路由、`apps/triggers/sources.py`
六路触发源；验收条件"六类事件各能触发一轮演进；同一事件去重后只触发一次"；
验证 T1 + T2）、R-079（六种事件触发源）、R-080（定期扫描与事件触发结合）、
I-11（事件回环）、`docs/design.md` §4（建议设置六种触发源）。

> **`TriggerSource` 早就存在，但它只是一份声明。**
>
> 六个枚举值躺在那里，谁都可以写 `trigger=TriggerSource.CODE`，然后没人说得
> 清这到底是**一次提交**、**一次质量失败**还是**一条用户反馈**。周期记录上写
> 着"代码触发"，事后翻的人看到的是一句无法核验的话。
>
> **六个触发源不是六个标签，是六种不同形状的事件。** 提交有 sha、质量失败有
> 用例 id、用户反馈有工单号 —— 它们的主体标识根本不是一回事。硬要用同一个
> 字段去装，最后装出来的就是一团糊。

## 0. 一句话

**六路各自去读各自的东西，读出来的是六种形状不同的事件；派发只有一条路，
因为去重窗口只有一份。** 前者是"看得见"，后者是"不重复"—— 缺了任何一个，
"事件驱动"都只是嘴上说说。

## 1. 三层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 契约 | `core/evolution/triggers.py` | 定义事件长什么样、哪类源能发哪种事件 | 不知道事件从哪来 |
| 编排 | `orchestration/triggers.py` | 派发、回环判定、去重、熔断 | 不知道 git 长什么样 |
| 触发 | `apps/triggers/sources.py` | 六路各自去读真的东西 | 不决定要不要开轮 |

**契约层在 `core/`，它连"git"和"pytest"这两个词都不该出现。** 它只回答一个
问题：**这件事属于哪一类？** 一个生产者把代码事件标成定时事件，契约层必须
报错 —— 因为那时候周期记录里写的就是"定时触发"，而实际上它是被一次提交触
发的，**事后没人能查出真相**。把这件事留到日志里，就是把"不可核验"写进了
系统的地基。

**编排层只有一扇门。** 六路源各自读、各自发，但**都从这一个门走** —— 因为回
环判定只有一份、去重窗口只有一份、熔断阈值只有一份。

**触发层只说"现在有什么"，不说"要不要因此开一轮"。** 那是派发那一侧的事。

## 2. 六类事件，各有各的形状

| 来源 | 事件类型 | 主体标识 | 读的是真的什么 | 一轮演进干什么 |
| --- | --- | --- | --- | --- |
| 定时 | `scan.found` | 项目 id | 一次扫描的结果 | 全项目扫描 |
| 代码 | `code.commit` | 提交 sha（40 位） | `git log` | 重新分析变更影响 |
| 质量 | `quality.failure` | 用例 node id | 真的跑一遍 pytest | 自动分析和修复 |
| 运行 | `runtime.incident` | 探针 id | 真的跑一条命令 | 创建诊断任务 |
| 外部 | `external.report` | 报告条目 id | 人写的台账 | 重新规划 |
| 知识 | `knowledge.update` | 文档 stem | 决策记录目录 | 评估是否需要演进 |

**"每类源恰好一种事件类型"不是省事，是承重。** 去重指纹是"事件类型 + 主体
标识"两样凑的 —— 主体撞上的时候，靠事件类型把两件事分开。"一次提交"与"一次
质量失败"的主体都是字符串，如果指纹只算主体，一次提交就可能把一条质量失败
挡掉。**把两件事当成一件事，比漏掉一件事更难查。**

**主体标识是空的，比撞车更糟。** 空的主体会让所有事件落进同一个指纹，于是只
有第一件被处理，其余全被当成重复挡掉 —— 而且**看起来一切正常**（开了轮、
有记录）。所以契约层直接拒绝空白的主体、空白项目和空白摘要。

## 3. 为什么派发只有一条路

```
六路源 ──► TriggerRouter ──► LoopBreaker ──► 循环 B
  │             │              (回环 → 去重 → 熔断)
  │             └── 去重窗口（一份）
  └── 各读各的
```

**每路各有一份去重窗口会出什么事？** 同一件事从两路来（一次提交既触发了代
码事件、又触发了知识事件，因为提交里改了 ADR），**会开两轮** —— 同一份工作
被做两遍，预算烧双倍，周期记录上还看不出哪里不对。

**去重窗口只有一份，所以指纹也只有一个定义。** 路由把 `TriggerEvent` 映成
`IncomingEvent` 时，用的是**事件类型的值**（`code.commit`），不是来源的名字
（`code`）。用来源的名字，"提交"与"质量失败"只要主体撞上就互相挡掉。

**回环判定在去重前面。** 顺序不能反：先看是不是自己引发的事件（回环 → 不
开），再看是不是重复（去重 → 不开），最后看是不是触发太多次（熔断 → 停）。
反过来会把回环当成重复，日志上写出来的原因就是错的 —— **"不开"必须说得清
为什么**。

**默认用内存存储。** 这是**已知不足**：进程重启，去重窗口就空了，重启后第一
次投递会被当成新事件再开一轮。真正的做法是把它落到库里，与周期记录放一起。

## 4. 实测：T1

**这一份测试里没有假的东西。** 打桩的只有各步处理器（跟
`tests/unit/orchestration/test_loop_b.py` 一样），但**图是真的 LangGraph 图，
闸门是真的去重窗口** —— 所以"开了一轮"这句话有底：库里真多了一行周期记录。

| 触发源 | 读的是真的什么 | 实测结果 |
| --- | --- | --- |
| 定时 | 试点仓库的源码索引（真扫一遍） | 扫到 **2** 个真问题 |
| 代码 | 本仓库真的 `git log` | **5** 条提交，sha 40 位 |
| 质量 | 试点仓库 `known_issues/`（真跑 pytest） | **9** 条用例真的没过 |
| 运行 | 试点仓库的 CLI（**真的崩一次**） | 退出码 **1** |
| 外部 | 人写的 `docs/issues.md` | **20** 条，一条不少 |
| 知识 | 仓库里真的 ADR | **1** 篇 |

**六个主体两两不同。** 定时的主体是项目 id、代码是 sha、质量是用例 id、运行
是探针 id、外部是 `PILOT-0NN`、知识是文档 stem —— 六路撞在一起的话，就只
是在跑同一件事。

**质量那一路跑的是真的。** 试点仓库 `known_issues/` 里那 9 条是 `xfail(strict
=True)` 的复现用例 —— 默认跑起来是"预期中的失败"，**不算质量问题**。所以
这一路默认带 `--runxfail`：**"这些毛病还在吗"要按真失败来跑。** 不带这个
开关，那 9 条会一条都不报 —— 而那正是最该报的东西。

**运行那一路是真的崩。** 探针跑 `python -m tinylib.cli stats ""`，退出码 1，
异常是 `ValueError: 空序列没有平均值`。事件摘要里带着退出码 —— 事后翻记录
的人知道当时是什么状态。

**外部那一路读的是人写的东西。** 台账是人写的，格式可能变，所以**认不出的
行直接跳过，不报错**；文件不在，就什么都不产出。缺台账不是事故。

## 5. 实测：T2

**验收条件里那个可量化的数：同一事件去重后只触发一次。**

| 指标 | 值 | 怎么来的 |
| --- | --- | --- |
| 投递次数 | **5** | 同一条外部事件连投 5 次 |
| 实际开轮数 | **1** | 周期记录里 `open_cycle` 的行数 |
| 被挡次数 | **4** | 路由的 `suppressed` 计数 |
| 挡下的原因 | **"去重"** | 决定里的 `reason` |
| 六路各投 2 次 | **6** 轮 | 每路各开 1 轮，六路合计 6 |
| 去重窗口 | **15 分钟** | 与 `core.events.dedup` 同值 |

**断言写的是"等于 1"，不是"小于等于 5"。** 后者会被"一轮都不开"蒙过去 ——
那是个把整件事做反了的实现，也一样能通过"小于等于 5"这条断言。

**六路各投 2 次 → 6 轮** 这条守住的是"六路共用一份去重窗口"。要是每路各有一
份窗口，同一件事从两路来就会开两轮 —— 那个数会变成 12。

**时间**（本机）：

| 一路 | 耗时 | 说明 |
| --- | --- | --- |
| 定时（扫一遍试点仓库） | 0.3 ms | 读索引，不读仓库 |
| 代码（`git log` 5 条） | 15.7 ms | 起子进程 |
| 质量（真跑一遍 pytest） | 358.0 ms | 起子进程，跑 9 条复现用例 |
| 运行（真跑一次 CLI） | 37.7 ms | 起子进程 |
| 外部（读台账） | 0.2 ms | 读一个文件 |
| 知识（读 ADR） | 0.2 ms | 读一个目录 |

**质量那一路慢了三个数量级 —— 所以它不能待在请求路径上。** 它得在后台跑，
或者挂在 CI 上；这也是为什么它默认带一个 120 秒的超时上限。

## 6. "没跑成"与"没有"是两件事

本仓库的老规矩：**缺实测值是失败，不是 0。**

**质量那一路如果 pytest 跑不起来（退出码 2/3/4/5），它抛错，不返回空。**
返回空等于把一个跑不起来的测试套件报成"没有用例没过" —— 一个假结论比一个
报错危险得多，因为假结论没人会去查。错误信息里写着"没跑成"，跟"没有失败"
是两种字。

**运行那一路反过来：跑不起来就是事故。** 命令起不来、超时、退出码非零，
三种都产出一个事故事件 —— 因为"没跑成"本身就是运行时的问题。

**同一件事，六个源有六种不同的处理方式，这是对的。** 台账格式变了要跳过，
pytest 跑不起来要报错，CLI 崩了要报事故 —— 差别不在实现，在**这件事的性质**。

## 7. 没测的，和已知的不足

**没测的：**

- **没有接上真正的调度器。** 六路源都在，但"谁在什么时候调用 `collect()`"
  这一段没做 —— 那属于阶段三的编排（TASK-P3-010 Temporal）。
- **没有落库。** 去重窗口、回环链、熔断计数都只在内存里；周期记录由循环 B
  那边写。真正跑起来的时候这三样都要落库，与周期记录放在一起。
- **没有真实项目的基线。** 上面那些数字全部来自 `samples/pilot_repo` ——
  那是一个**刻意做小**的试点仓库。真实仓库上六路的产出比例是多少（提交多的
  仓库和文档多的仓库完全不是一回事）**没测过**。
- **没有测并发。** 派发是 `async` 的，但**同一时刻两个派发撞上同一个事件**
  会怎样，没测过。内存版的去重窗口是原子的（claim 一次），换成落库版还要
  再看一遍。

**已知的不足（不是设计，是缺口）：**

- **去重窗口只活在内存里。** 进程重启，窗口就空了 —— 重启后第一件事会被当
  成新事件再开一轮。已在 `build_router` 的文档里写明。
- **知识那一路只接了决策记录（ADR）。** 设计文档里知识事件写的是"依赖漏洞、
  技术升级" —— 依赖漏洞扫描是同一类事的另一种来源，要接进来只要再写一个适
  配器。**这一层不假装自己接了它。**
- **代码那一路只看提交，不看 PR 与分支。** `git log` 读的是一条直线的历史；
  真实项目里"PR 合入"才是那个语义上的事件。
- **外部那一路的台账格式是定死的**（`### <ID> —— <标题>`）。人写的格式一旦
  变了，这一路就会安静地什么都不产出 —— 而"什么都没产出"跟"没有反馈"长得很
  一样。
- **六路的事件体量差别很大。** 一次提交就是一个事件，一条提交记录就是 20 个
  事件 —— 但它们都只开一轮，因为主体标识各不相同。**这一点是对的**，但也要
  意识到：一次批量导入会在几秒内开 20 轮。

## 8. 与设计要求的关系

| 要求 | 落在哪 |
| --- | --- |
| R-079 六种事件触发源 | `apps/triggers/sources.py`：六路源各读各的真的东西 |
| R-080 定期扫描与事件触发结合 | 定时那一路复用 `apps/scheduler/scan_job.py` 的 `fresh_signals` —— **"什么算新问题"只有一处知道** |
| I-11 事件回环 | `orchestration/triggers.py`：回环判定在去重之前，被回环挡住的事件不占去重窗口 |
| R-029 证据必须可独立核验 | 每条事件带**主体标识** —— 提交 sha、用例 node id、报告条目 id，拿着就能去查 |
| R-033 假设要能被事后比 | 周期记录里存的是**触发源**（`code` / `quality` / …），事后能分得出哪类触发带来了哪些收益 |
| R-028 候选要有真实证据 | 事件的 `summary` 带着真的内容（退出码、异常、提交标题、缺陷标题） |
