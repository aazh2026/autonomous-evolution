# 断点恢复 —— 一本步骤账，一个外部证人

设计依据：`docs/tasks.md` TASK-P3-016（交付物：进程重启 / 机器重启后从检查点
恢复；验收条件"在执行中强杀进程，重启后任务状态可恢复且不重复执行已完成的副
作用"；验证 T1）、R-091（重试 / 超时 / 恢复机制）、R-095（中断后可恢复或重新
执行）、R-099（验收证据不因下一轮丢失）。

> **代码库里已经有两样东西看起来像答案。**
>
> 一是 `core/task/state_machine.py` 里那条"幂等重投是空操作"的规则 —— 它保护
> 的是**状态迁移**，不是**迁移之前那个副作用**。重投一次 `START`，状态机不会
> 报错，但工作区会被重新开一次、会话会被重新开一次、代码会被再提交一次。
>
> 二是 `executors/base.py` 里的幂等键 `task_id:attempt` —— 键算出来了，但**从
> 来没有落库，也从来没有被当作查询条件用过**。它只是一串被写进事件载荷里的
> 字符串。
>
> 于是"重复执行已完成的副作用"这件事，今天**没有任何机制挡着**。

## 0. 一句话

**先记"我要做这一步"，再做，做完记"做完了"；重启之后先问账本，做完了就跳过，
结果未知就去问外部世界，问不出来就停下来。**

最后那半句是这一层的全部难点，也是它与"加个 try/except 重跑一遍"的全部差别。

## 1. 三层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 契约 | `core/task/resume.py` | 步骤账、三档状态、四档答复、探测三档 | 不知道怎么把流程跑起来 |
| 编排 | `orchestration/resume.py` | 拿到答复之后该干什么 | 不知道账存在哪儿 |
| 落库 | `infrastructure/database/step_effect.py` | 每次写自己提交 | 不判断状态 |

**"账"留在 `core/`，"怎么用"留在 `orchestration/`。** 账的语义是领域逻辑；一轮
怎么跑是编排的事 —— **两者混在一起，就没人能单独验"账的语义对不对"**。

**`orchestration/` 不导入 `apps/`，`core/` 不导入 `executors/`。** 这一层与
其它层一样守这条线：它是编排的机制，不是业务。

## 2. 三档状态，不是一档"做完 / 没做完"

| 状态 | 意思 | 恢复时怎么办 |
| --- | --- | --- |
| `started` | 副作用开始了，**还不知道做完没有** | **去问外部世界** |
| `done` | 副作用做完了 | **跳过** |
| `failed` | 尝试过，明确失败了 —— 副作用没有生效 | **可以重跑** |

**中间那档才是断点恢复真正要处理的情况。** 进程被强杀，可能停在副作用的任意
位置：

- 停在副作用**之前** —— 没做，重做。
- 停在副作用**之后、记录之前** —— **做了，但没记上**。
- 停在记录**之后** —— 做了，也记上了。

第二种与第一种**在账本里长得一模一样**（都是"开始了，没有完成记录"）。把它并
进"没做完"，重启之后就会把已经做完的事**再做一遍**；把它并进"做完了"，就会
漏掉没做完的事。

**所以"完成了"这一条记录必须比副作用晚一步 —— 早一步它就是一句谎话。**

## 3. 四档答复，不是"能跑 / 不能跑"

要跑一步时，账本给出四种答复之一：

| 答复 | 意思 | 执行器该做什么 |
| --- | --- | --- |
| `ACQUIRED` | 拿到了 | **干活** |
| `ALREADY_DONE` | 已经做完了 | **跳过** |
| `IN_PROGRESS` | 别人正在做（租约还活着） | **停** —— 别碰 |
| `NEEDS_PROBE` | 上一个执行者不见了，结果未知 | **去问外部世界** |

**"不能跑"至少有两种完全不同的原因。** "已经做完了"（跳过，正是我们要的）与
"别人正在做"（等着）如果被混成一句话，副作用就会被重复执行 —— 那正是这一层
要防的事。

**理由是必需品。** `StepClaimResult.reason` 带着一句"为什么"，因为"不能跑"和
"别人在跑"要采取的后续动作完全不同，而调用方只有拿到理由才知道该等还是该停。

## 4. 租约 —— "有人在管"与"人没了"的分界

`lease_until` 把两件事分开：

- **租约还活着** —— 有人正在做这一步。别碰。
- **租约过期了** —— 上一个执行者不见了（被强杀了）。**结果未知，去问。**

**没有租约，一次崩溃就等于这个任务永久停住。** 被强杀的那一步会永远卡在"别人
正在做"，谁也不敢碰 —— 而"不敢碰"和"不该碰"不一样：前者是系统瘫了。

**租约也要跟着接管一起续。** 接管之后这一步就是"我在做"，租约必须重新算 ——
否则刚接管的这一步会立刻被下一个执行者当成"上个执行者死了"。

## 5. 账本的键 —— `(task_id, step)`，不带 attempt

**一个任务里的同一个步骤，副作用最多发生一次。** 重试的是**同一件事**，不是
另一件事。

把 `attempt` 放进唯一约束，就等于允许同一个副作用发生两次 —— 那正是这张表要
防的事。`attempt` 照样记（它是"这是第几次"的事实），只是**不参与身份**。

**它与执行器的幂等键不是一回事。**

| 键 | 形式 | 区分的是 |
| --- | --- | --- |
| 执行器幂等键 | `task_id:attempt` | 同一次任务的**不同尝试** |
| 步骤账的键 | `task_id:step` | 同一个任务的**不同步骤** |

两个键各有各的用处，混用会丢掉其中一个的语义。

## 6. 探测 —— 三档，第三档最重要

账本只能回答"有人开始过、没写完成"，它**答不了**"到底做完没有"。那要问外部
世界：

```python
async def _probe_commit() -> ProbeOutcome:
    if _has_effect_commit(repo):      # git log 里有没有那个提交
        return ProbeOutcome.COMPLETED
    return ProbeOutcome.NOT_COMPLETED
```

| 探测的回答 | 意思 | 执行器该做什么 |
| --- | --- | --- |
| `COMPLETED` | 副作用生效了 | **别做** —— 记完成，跳过 |
| `NOT_COMPLETED` | 副作用没生效 | **接管，重做一次** |
| `UNKNOWN` | **问不出来** | **停下来** |

**"问不出来"是一档，不是布尔值。** 硬把它当成"没发生"就会重复执行副作用，硬
把它当成"发生了"就会漏掉一件事。**两种猜法都是错的**，所以唯一正确的动作是
停。

**"停下来"不是失败，是正确。** 停下来之后，账本上留着"这一步结果未知"，人
（或下一轮带着更强探测能力的执行器）可以接手。**而猜错了的代价是把一件已经
发生过的事又发生一次。**

**没有探测的步骤在结果未知时只能停。** 账本答不了"做完没有"，硬猜就是重复执行
或漏执行。

## 7. 数据库层的三道拒绝

应用层的"请记得检查"可以被绕开（脚本、手工 SQL）。数据库层的不会。

| 触发器 | 拒绝什么 | 为什么 |
| --- | --- | --- |
| `trg_task_step_effect_done_irreversible` | 把 `done` 改成别的状态 | 把一件已经发生过的事说成没发生过，恢复时就会**再做一遍** |
| `trg_task_step_effect_append_only_delete` | DELETE | 抹掉之后"这一步到底跑过没有"就没人能回答了 |
| `trg_task_step_effect_append_only_truncate` | TRUNCATE | 同上 |

外加两个 CHECK：`attempt >= 1`、`status IN ('started','done','failed')`。

**"完成"先到先得。** 更新语句的 `WHERE` 里带着 `status <> 'done'`，所以迟到的
完成记录改不动已经完成的那一条；而数据库层的守卫连手工改库都堵住了。

**"迟到的失败不能把完成 undo 掉。"** 两个执行者跑同一步时，可能一个先成功、
另一个后失败 —— **先成功的那个是真的**。把完成改成失败，等于把一件已经发生过
的事说成没发生过。

## 8. 每次写都自己提交

`PostgresStepEffectLedger` 的每一次写都开自己的事务、**自己提交**。

这一点与 `PostgresBudgetLedger` 同一个理由，但结论相反：预算扣减要**先于**业务
事务生效（钱已经花了），而步骤账必须**活过**业务事务 —— 记完成的那一次提交，
就是"这一步做完了"这件事变成事实的那一刻。

**不提交就没有断点。** 重启之后账本会说"这一步没做完"，而它其实做完了。

## 9. 怎么用

```python
from infrastructure.database.step_effect import PostgresStepEffectLedger
from orchestration.resume import ResumableStepRunner, Step

ledger = PostgresStepEffectLedger(session_factory, lease_seconds=60)
runner = ResumableStepRunner(ledger, attempt=attempt)

report = await runner.run(task_id, [
    Step(name="commit", run=_commit, probe=_probe_commit),
    Step(name="publish", run=_publish, probe=_probe_publish),
])

if report.halted:
    ...  # 停住了 —— 看 report.halted_step 与那一步的 detail
```

**中断了就别往下走。** `run()` 遇到停住的那一步就 `break` —— 停下来的理由是
"结果问不出来"或"别人正在做"，这两种情况下继续跑后面的步骤，就是在**不确定
的地基上继续盖房子**。

**失败会原样抛出去。** 账本上记一条 `failed`，然后把异常交给调用方 —— 因为"哪
一步失败了、为什么失败"是调用方要处理的，而吞掉异常会让它变成"这个任务莫名其
妙地停了"。**账本记状态，异常带原因。**

## 10. 怎么验 —— 三个杀点，一个外部证人

`tests/integration/test_resume_after_kill.py` 跑的是**真东西**：真的 PostgreSQL、
真的 git 仓库、真的 `SIGKILL`（子进程自己朝自己开枪）。

**证人是 git 自己的提交历史。** 系统自己的报告说"我跳过了这一步"，那验的是
"执行器与执行器自己的报告一致" —— 恰恰是最需要防的那种自证。git 不知道有什
么步骤账，它只知道仓库里有没有那个提交。**提交只有一条，才是真的没有重复执
行。**

| 杀点 | 副作用做了吗 | 记录写了吗 | 重启后该做什么 |
| --- | --- | --- | --- |
| `commit:before` | 没有 | 没有（只有"开始了"） | **补做一次** |
| `commit:after` | **做了** | **没有** | **别做** —— 探测认出来就跳过 |
| `publish:before` | 上一步做了 | 上一步写了 | **跳过上一步**，补做这一步 |

**杀点是确定的，所以那个最难复现的窗口必然被复现**，而不是"碰运气撞上"。

**用 `SIGKILL` 而不是 `SIGTERM`。** `SIGTERM` 可以被捕获 —— 生产代码里通常有
清理逻辑，于是"被杀"变成了"有序退出"，而**有序退出会把状态收拾干净**：那正是
断点恢复要处理的场景里**不会发生**的事。

**还有一个用例跑两个执行者。** 第一个占着这一步不放，第二个来了只能停 ——
**两个执行者同时做同一件事，重复执行就不只是"多了一次提交"**，而是两个执行者
拿到了两份互相打架的状态。
