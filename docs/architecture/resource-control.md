# 预算与资源控制 —— 一本账、一道准入门、一个信号量

设计依据：`docs/tasks.md` TASK-P3-015（交付物：跨周期预算、成本归集、并发限流；
验收条件"连续运行期间每日成本不超过 `max_daily_cost`；超限时优雅停止而非崩
溃"；验证 T1 + T2）、R-013（Budget 含日成本与并发上限，可配）、R-018（Budget 管
Token / 调用 / 资源 / 时间）、TASK-P1-012（预算账本与原子扣减）、TASK-P2-013
（并行执行引擎）、TASK-P3-018（连续 10 周期长跑的前置件）、`docs/design.md`
§3.1（Budget Manager）。

> **P1-012 把账本做对了，但没有回答"预算约束了谁"。**
>
> `BudgetManager` 管的是"**一个作用域**的账"。而演进是**一个接一个的周期** ——
> 于是"每个周期各建一个 BudgetManager"这件事看上去像无害的写法，实际效果是
> **每个周期都有一份日预算**。跑十轮，账面上的日成本是十份上限。
>
> **上限还能不能被叫做上限，取决于一共有多少本账。**

## 0. 一句话

**所有周期记同一本账；开跑之前先问一句"今天还能跑吗"；撞过墙就停下来，把原因
写进结论里；并发只有一个数，谁用谁从同一个闸门拿号牌。**

前半句与后半句是一件事的两面：**没有一本账，就不知道该不该停；没有一道准入门，
就永远停不下来。**

## 1. 三层，各管各的

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 契约 | `core/policy/budget.py`（P1-012） | 预算、账本、原子扣减、周期键 | 不知道"周期"是什么 |
| 契约 | `core/policy/resource.py` | 闸门、准入门、并发闸门、成本归集 | 不知道怎么把周期跑起来 |
| 编排 | `orchestration/continuous.py` | 一轮接一轮地跑，撞墙就优雅停止 | 不判断能不能开跑 |
| 编排 | `orchestration/parallel_runner.py` | 用共享闸门跑并发任务 | 不管钱 |

**"预算"留在 `core/`，"怎么跑"留在 `orchestration/`。** 预算怎么算是领域逻辑；
一轮接一轮怎么跑是编排的事 —— **两者混在一起，就没人能单独验"钱算对没有"。**

**闸门是唯一的入口。** 同一笔钱从两条路记进来，审计时就得先分辨哪一遍才是真
的 —— 所以跨周期这条路走 `ResourceGate.charge`；执行器那一层的单次记账
（`orchestration/cost_accounting.py`）记的是它自己的账，**两条路别同时用同一
笔钱**。

## 2. 第一件事：一本账

账本的主键是 `(scope, metric, period)`。**周期不是账本的概念，是作用域的概念
** —— 换句话说，"记在哪本账上"这件事一旦定下来，跨周期预算就成立了。

`ResourceGate` 持有一个 `BudgetManager`，**所有周期都往它记**：

```python
gate = ResourceGate(Budget(max_daily_cost=Decimal("5")), scope="pilot")
for cycle_id in ("cycle-1", "cycle-2", ...):
    await gate.charge(ResourceUsage(cost=...), cycle_id=cycle_id)
```

**"每个周期各建一个 manager" 这条路的代价是量出来的：**

| 写法 | 六轮各花 5 块、上限 5 块 | 账面日成本 |
| --- | --- | --- |
| 每轮一个 `BudgetManager`（六本账） | 六轮全部成功 | **30**（上限的 6 倍） |
| 一个 `ResourceGate`（一本账） | 第 2 轮起被拒 | **5** |

**上限被架空成六倍，而不是"差一点"。** 这条差别就是这一层存在的全部价值
（`tests/unit/policy/test_resource.py` 里那条叫
`test_a_budget_per_cycle_would_have_been_six_books` 的用例就是钉这件事的）。

**作用域是账本的主键，不是对象的属性。** 两个 `ResourceGate` 对象，只要
`scope` 相同，在数据库账本上就是**同一行账户** —— 这正是跨进程时预算仍然成
立的原因（`tests/integration/test_resource_gate_concurrency.py` 里两个不同对
象、同一个 scope，第二个读到的就是第一个花掉的钱）。

## 3. 第二件事：撞过墙就别再开新周期

**这是这一层最容易被漏掉、也最要紧的一条。**

账本的原子扣减只保证"**记进去的**总额不超上限" —— 它管不了"这一轮该不该开
跑"。撞墙的那一笔**没有记进累计额**（累计额只增不减，拦下来的钱不算花出去），
于是：

> 余额 90 / 100 —— **看着还有余量。**

只看余额，系统会再开一轮、再撞一次、再撞一次。**每一天都撞一次，直到有人在别
处看见日志。**

所以准入门 `admit()` 有**两个**检查：

| 检查 | 问的是 | 挡住什么 |
| --- | --- | --- |
| 一 | 累计额 ≥ 上限了吗 | 余额真的用完了 |
| 二 | **今天撞过一次了吗**（读流水里的被拒记录） | 余额还剩着，但今天已经撞过墙 |

**第二个检查才是"跨周期"三个字真正的落点** —— 而它必须读**流水**，不能读余
额。

实测（真实数据库，10 个并发周期，每次 15 块，上限 100）：

| 量 | 值 |
| --- | --- |
| 记进账的 | **90**（6 次成功） |
| 被拒的流水 | **4** 条，**都在库里** |
| `daily_spend()` | **90 / 100 —— 还有余量** |
| `admit()` | **不放行** —— "daily_cost 今天已经撞过一次上限（90 / 100）" |

**被拒的流水不是垃圾，是"今天到头了"的证据。** 账本不许删除（append-only 是数
据库触发器强制的），所以这条证据天然活得下来 —— 而准入门就是靠它做判断的。

## 4. 第三件事：停止是结论，不是异常

**撞墙时抛 `BudgetExhausted` 会把整个进程掀掉** —— 正在跑的东西没了，跑完的
东西也没了。而"我们花到上限了"这件事本身就该被记下来。

所以停止的形状是**一个值**：

```python
ContinuousRun(
    cycles=("cycle-1", ..., "cycle-5"),
    stopped=True,
    reason="daily_cost 已经用满（5.000000 / 5）—— 不再开新周期",
    total=Decimal("5"),
    blocked=False,
)
```

**理由里带维度、带已花、带上限** —— 补救动作各不相同（改预算？改优先级？等明
天？），只说"不行"的话，调用方什么也做不了。

**周期词汇表里早有这一档。** `core/metrics/cycle.py` 的 `CycleStatus.BUDGET_
EXHAUSTED` 是"跑完了但没变好"，outcome 是 `stalled`。**被预算掐断的周期确实跑
完了 —— 它跑完了，只是没变好。**

## 5. 并发只有一个数

上限写在 `Budget.max_parallel_agents` 里，但**每个引擎各建各的信号量** —— 两
批任务同时跑，limit 就翻倍了。**上限只在单批里成立，等于没有上限。**

现在引擎持有**一个** `ConcurrencyLimiter`（默认由预算建出来，也可以注入
`ResourceGate` 手里那一个）：

| | 早先 | 现在 |
| --- | --- | --- |
| 信号量 | 每次 `run()` 现造一个 | 引擎持有，跨批次共享 |
| 注入闸门 | 注入不了（参数不存在） | `limiter=` 或 `gate.limiter` 都行 |
| "现在跑着几个" | 引擎自己数一遍 | **就是闸门那个数**（一个出处） |

**实测（把共享闸门换回"每批现造"）：**

| 场景 | 上限 | 早先的峰值 | 现在 |
| --- | --- | --- | --- |
| 两批同时跑 | 3 | **6**（两倍） | ≤ 3 |
| 两个引擎共用一个闸门 | 3 | **8**（闸门形同虚设） | ≤ 3 |
| 注入闸门手里那一个 | 2 | **8** | ≤ 2 |

**证据是独立的仪表。** 断言用的是任务自己数的"同时跑着几个"，不是引擎报出来的
数 —— **用被测对象自己的读数证明被测对象，是循环论证。**

## 6. 三条不通的路，和一条要说明白的限制

| 情况 | 结论 | 记的是什么 |
| --- | --- | --- |
| 一轮花超了上限 | **这一笔不记进累计额**，但留一条"被拒绝"的流水 | "我们想花超了" |
| 撞过墙之后再开新周期 | **不放行** | "今天已经撞过一次上限" |
| 换了作用域 | **换了一本账** —— 跨周期预算在那个作用域上不成立 | 新账从零开始 |

**要说清楚的一条限制：上限拦的是记账，不是时间机器。**

这一轮的钱**已经花掉了**，拦是拦不回来的 —— 模型调用发出去了，token 已经用
了。能拦的只有三件事：

1. **不把它记成正常花销**（累计额因此不超上限）；
2. **不再开新周期**（"今天到头了"）；
3. **留下被拒的流水**（差额因此查得出来）。

**所以账上的数不会超，而真实的花费可能超** —— 那个差额就是那条"被拒绝"的流
水。**把账说成"实际花了多少"，就是在说一个查不出来的谎。**

## 7. 实测：T2

**验收条件：连续运行期间每日成本不超过 `max_daily_cost`；超限时优雅停止而非崩
溃。**

### 7.1 连续运行（内存账本）

| 量 | 值 |
| --- | --- |
| 上限 | 5 块 / 天 |
| 允许的轮数 | 20 |
| 实际跑了几轮 | **5** |
| 停在第几轮 | 第 6 轮开跑之前 —— 准入门不放行 |
| 账上的日成本 | **5.000000**（= 上限，不超） |
| 停止的形状 | 一个结论（`stopped=True` + 理由），**没有异常** |
| 耗时 | **0.24 ms**（5 轮，含 5 次准入 + 5 次记账） |

### 7.2 真实数据库 + 真实并发

10 个并发周期，各 15 块，上限 100（`tests/integration/`）：

| 量 | 值 |
| --- | --- |
| 记进账的 | **90**（6 次成功） |
| 被拒的流水 | **4** 条，**落在库里** |
| 数据库 `budget_account.spent` | **90** —— 上限住在数据里 |
| 不变量 | 累计额 ≤ 上限，且累计额 = 成功次数 × 单次金额 |
| 撞墙后 `admit()` | **不放行**，尽管余额还有 10 块的余量 |

**"数据库里的累计额也不超限"是单独查库验的** —— 不是只有闸门记得。**只靠应用
层判断的预算，绕过应用层就没了。**

### 7.4 日切

**日切不需要删任何记录。** `period_key` 把 `daily_cost` 按自然日分窗口，新的一
天是新的一行累计额，累计额从零开始 —— 这对 append-only 的账本很关键（账本不
允许删除，日切就不能靠删除实现）。

实测：上限 1 块，第一轮花掉 1 块 → 当天不再放行；**时钟拨到第二天 → 放行，
当天的累计额是 0**。

## 8. 没测的，和已知的不足

**没测的：**

- **没有跑过真的连续 10 周期。** TASK-P3-018 那个长跑是这里的前置件；**这一层
  只验了"跑多少轮就停"，没验"跑十轮之后系统还是不是好的"**。
- **没有真的超预算过。** 上面的"撞墙"都是构造出来的（让一轮花 9 块、上限 5
  块）。**真实系统里钱是怎么花超的，没量过** —— 而那正是"要不要在开跑之前
  先看一眼余额"这个决定的关键依据。
- **没有测过多个进程各持一个闸门的场景。** 数据库账本保证了跨进程的原子扣减
  （P1-012 已验），**但"跨进程各自跑各自的准入门"没有验过** —— 两个进程可能
  同时看到"还有余额"然后同时开跑。**闸门不是分布式锁**，这一条是已知的缺口。
- **没有测规模。** 一千轮连续跑要多久、账本会不会长到查不动，**没测过**。
- **没有测过成本归集的准确性。** "这一轮花了多少"目前是闸门在内存里累加的数
  （`_cycle_spend`），**没有跟账本对账** —— 而两处都记了同一笔钱。

**已知的不足（不是设计，是缺口）：**

- **上限拦的是记账，不是时间机器。** 见 §6 —— 这是事实，不是缺陷，但它决定
  了"账面不超"不等于"实际没超"。
- **周期归属只在内存里。** `cycle_spend` 记在闸门对象上，**进程一退就没了**。
  账本里那笔钱是按 `(scope, metric, period)` 记的，**没有"哪一轮"这一维**。
  **"这一轮花了多少"在跨进程时答不出来。**
- **准入门不是分布式锁。** 见上面"没测的"那一条 —— 跨进程时它只能给出"建议
  不要开跑"，给不出"保证只有一个进程在跑"。
- **准入门每次都要扫流水。** 账本没有"按周期查"的接口，所以"今天撞过没有"
  这个判断要把**这个维度在这个作用域下的全部流水**拉回来再过滤。**流水长到
  几万条之后这一步会变慢** —— 那时要往账本上加"按周期查"的口子，而不是在这
  里硬扛。**现在是每个维度各查一次，而不是一次查全部。**
- **"撞过墙"是按天判的。** 第二条检查按 `period_key` 找当天的被拒流水；**撞过
  墙之后当天就全停了** —— 即便余额还剩很多。**这是有意为之**（免得一轮一轮
  地撞），但**它比"余额用完"严格得多**，值得知道。
- **并发限流只在进程内。** `ConcurrencyLimiter` 是 asyncio 信号量，**跨进程无
 效** —— 两个进程各限各的。**R-013 说的"并发上限"今天只在单进程里成立。**
- **归集与记账有两条路。** `orchestration/cost_accounting.py` 记执行器那侧的
  单次成本，`ResourceGate` 记跨周期那一侧。**两处都在，就有两本账** —— 眼下靠
  约定不共用同一笔钱，**没有结构上的保证**。
- **没有接进 Director 的决策链。** 预算撞墙现在是编排层自己停，**Director 那边
  不知道发生了什么**，也就没法"申请追加预算"或者"换个优先级"。
