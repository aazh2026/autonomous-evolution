# 多项目管理 —— 两个项目并行演进，互不串扰

设计依据：`docs/tasks.md` TASK-P4-010（交付物"Project Registry 完整化、项目隔离"；
验收条件"两个项目并行演进，任务 / 候选 / 决策互不串扰；**预算分别核算**"；验证
T1 + T2）、R-016（Project Registry 管多项目）、R-102（不得自主修改控制自身的系
统）、`docs/design.md` §3.1（Project Registry 管多项目及其仓库、环境和技术栈；
Budget Manager 管 Token / 模型调用 / 计算资源和时间预算）、§7（治理策略变更需审批，
系统不得自主修改治理策略）。

> **单项目下，串扰是看不见的。**
>
> 三个阶段都是"一个项目"，所以一条"按 id 取任务"的路径在单项目下**看不出任何问
> 题** —— 取到的永远是那一条。等到有两个项目，串了也已经**记进库了**：候选照记、
> 决策照下、任务照派，只是全都记在了别人的账上。
>
> 更麻烦的是**串扰不会报错**。A 项目的候选被 B 项目读到，没有任何一层会喊"这是
> 别人的东西" —— 读到的人只会觉得"这条候选不错"。等发现的时候，账已经混了、代码
> 已经合错分支了。
>
> 所以隔离不能靠"记得别搞混"，得**构造出来就拦得住**。

## 0. 一句话

**作用域是值对象，不是字符串；按项目读要过滤，按 id 取要报错；治理变更必须带一
条成立的审批；预算的 scope 是项目自己，且扣减时以作用域为准。**

## 1. 缺口在哪："完整化"补的是哪一块

阶段一已经有 `core/project/registry.py` 的 `ProjectRegistry` —— 一个内存注册表，
接口按多项目设计；数据库里也早有 `project` 表与 `core.entities.Project.from_domain`
/ `to_domain`。缺的是**中间的持久化实现**。

| 缺什么 | 后果 |
| --- | --- |
| 没有"登记"的入口 | 各处自己 `session.add`，登记了什么没人说得清 |
| 没有"读"的路径 | 表里的项目读不回来 —— 库变成了只写的地方 |
| 没有"改"的路径 | **治理策略怎么改，没有一条带审计的路** |
| 没有"按项目取"的闸门 | 取到别人的候选 / 决策 / 任务，**不会报错** |
| 预算的 scope 没有项目维度 | 两个项目的钱记在同一个口径下 |

四层，各管各的：

| 层 | 文件 | 做什么 | 不做什么 |
| --- | --- | --- | --- |
| 领域 | `core/project/scope.py` | 作用域这个值本身 | 不碰数据库 |
| 数据 | `infrastructure/database/project_scope.py` | 按项目取候选 / 决策 / 任务 | 不知道什么叫"有效候选" |
| 注册表 | `infrastructure/database/projects.py` | 登记 / 读取 / 治理变更 | 不管预算 |
| 账本 | `infrastructure/database/project_budget.py` | 按项目分别核算 | 不重新实现记账 |

## 2. 作用域是值对象，不是字符串

`ProjectScope` 是个 frozen dataclass，构造时就把不合法的项目 id 拒掉：空白、前后
空白、内嵌空白、含冒号。

**为什么值得单独校验。** 作用域键是 `project:` + id 拼出来的。id 里带空白或冒
号，键就"人读得懂、机器解析不回来" —— 而解析不回来的键意味着**两个不同的作用域
可能算出同一个键**。那时隔离就是假的，而且**假得看不出来**：两个项目共用一行预算，
报表上只有一行，谁也看不出哪里不对。

**代价要说清楚。** 领域模型 `Project.id` 只要求非空，所以**带空白或冒号的项目 id
在作用域层被拒掉** —— 注册表装得下它，但它没法参与按项目核算的账。这是有意的取
舍：**宁可少支持一种 id，也不要一个算不清的账。**

**前缀不是装饰。** 账本的 scope 是自由文本列（`budget_account.scope`），里面可能
还有"全局"这类别的口径。裸 id 会跟它们撞在一起，撞了以后两个口径的钱混在一行
里，而那一行的数字从此不再代表任何东西。

## 3. 隔离闸门：按 id 取要报错

`ProjectRecords` 把"这一行属于哪个项目"变成**每次取行都要过的一道闸**。

| 场景 | 行为 | 为什么 |
| --- | --- | --- |
| 列表（按项目取候选 / 决策 / 任务） | **过滤** | 列表的语义本来就是"给我这个项目的东西" |
| 按 id 取一行 | **不属于这个项目就报错** | 调用方要的是**那一条**，不是"这个项目的候选" |

**为什么按 id 取不能报"查无此项"。** 那一行确实存在 —— 它在别的项目名下。把它报成
"不存在"，越权读就退化成了统计口径问题，而不是权限问题。所以分成两个错误：
`NotFoundError` 与 `ScopeViolationError`。

**数据库已经挡住了一半。** `evolution_candidate` / `evolution_decision` / `task`
三张表都对 `project.id` 有外键 —— 候选与决策一定挂在某个**已注册**的项目下，物理
上无法挂到不存在的项目上。这一层补的是另一半：**挂对了项目，不代表你有权按另一
个项目的身份去读它。**

## 4. 治理变更要审批

`PostgresProjectRegistry.replace()` 是改项目定义的**唯一**入口。它要求一条审批凭
据，并且**先查审批、后写库** —— 顺序反了的话，"审批查不到"与"写了一半"会同时发生，
而"写了一半"意味着治理策略已经被改过了，只差一张凭据。

凭据要**同时**满足四件事，缺一即拒：

| 条件 | 不满足时报什么 |
| --- | --- |
| 查得到这条审批记录 | `查不到审批记录` |
| 操作是 `modify_governance` | `这条审批批的是 X，不是治理变更` |
| 批的是**这个项目** | `这条审批批的是 Y，不是这个项目` |
| **现在还算数**（未决 / 被拒 / 过期都不算） | `这条审批现在的结论是 expired` |

**"现在还算数"直接复用审批层自己的规则。** "过期盖住批准""拒绝最优先"是
`core/policy/approval.py` 的 `outcome()` 定的 —— 注册表**不重新实现一遍**：两处各
判一次，迟早会有一处判错，而判错的方向是"放行了一次没人批过的治理变更"。

**查不到就报错，绝不"查不到就当有"。** 审计写入失败时必须**失败关闭**。

**登记不覆盖。** 重复登记**同样的**内容是幂等的（演示与长跑都会反复跑这条路
径）；**不一样的**内容直接报 `ProjectConflictError` —— 静默覆盖等于允许任何人把一
个项目的策略换成另一个项目的策略，且不留痕迹。要改就走 `replace`，那条路要求审批。

**`local_path` 不入库。** 它是**这台机器上的**路径：换一台机器它就没意义了，而把
它写进库里会让人以为"库里那个路径是权威的"。所以库里比的是"存下来的那些东西"，
而不是两份领域对象是否逐字段相等。

## 5. 预算分别核算

**"分别核算"不是"分两本账"。** 一本账、两条记录也行 —— 但那样"这个项目花了多
少"要靠人把流水按 scope 分组求和。求和是人做的，人会忘。所以**账本里每一行的
scope 就是项目的 scope**，而取数的那一层直接按项目给数。

| 机制 | 做法 | 挡住什么 |
| --- | --- | --- |
| scope 键 | `project:<id>` | 两个口径的钱混在一行 |
| 扣减以作用域为准 | 请求里的 scope **一律被覆盖** | 调用方填错项目 id，钱记到别人头上 |
| 上限跟着项目走 | `ProjectBudget(scope, budget, ledger)` | 甲的花光了乙也花不了 |
| 报表按项目出行 | `ProjectSpendReport.rows` | 只有总数、没有分项 |

**记错项目比记错数字更难发现。** 数字错了能对账，项目记错了，对出来的是"另一个项
目的钱" —— 而那一行流水看起来完全正常。

**周期是"按 metric 定的"，不是"按项目定的"。** 日成本按自然日重置，其余按生命周
期累计。账号行的主键是 `(scope, metric, period)`，scope 不同就是不同的行。

## 6. 实测

### 6.1 纯函数层（T1，20 条）

`tests/unit/project/test_scope.py` —— 作用域的口径：

- 键的形状（前缀、两个项目不撞键、能解析回项目）；
- **不合法的 id 一律拒掉**（空 / 纯空白 / 前后空白 / 内嵌空白 / 制表符 / 冒号）；
- 不认识的 scope 键**不还原**（还原会造出一个不存在的项目，而那个假项目会有一份
  自己的账）；
- 相等即"同一个项目"；作用域不可变。

### 6.2 真实数据库层（T2，32 条）

`tests/integration/test_multi_project.py` —— 真 PostgreSQL，两个项目**并行**跑完各
自的候选 → 决策 → 任务链路（`asyncio.gather`，两个会话各开各的事务）。

**注册表（6 条）**：两个项目能登记；重复登记幂等；内容不同报冲突且**不覆盖**；读
得回来（六要素 / 仓库 / 技术栈 / 环境）；不存在的项目报 `ProjectNotFoundError`。

**治理变更（8 条）**：没凭据 → `MissingApprovalError`；未表态 → 拒；已过期 → 拒；
批的是别的项目 → 拒；批的是别的操作 → 拒；查不到记录 → 拒；**每一条失败之后项目
定义一个字都不许变**；批了 → 放行，且**改 A 不动 B**。

**隔离（11 条）**：每个项目只看得到自己的候选 / 决策 / 任务；一批行不跨项目；三张
表的行数各为 2、各属一个项目；按 id 取别的东西 → `ScopeViolationError`；不存在的
id → `NotFoundError`（**与越权分开**）；库里有数据的项目 id 两个都在。

**预算（7 条）**：各花各的；账本里是**两行**；请求里的 scope 被覆盖；**甲的钱快花完
了乙照样能花**（额度各自）；超自己的上限报错；报表每项目一行（含"还剩多少"）；没花
过的项目在报表上是**一行 0**而不是查不到。

## 7. 没测的，和已知的不足

1. **没有真的跑两个项目的演进循环。** 这里验的是"两个项目的数据在同一个库里互不
   串扰"，不是"两个项目的演进循环同时跑"。后者要两个真实仓库、两套执行器，阶段
   四才有。
2. **没有跨进程的并发扣减测试。** 记账的并发原子性由 `TASK-P1-012` 的
   `tests/integration/test_budget_concurrency.py` 验（那一条验的是**同一个 scope**
   下的并发）；"两个 scope 同时扣"没有被单独压过 —— 逻辑上它们连的行都不同，但没
   测过就是没测过。
3. **`register` 的幂等比较是逐字段的。** 领域模型以后加字段，这段比较必须同步改 ——
   漏改的后果是"同一个项目两次登记报冲突"，而不是数据出错。**漏改会响**，所以能
   被发现。
4. **项目 id 的白名单比领域模型严。** 带空格 / 冒号的 id 注册得了，但用不了作用域。
   见 §2 的取舍说明。
5. **`replace` 覆盖了全部列，但 `policy` 列是 `goal.autonomy` 的副本** —— 两列在同
   一次替换里一起改，没有单独改 `policy` 的路径。这是有意的（`policy` 是审计副
   本），但也意味着**改 `policy` 必须改 `goal.autonomy`**。
6. **`ProjectScope` 只校验字符，不校验项目是否真的存在。** 作用域可以指向一个没登记
   的项目 —— 那笔账会记在一个不存在的项目名下。**账本层不查注册表**：那会让"先记
   账、后登记项目"这种合法的先后来不了。
7. **审批凭据用 `task_id` 装项目 id。** `approval_request` 表没有 `project_id` 列，
   而 `task_id` 没有外键 —— 所以治理审批把项目 id 放在 `task_id` 里。这是不加迁移
   的代价（见 §8）。
8. **没有验"注册表里只有一个项目"时的行为。** 单项目下这套闸门是空转的 —— 它不影
   响任何现有路径，但也没有被证明"单项目时不影响老行为"。

## 8. 为什么没加迁移

`budget_account.scope` 是自由文本列，不是项目外键；`approval_request` 没有
`project_id` 列。两个项目维度都**骑在现成的列上**：

- 预算：`scope` 用 `project:<id>` 这个带前缀的键 —— 与"全局"这类别的口径区分得开，
  且能解析回来。
- 审批：项目 id 装在 `task_id` 里（该列是 `varchar` 且**无外键**）。

**没有加 Alembic 迁移是有意的。** 阶段四还有 0010、0011……要加，而同一时刻另一个
工作树也在改这个仓库 —— 两边各加一个 head，`alembic upgrade head` 就会对谁都失
效。所以这一版**先不碰 schema**，把项目维度做在既有列上。

**代价要说清楚**：没有 `project_id` 外键，就没法用数据库约束"这个审批必须属于这个
项目" —— 那条检查现在在应用层（注册表查审批时比对）。**它仍然是失败关闭的**：查不
到就不改。
