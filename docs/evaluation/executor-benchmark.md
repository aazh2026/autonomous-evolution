## 一、这一页要回答什么

一句话：**同一条缺陷，同一段指令，换一个执行器，结果差多少？**

所以口径的全部功夫都花在**控制变量**上：

| 变量 | 口径 | 为什么必须这么定 |
| --- | --- | --- |
| 任务集 | 试点仓库 `known_issues/` 里登记的 9 条已知缺陷 | 任务集**从仓库里读出来**，不是写死一份清单 —— 缺陷修好了清单还在，那就成了在测一条已经不存在的缺陷 |
| 模型 | 四个执行器**全部**跑 MiniMax-M3 | 换了执行器就换了模型，比较测的是"模型 + 执行器"这一坨，说不清是谁的功劳 |
| 后端 | 同一家 API（`api.minimaxi.com`） | 同上 |
| 指令 | **逐字相同**的一段 | 指令是自变量。指令一变，比的就是"执行器 + 指令" |
| 验收 | **我们自己的** pytest，跑在一份干净副本上 | 验收不能交给被测方 —— 验收是尺子，尺子不能是选手 |
| 成本 | **一张价目表 × 各自的 token 数** | 见 §四 |
| 统计 | 精确检验（Fisher / 置换）+ Holm 校正 | 样本很小，正态近似不可信 |

**"跑过"和"跑过并通过"是两件事，"没跑成"和"跑过但没过"更是两件事。**
所有指标都是三态的：`已计算` / `无样本` / `基线缺失`。**"缺实测值"是失败，不是
0** —— 一个没装的执行器在看板上显示成"成功率 0"，那是在说它能力差。

## 二、任务集与验收

### 任务从哪来

`samples/pilot_repo/known_issues/test_known_issues.py` 里每条 `@pytest.mark.xfail(strict=True)`
用例就是一条任务。`strict=True` 意味着**修好了就算 XPASS**，XPASS 是失败 —— 所以
"修好了"这件事本身也要靠真跑一遍 pytest 才能确认，不是靠执行器自己说。

9 条缺陷覆盖了几类不同的修法：

| 编号 | 缺陷 | 考的是什么 |
| --- | --- | --- |
| PILOT-001 | 空输入时 CLI 抛未捕获的 ValueError | 边界检查 + 错误契约 |
| PILOT-002 | 百分位越界时 CLI 抛未捕获的 ValueError | 同上，换个入口 |
| PILOT-003 | `--slug` 与 `--limit` 同时给出时 `--limit` 被静默忽略 | 参数优先级 |
| PILOT-004 | main 遇非法参数抛 SystemExit，与"返回退出码"的契约不符 | 契约一致性 |
| PILOT-005 | Money 声称不可变，amount 却可以直接改 | 可变性封装 |
| PILOT-006 | `load_config` 接受空键 | 输入校验 |
| PILOT-007 | 重复键静默取最后一个 | 重复项策略 |
| PILOT-008 | 超长单词不被硬折行，行宽超过 width | 格式化边界 |
| PILOT-009 | 非正间隔在 `next_run` 里报错、在 `is_due` 里却静默返回 | 同一语义两处不一致 |

### 验收怎么算

每次运行都**拷贝一份干净的试点仓库**再让执行器动手，然后：

1. 跑目标用例 —— 必须从 xfail 变成 XPASS（真修好了）；
2. 跑仓库里既有的回归套件 —— 挂了就记"引入回归"；
3. 跑一遍**对照仓库** —— 检查它有没有去改验收文件（改了不起作用，但要看）。

**"改用例作弊"是防不住的，所以干脆不防** —— 验收跑的是我们留在干净副本里的那份，
执行器改的是它那份工作区。想作弊得先改到验收文件，而那不是它能改到的地方。

### 每条任务跑几次

**9 条任务 × 3 次 = 27 次运行 / 执行器。**

3 次不是拍脑袋定的，是**算出来的**：Fisher 精确检验在每组 n=3 的时候，双侧
p 值的最小可能值是 `2 / C(6,3) = 0.1` —— **比 0.05 大**。也就是说，n=3 时"显
著"在算术上就是不可能的，不管数据长什么样。所以要么把样本量提到 27 次（每组
27 个计数，最小 p = 2/C(54,27) ≈ 1e-15，够用了），要么就别谈显著性。

## 三、指标口径

看板上的每一列都对应一个 `MetricResult`，三态：

| 指标 | 定义 | 分母里有什么 |
| --- | --- | --- |
| 可用率 | 探针通过的运行数 / 全部运行数 | 全部 |
| 成功率 | 通过验收的运行数 / **跑成了的**运行数 | 跑成了的（**"没跑成"不进分母**） |
| 回归率 | 引入回归的运行数 / **跑成了且通过目标用例的**运行数 | 同上 |
| 成本中位数 | **统一价目表折算**（§四） | 跑成了的 |
| token 中位数 | 四类 token 之和 | 跑成了的 |
| 耗时中位数 | 墙钟秒数 | 跑成了的 |
| 工具自报成本 | 各 CLI 自己报的数 | **只记录，不比较**（§四） |
| 没跑成 | 计数字段 | —— |

**"没跑成"不进分母，是硬规定。** 把"没跑起来"算成失败，等于把"这个执行器在我
这儿没配好"说成"它能力差" —— 这两件事在选型时完全不同。

## 四、成本为什么不能直接比

### 实测出来的硬证据

同一段指令、同一个模型、同一份工作区，三个 CLI 各自报的成本：

| 执行器 | 自报成本 | 折算成本（统一价目表） | 倍数 |
| --- | --- | --- | --- |
| Claude Code | ~$0.104 | ~$0.011 | **9.4×** |
| OpenCode | $0.011 | ~$0.011 | 1× |

**Claude Code 把 MiniMax-M3 按 $5.007/M 输入价记账，OpenCode 按 $0.30/M** —— 同
一次调用，16 倍。**"自报成本"这一列在四个执行器之间没有任何可比性**：它量的是
"这个工具查了自己的价目表"，不是"这次调用花了多少"。

所以口径是：

> **成本 = 一张价目表 × 各自的 token 数。**

价目表（models.dev 的 `minimax/MiniMax-M3` 条目，2026-11-10 取值）：

| 项 | 单价（每百万 token） |
| --- | --- |
| 输入 | $0.30 |
| 输出 | $1.20 |
| 缓存读 | $0.06 |
| 缓存写 | $0.30（按输入价算，保守） |

**"工具自报成本"那一列仍然记着** —— 它不是没用，它是**记账口径差异的证据**，
将来某个工具的价目表算错了要回头查账，用得着。

### token 的记法也不一样

三个 CLI 的 token 语义**不一样**，不归一化就会把缓存算两遍钱：

| 执行器 | 输入 token 含不含缓存命中 |
| --- | --- |
| Claude Code | **不含** —— 缓存读/写在 `cache_read_input_tokens` / `cache_creation_input_tokens` 里单列 |
| OpenCode | **不含** —— `part.tokens.cache` 单列 |
| Codex | **含** —— `usage.input_tokens` 里已经包了 `cached_input_tokens` |

归一化成四个字段 `input / output / cache_read / cache_write`，Codex 的输入**要减
掉缓存命中**。少减一次，同一批 token 的成本会凭空多出一截。

**手算可验**：OpenCode 一次运行的 36825 输入 + 3 输出 + 128 缓存读 ——

```
36825×0.30/1e6 + 3×1.20/1e6 + 128×0.06/1e6
= 0.0110475 + 0.0000036 + 0.00000768
= 0.01105878
```

和它自己报的数字分毫不差 —— 这说明**折算口径是对的**，错的只是它查的价目表。

### "0 不是免费"

OpenCode 在没有登记价目表时会把成本报成 `0`。**记成 0，看板上就会冒出一条
"这个执行器便宜到离谱"的假差异** —— 那是记账口径的差别，不是能力差别。所以
**读到的 0 一律当作"没标价"**，该格显示"无样本"。

## 五、统计怎么做

**没有 scipy。** 依赖越少，结论越不会被"某个库的版本变了"污染；而 Fisher 精确
检验的数学只需要一行组合数。

- **成功率** → Fisher 精确检验。2×2 表，双侧，按 Fisher 的定义把**所有**边际相
  同的表都算一遍取概率之和，不是"双尾各半"。
- **成本、耗时** → 中位数的**置换检验**。把两组的数混在一起重新分组，看观测
  到的差距有多少种分法排得上。样本够小（组合数 ≤ 200000）就**精确枚举**，否则
  蒙特卡洛（种子固定，+1 修正）。**方法名会写明是哪一种** —— 把蒙特卡洛说成
  "精确检验"就是在骗人。
- **多重比较** → **Holm 校正**。四个执行器两两比是 6 对，四项指标就是 24 次检
  验；不校正的话，"至少有一次显著"几乎必然发生（1 − 0.95²⁴ ≈ 70%）。

**为什么用中位数不用均值**：一次卡死的运行能把均值拖走一大截，而中位数不受影
响；而且这批数据的分布形状**没法验证**（n 太小），正态前提无从谈起。

**为什么用精确检验不用卡方**：卡方近似在期望频数小于 5 时失效得很难看 ——
"9 个任务跑 3 次"正好落在这个区间里。

## 六、环境抖了怎么办

**后端不是永远在线的。** 第一次全量跑（2026-11-10 03:34 起）正好撞上 MiniMax
的限流：Claude Code 连续 27 次返回 API 层错误，Codex 的探针直接吃到一句
"We're currently experiencing high demand, which may cause temporary errors."
—— **54 次运行全部作废**。

那 54 条记录归档在
[`executor-benchmark-incident-2026-11-10.jsonl`](executor-benchmark-incident-2026-11-10.jsonl)。
它们没进看板 —— **那不是执行器的能力数据，是后端当时在抖**。

### 两件事因此改了口径

**一、原始输出要留着。** 那一轮只留了一句"执行器报错：（没有说清楚）"，所以
**分不清是限流、是能力差、还是参数不认** —— 只能靠再手跑一遍探针才定位到是
后端。现在每条记录都带一份脱敏后的原始输出（最多 4000 字，保留换行，**留尾
部** —— 报错通常在最后）。

**二、只对环境级故障重试。** 重试的是**后端自己的话** —— 限流、繁忙、暂时不
可用，外加后端自己报出来的 429/5xx：

| 情况 | 算不算环境问题 | 重试吗 |
| --- | --- | --- |
| 后端说"我忙不过来" / 429 / 5xx | 是 | **重试** |
| 超时（跑太久被掐了） | 否 | 不重试 |
| "模型没做对"（能力问题） | 否 | 不重试 |
| 认不出原因的环境错误 | 认不出 | **不重试** |

**超时不在重试之列，这是刻意的。** 超时是执行器自己跑得慢 —— 重试只会把"它
慢"盖成"它行"，而这次评测要量的恰恰是能力。**认不出原因就不重试** —— 宁可
少重试，也不要把能力差重试成通过。

**重试次数记在记录里，也摆在看板上。** 一个执行器次次都要重试才跑得通，那本
身就是结论 —— 藏起来，看板上就只剩一个干干净净的"成功率 90%"。

## 七、怎么跑

```bash
# 全量矩阵（9 任务 × 3 次 × 4 执行器）
.venv/bin/python -m scripts.run_executor_benchmark \
    --attempts 3 --timeout 420 --retries 2 \
    --log docs/evaluation/executor-benchmark-runs.jsonl \
    --board docs/evaluation/executor-benchmark-board.md

# 只重算看板，不重跑（结论要能被重新算一遍）
.venv/bin/python -m scripts.run_executor_benchmark \
    --render-only --log docs/evaluation/executor-benchmark-runs.jsonl
```

**探针在前面。** 一个执行器连"回答一个字 ok"都做不到（后端连不上、认证过期、
参数不认），就别急着跑 27 次真任务 —— 探针不过直接记"没跑成"，并把原因写进
原始记录。**探针超时就等于"它压根没起来"** —— 不管它有没有吐出过一个字，
让它接着跑 27 次真任务只会把同一个环境问题重复 27 遍，还烧 27 遍的钱。

**中断了可以接着跑。** 每跑完一次就往 JSONL 里追加一行；重跑时按
`(执行器, 任务, 次数)` 跳过已经记过的。

**凭证只从环境变量来**，配置文件里只写环境变量的**名字** —— 生成的 provider
配置不进版本库，`sk-` 一律脱敏。

### 三个执行器各自要什么

| 执行器 | 版本 | 怎么配 |
| --- | --- | --- |
| Claude Code | 2.1.158 | `--model MiniMax-M3`，走 `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` |
| Codex | 0.167.0 | 需要 `CODEX_HOME` 指向一份生成的 `config.toml`：`wire_api = "responses"`（`"chat"` 已不被支持），自定义 `model_providers` |
| OpenCode | 1.19.5 | 需要 `OPENCODE_CONFIG` 指向一份生成的 `opencode.json`：自定义 openai-compatible provider |
| Gemini CLI | 0.24.0 | **装得上也跑不通** —— 见 §八 |

## 九、这页没说的、也没敢说的

- **样本量。** 27 次/执行器，够Fisher 精确检验用，**不够**支撑"这个执行器一定
  更好"这种断言。看板能说的是"在 9 条缺陷 × 3 次这个规模上，差异有多大、是否
  显著"。
- **同一个模型。** 四个执行器跑的都是 MiniMax-M3。这是为了控制变量，但结论
  **不能外推**到别的模型 —— 执行器排名可能随模型而变。
- **任务集只有 9 条。** 覆盖了几类修法，但覆盖不了所有缺陷类型。
- **"没跑成"的执行器不参与两两比较。** 这不是漏算，是口径：它没跑成，说明的
  是"配不对"，不是"能力差"。但它也就没法参与显著性比较了。
- **成本口径有保底假设。** 缓存写按输入价算、缓存读按 $0.06/M 算 —— 换个
  价目表，成本的绝对值会变，**相对关系不一定变**。
