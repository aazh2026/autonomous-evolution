> 只是一句口号。

## 一、这一页要回答什么

一句话：**同一条缺陷，同一段指令，换一个执行器，结果差多少？**

所以口径的全部功夫都花在**控制变量**上：

| 变量 | 口径 | 为什么必须这么定 |
| --- | --- | --- |
| 任务集 | 试点仓库 `known_issues/` 里登记的 9 条已知缺陷 | 任务集**从仓库里读出来**，不是写死一份清单 —— 缺陷修好了清单还在，那就成了在测一条已经不存在的缺陷 |
| 模型 | 四个执行器**都指向** MiniMax-M3（gemini-cli 实际没跑起来，见 §八） | 换了执行器就换了模型，比较测的是"模型 + 执行器"这一坨，说不清是谁的功劳 |
| 后端 | 同一家 API（`api.minimaxi.com`） | 同上 |
| 指令 | **逐字相同**的一段 | 指令是自变量。指令一变，比的就是"执行器 + 指令" |
| 验收 | **我们自己的** pytest，跑在一份干净副本上 | 验收不能交给被测方 —— 验收是尺子，尺子不能是选手 |
| 成本 | **一张价目表 × 各自的 token 数** | 见 §四 |
| 统计 | 精确检验（Fisher / 置换）+ Holm 校正 | 样本很小，正态近似不可信 |

**"跑过"和"跑过并通过"是两件事，"没跑成"和"跑过但没过"更是两件事。**
所有指标都是三态的：`已计算` / `无样本` / `基线缺失`。**"缺实测值"是失败，不是
0** —— 一个没装的执行器在看板上显示成"成功率 0"，那是在说它能力差。

## 二、任务集与验收

### 任务从哪来

`samples/pilot_repo/known_issues/test_known_issues.py` 里每条 `@pytest.mark.xfail(strict=True)`
用例就是一条任务。`strict=True` 意味着**修好了就算 XPASS**，XPASS 是失败 —— 所以
"修好了"这件事本身也要靠真跑一遍 pytest 才能确认，不是靠执行器自己说。

9 条缺陷覆盖了几类不同的修法：

| 编号 | 缺陷 | 考的是什么 |
| --- | --- | --- |
| PILOT-001 | 空输入时 CLI 抛未捕获的 ValueError | 边界检查 + 错误契约 |
| PILOT-002 | 百分位越界时 CLI 抛未捕获的 ValueError | 同上，换个入口 |
| PILOT-003 | `--slug` 与 `--limit` 同时给出时 `--limit` 被静默忽略 | 参数优先级 |
| PILOT-004 | main 遇非法参数抛 SystemExit，与"返回退出码"的契约不符 | 契约一致性 |
| PILOT-005 | Money 声称不可变，amount 却可以直接改 | 可变性封装 |
| PILOT-006 | `load_config` 接受空键 | 输入校验 |
| PILOT-007 | 重复键静默取最后一个 | 重复项策略 |
| PILOT-008 | 超长单词不被硬折行，行宽超过 width | 格式化边界 |
| PILOT-009 | 非正间隔在 `next_run` 里报错、在 `is_due` 里却静默返回 | 同一语义两处不一致 |

### 验收怎么算

每次运行都**拷贝一份干净的试点仓库**再让执行器动手，然后：

1. 跑目标用例 —— 必须从 xfail 变成 XPASS（真修好了）；
2. 跑仓库里既有的回归套件 —— 挂了就记"引入回归"；
3. 跑一遍**对照仓库** —— 检查它有没有去改验收文件（改了不起作用，但要看）。

**"改用例作弊"是防不住的，所以干脆不防** —— 验收跑的是我们留在干净副本里的那份，
执行器改的是它那份工作区。想作弊得先改到验收文件，而那不是它能改到的地方。

### 每条任务跑几次

**9 条任务 × 3 次 = 27 次运行 / 执行器。**

3 次不是拍脑袋定的，是**算出来的**：Fisher 精确检验在每组 n=3 的时候，双侧
p 值的最小可能值是 `2 / C(6,3) = 0.1` —— **比 0.05 大**。也就是说，n=3 时"显
著"在算术上就是不可能的，不管数据长什么样。所以要么把样本量提到 27 次（每组
27 个计数，最小 p = 2/C(54,27) ≈ 1e-15，够用了），要么就别谈显著性。

## 三、指标口径

看板上的每一列都对应一个 `MetricResult`，三态：

| 指标 | 定义 | 分母里有什么 |
| --- | --- | --- |
| 可用率 | 探针通过的运行数 / 全部运行数 | 全部 |
| 成功率 | 通过验收的运行数 / **跑成了的**运行数 | 跑成了的（**"没跑成"不进分母**） |
| 回归率 | 引入回归的运行数 / **跑成了且通过目标用例的**运行数 | 同上 |
| 成本中位数 | **统一价目表折算**（§四） | 跑成了的 |
| token 中位数 | 四类 token 之和 | 跑成了的 |
| 耗时中位数 | 墙钟秒数 | 跑成了的 |
| 工具自报成本 | 各 CLI 自己报的数 | **只记录，不比较**（§四） |
| 没跑成 | 计数字段 | —— |

**"没跑成"不进分母，是硬规定。** 把"没跑起来"算成失败，等于把"这个执行器在我
这儿没配好"说成"它能力差" —— 这两件事在选型时完全不同。

## 四、成本为什么不能直接比

### 实测出来的硬证据

同一条缺陷、同一段指令、同一个模型、同一份工作区，27 次运行的中位数：

| 执行器 | 工具自报成本 | 折算成本（统一价目表） | 倍数 |
| --- | --- | --- | --- |
| Claude Code | $0.8812 | $0.0689 | **12.79×** |
| Codex | 无样本（不报） | $0.0454 | —— |
| OpenCode | 无样本（报 0 = 没标价） | $0.0345 | —— |

**Claude Code 把 MiniMax-M3 按 $5.007/M 输入价记账，厂商自己的表是 $0.30/M** ——
同一次调用，16 倍。**"自报成本"这一列在几个执行器之间没有任何可比性**：它量的是
"这个工具查了自己的价目表"，不是"这次调用花了多少"。

所以口径是：

> **成本 = 一张价目表 × 各自的 token 数。**

价目表（models.dev 的 `minimax/MiniMax-M3` 条目，2026-11-10 取值）：

| 项 | 单价（每百万 token） |
| --- | --- |
| 输入 | $0.30 |
| 输出 | $1.20 |
| 缓存读 | $0.06 |
| 缓存写 | $0.30（按输入价算，保守） |

**"工具自报成本"那一列仍然记着** —— 它不是没用，它是**记账口径差异的证据**，
将来某个工具的价目表算错了要回头查账，用得着。

### token 的记法也不一样

三个 CLI 的 token 语义**不一样**，不归一化就会把缓存算两遍钱：

| 执行器 | 输入 token 含不含缓存命中 |
| --- | --- |
| Claude Code | **不含** —— 缓存读/写在 `cache_read_input_tokens` / `cache_creation_input_tokens` 里单列 |
| OpenCode | **不含** —— `part.tokens.cache` 单列 |
| Codex | **含** —— `usage.input_tokens` 里已经包了 `cached_input_tokens` |

归一化成四个字段 `input / output / cache_read / cache_write`，Codex 的输入**要减
掉缓存命中**。少减一次，同一批 token 的成本会凭空多出一截。

**折算公式本身是可验的。** 拿 OpenCode 当时用另一个模型跑的一次单步会话做对
照 —— 它自己报 $0.01105878，按统一价目表手算：

```
36825×0.30/1e6 + 3×1.20/1e6 + 128×0.06/1e6
= 0.0110475 + 0.0000036 + 0.00000768
= 0.01105878
```

分毫不差 —— 这说明**折算公式是对的**；两个工具报的数不一样，差别全在"查了哪张
价目表"，不在"算了哪几个字段"。

### 累计值还是单步值 —— 一个数里塞着两种语义

OpenCode 每走一步就发一个 `step_finish`，**每一步都带一份 token 账**。第一版
读数取的是**第一个** `step_finish`，于是 27 次运行的 token 中位数只有 37232 ——
看起来比 Claude Code 便宜 18 倍。

改取**最后一个**，变成 62022 —— 还是差得离谱，但依然说不通：一次修缺陷要改代码、
跑测试、看结果，怎么可能只生成几十个 token？

**最后是抓了一次完整的事件流，逐字段对出来的**（把 `src/calc.py` 里的加法改成
减法，五步）：

| 步 | input | output | reasoning | cache.read | total |
| --- | --- | --- | --- | --- | --- |
| 1 | 35009 | 30 | 78 | 1956 | 37073 |
| 2 | 141 | 45 | 0 | 36964 | 37150 |
| 3 | 121 | 75 | 0 | 37104 | 37300 |
| 4 | 92 | 45 | 0 | 37224 | 37361 |
| 5 | 121 | 19 | 0 | 37315 | 37455 |

**两种语义混在同一个 `step_finish` 里：**

- `input` / `output` / `reasoning` 是**每一步的增量** —— 第一步 35009（系统提示
  + 工具定义 + 提问，一次性进了模型），第二步就掉到 141；`output` 也会从 75 掉回
  45。**它们要加起来。**
- `cache.read` 是**累计值** —— 1956 → 36964 → 37104 → 37224 → 37315，一路只增不
  减。**取最后一个就对了。**

这也讲得通：每一步都要把整段对话再送一遍，绝大部分命中缓存。所以"没命中缓存的
那部分"是每步新增的少量（加起来），而"从缓存读了多少"是整场累加（取最后）。

**`total` 那格不能信** —— 它是"本步的 input + output + reasoning + **累计的**
cache.read"拼出来的，既不是本步的总量，也不是整场的总量。所以整场总量自己算。

**手算可验**：上面那五步加起来是 —— 输入 35484、输出 214、推理 78、缓存读 37315：

```
35484×0.30/1e6 + (214+78)×1.20/1e6 + 37315×0.06/1e6
= 0.0106452 + 0.0003504 + 0.0022389
= 0.0132345
```

跟 :func:`opencode_tokens` 算出来的一模一样 —— 单元测试里就钉着这个数。

**这条坑值得单独写一节，因为它有个特别坏的性质：算出来的数看起来完全正常。**
37232 不是 0，不是 `None`，在看板上就是一列正常的整数 —— 谁也不会怀疑它。**一
个错误的数字，长得和对的数字一模一样。** 而且它两次都骗过了人：取第一个不对，
取最后一个也不对，只有把整条事件流拉出来逐字段对，才能发现这个数压根不是那么
回事。

**所以逐步明细现在原样存进日志。** 原始输出是截断的（留尾部 4000 字），事后翻不
回来 —— 口径再改就得重跑几十次真任务。每条记录里存一份 `token_steps`，折算方式
变了直接重算，不必重跑。

### 推理 token 算不算输出

OpenCode 把 `reasoning` 单列一格，Claude Code 与 Codex 的输出计数里已经含了推
理。**各家都按输出价给推理计费** —— 所以不并进去，等于白送 OpenCode 一截便宜。
那是记账口径的差别，不是能力差别。归一化时 `output = output + reasoning`。

### "0 不是免费"

OpenCode 在没有登记价目表时会把成本报成 `0`。**记成 0，看板上就会冒出一条
"这个执行器便宜到离谱"的假差异** —— 那是记账口径的差别，不是能力差别。所以
**读到的 0 一律当作"没标价"**，该格显示"无样本"。

## 五、统计怎么做

**没有 scipy。** 依赖越少，结论越不会被"某个库的版本变了"污染；而 Fisher 精确
检验的数学只需要一行组合数。

- **成功率** → Fisher 精确检验。2×2 表，双侧，按 Fisher 的定义把**所有**边际相
  同的表都算一遍取概率之和，不是"双尾各半"。
- **成本、耗时** → 中位数的**置换检验**。把两组的数混在一起重新分组，看观测
  到的差距有多少种分法排得上。样本够小（组合数 ≤ 200000）就**精确枚举**，否则
  蒙特卡洛（种子固定，+1 修正）。**方法名会写明是哪一种** —— 把蒙特卡洛说成
  "精确检验"就是在骗人。
- **多重比较** → **Holm 校正**。实际参与比较的是三个执行器（gemini-cli 没有样
  本），两两 3 对 × 四项指标 = 12 次检验；不校正的话，"至少有一次显著"几乎必然
  发生（1 − 0.95¹² ≈ 46%）。

**为什么用中位数不用均值**：一次卡死的运行能把均值拖走一大截，而中位数不受影
响；而且这批数据的分布形状**没法验证**（n 太小），正态前提无从谈起。

**为什么用精确检验不用卡方**：卡方近似在期望频数小于 5 时失效得很难看 ——
"9 个任务跑 3 次"正好落在这个区间里。

## 六、环境抖了怎么办

**后端不是永远在线的。** 第一次全量跑（2026-11-10 03:38 起）正好撞上 MiniMax
的限流：Claude Code 连续 27 次返回 API 层错误，Codex 的探针直接吃到一句
"We're currently experiencing high demand, which may cause temporary errors."
—— **54 次运行全部作废**。

那 54 条记录归档在
[`executor-benchmark-incident-2026-11-10.jsonl`](executor-benchmark-incident-2026-11-10.jsonl)。
它们没进看板 —— **那不是执行器的能力数据，是后端当时在抖**。

### 两件事因此改了口径

**一、原始输出要留着。** 那一轮只留了一句"执行器报错：（没有说清楚）"，所以
**分不清是限流、是能力差、还是参数不认** —— 只能靠再手跑一遍探针才定位到是
后端。现在每条记录都带一份脱敏后的原始输出（最多 4000 字，保留换行，**留尾
部** —— 报错通常在最后）。

**二、只对环境级故障重试。** 重试的是**后端自己的话** —— 限流、繁忙、暂时不
可用，外加后端自己报出来的 429/5xx：

| 情况 | 算不算环境问题 | 重试吗 |
| --- | --- | --- |
| 后端说"我忙不过来" / 429 / 5xx | 是 | **重试** |
| **额度用完了**（用量上限 / quota） | 是，但重试没用 | **不重试，停下来** |
| 超时（跑太久被掐了） | 否 | 不重试 |
| "模型没做对"（能力问题） | 否 | 不重试 |
| 认不出原因的环境错误 | 认不出 | **不重试** |

**超时不在重试之列，这是刻意的。** 超时是执行器自己跑得慢 —— 重试只会把"它
慢"盖成"它行"，而这次评测要量的恰恰是能力。**认不出原因就不重试** —— 宁可
少重试，也不要把能力差重试成通过。

**重试次数记在记录里，也摆在看板上。** 一个执行器次次都要重试才跑得通，那本
身就是结论 —— 藏起来，看板上就只剩一个干干净净的"成功率 90%"。

### 第三件事：额度用完了 ≠ 忙不过来

第二次跑 OpenCode 时撞上了：**MiniMax 的 OpenAI 兼容端点返回 `429`，正文是
"已达到 Token Plan 用量上限：请升级 Token Plan 套餐或购买积分补充用量。
(2056)"。**

**429 看着像限流，其实是"额度用完了"。** 按限流去重试的代价是实测出来的：24
次运行 × 2 次重试 = **48 次白跑的调用**，每次拿回来的都是同一句"额度用完
了"。额度不会因为重试而多出来 —— 重试只会把同一个失败再烧两遍。

所以口径上分成两路：

| 认出来的说法 | 判断 | 处理 |
| --- | --- | --- |
| high demand / rate limit / 429 / 5xx | 忙不过来 | 等一等，重试 |
| 用量上限 / quota / 余额不足 | **没额度了** | **停下来**，别再撞 |

**停下来之后不是从头再来。** 撞上额度的那一轮：跑完的记着（不重跑），剩下
的记成"没跑成"并写明"额度用完了，没跑（不是没做到）" —— **"没跑成"是空缺，
不是结果**，所以补了额度再跑一次，那些空缺会被真正跑出来的数顶掉。

**这条区分还纠正了一个更早的疏漏。** 原来续跑逻辑是"记过就跳过"，于是那 24
条"没跑成"会**永远挡住**重跑 —— 除非人工去删日志。现在改成：**只有跑过的
（有通过有失败）才不再重跑，"没跑成"的一律重跑。**

## 七、怎么跑

```bash
# 全量矩阵（9 任务 × 3 次 × 4 执行器）
.venv/bin/python -m scripts.run_executor_benchmark \
    --attempts 3 --timeout 420 --retries 2 \
    --log docs/evaluation/executor-benchmark-runs.jsonl \
    --board docs/evaluation/executor-benchmark-board.md

# 只重算看板，不重跑（结论要能被重新算一遍）
.venv/bin/python -m scripts.run_executor_benchmark \
    --render-only --log docs/evaluation/executor-benchmark-runs.jsonl
```

**探针在前面。** 一个执行器连"回答一个字 ok"都做不到（后端连不上、认证过期、
参数不认），就别急着跑 27 次真任务 —— 探针不过直接记"没跑成"，并把原因写进
原始记录。**探针超时就等于"它压根没起来"** —— 不管它有没有吐出过一个字，
让它接着跑 27 次真任务只会把同一个环境问题重复 27 遍，还烧 27 遍的钱。

**中断了可以接着跑。** 每跑完一次就往 JSONL 里追加一行；重跑时按
`(执行器, 任务, 次数)` 跳过**已经跑过**的（跑过的 = 通过或失败）。**"没跑成"
的不算跑过** —— 它是空缺，环境修好了就该重跑，重跑出来的数会把它顶掉。

**源仓库被动了，整轮就停。** 每次运行前后都对源仓库做一次全文件哈希；一旦
对不上，立刻中止并退出码 3 —— 因为工作区是从源仓库拷出来的，源仓库被改了，
后面所有运行都建在污染过的地基上。**第一次失败、后面几次成功，全是假的。**

**凭证只从环境变量来**，配置文件里只写环境变量的**名字** —— 生成的 provider
配置不进版本库，`sk-` 一律脱敏。

### 出口门怎么判

> **关键判据**：`TASK-P2-018` 的评测数据显示不同执行器在至少一项指标上存在**统计
> 上可辨的差异** —— 否则"可替换执行器"只是名义上的。

**过了，而且过了不止一项。** token 中位数三对全部显著（Holm 校正后 p = 0.0003），
成本中位数两对显著，耗时中位数两对显著。

**但这个"过"要说清楚是怎么过的 —— 这页不打算把话说漂亮：**

**一、能力上没测出差异。** 三个执行器在这 9 条缺陷上**全都是 27/27，回归率全是
0**。成功率上的 p 值是 1.0 —— **一点差异都没有**。所以这批评测能说的只是"这三个
执行器**都做得到**"，**说不了"哪个做得更好"**。任务集只有 9 条、每条都是单文件
级别的修法，对 MiniMax-M3 这种模型来说太容易了 —— **天花板效应**，不是执行器
之间平手。

**二、可辨的差异全在"怎么干"上，不在"干不干得成"上。** 差得最显著的是 **token
用量**：Claude Code 用掉 OpenCode 的 **5.19 倍**。看缓存占比就明白了 —— Claude
Code 90.9% 的 token 是缓存读，说明它**把同一批文件反复读了很多轮**（37 轮一
次运行）；OpenCode 只有 45.5% 命中缓存，它的上下文更"干净"。**token 差 5 倍，
耗时长 42%，成本差 2 倍** —— 这是三种不同的干活方式，不是三种不同的能力。

**三、Codex 是这批数据里性价比最高的。** 它比 Claude Code 少用 45% 的 token、
便宜 34%、还快 8%（虽然这 8% 不显著）；比 OpenCode 少用 65% 的 token、跑得快
53%，而成本上的差别（1.31×）**并不显著**。**OpenCode 唯一的优势是 token 读数
最小 —— 但它慢 42%~53%，在墙钟时间敏感的活儿上不划算。**

**四、别把这些结论外推。** 同一个模型、同一个任务集、同一台机器 —— 换了模型，
排名可能反过来（§九）。

### 三个"没敢说的"

- **Gemini CLI 缺席。** 四个执行器里只测了三个，**四分之一的执行器矩阵是空的**。
  "可替换执行器"这句话只在测到的三个上成立。
- **成本里缓存占大头。** 三个执行器的缓存读占比分别是 90.9% / 86.2% / 45.5%，
  而缓存读只要 $0.06/M。**换个价目表，这三列的相对关系可能变** —— 缓存越便宜，
  用得多的执行器越划算。
- **回归率全是 0 不代表它们不会引入回归。** 回归套件只有 43 条，9 条缺陷都是小
  修法，**这个规模抓不到大的回归**。

## 九、这页没说的、也没敢说的

- **样本量。** 27 次/执行器，够Fisher 精确检验用，**不够**支撑"这个执行器一定
  更好"这种断言。看板能说的是"在 9 条缺陷 × 3 次这个规模上，差异有多大、是否
  显著"。
- **天花板。** 三个执行器在这 9 条缺陷上全满分 —— **测不出能力上限的差异**。
  要看出"谁更可靠"，任务集得更难（跨模块、依赖多的那种），或者换一个弱一档的
  模型。**当前这批数据只对"强模型 + 小任务"这个组合有效。**
- **同一个模型。** 四个执行器跑的都是 MiniMax-M3。这是为了控制变量，但结论
  **不能外推**到别的模型 —— 执行器排名可能随模型而变。
- **任务集只有 9 条。** 覆盖了几类修法，但覆盖不了所有缺陷类型。
- **"没跑成"的执行器不参与两两比较。** 这不是漏算，是口径：它没跑成，说明的
  是"配不对"，不是"能力差"。但它也就没法参与显著性比较了 —— Gemini CLI 就是
  这么空着的。
- **成本口径有保底假设。** 缓存写按输入价算、缓存读按 $0.06/M 算 —— 换个
  价目表，成本的绝对值会变，**相对关系不一定变**（缓存读占大头，尤其如此）。
- **token 计数本身也是各工具自己说的。** 口径已经把能归一化的都归一化了（缓存
  读写、推理 token、Codex 的重复计费），但**三家对"工具调用的参数算不算输出
  token"的处理未必一致** —— 那是各家自己实现的，外部核对不了。所以 token 这一列
  应当读成"**按各工具自己报的数折算**"，不是"按 API 账单折算"。**真要较真，得
  对一遍供应商账单。**
- **墙钟时间受本机负载影响。** 三次运行是连着跑的，中间没有别的负载 —— 但这
  台机器上同时开着别的东西就会偏。耗时这一列的 p 值本来就只有 0.0019~0.0038，
  **别拿它当精确的性能排名。**
